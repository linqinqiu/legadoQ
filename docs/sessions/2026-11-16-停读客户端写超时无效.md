# 停读客户端：写超时那条路走不通（实测）

> 2026-11-16 ｜ 目标：把 `stalled-client-check`（任务 #36 / #69）从红变绿，或至少证明当前的手段无效。

## 背景与目标

工作树里有一份未提交的改动，想在应用层给「大响应写」加超时（`LEGADO_SLOW_CLIENT_WRITE_TIMEOUT_MS`，默认 1000ms），
做法是在 `StaticWeb.kt` 里把 `call.respondBytes` 丢进子协程，再用 `withTimeoutOrNull` 等它，超时就取消
`writeJob` 与 `call` 自己的 Job。另外 `Application.kt` 把 `applyIoParallelism()` 提前到类初始化。

这一轮要回答的只有一个问题：**这个办法对门禁有用吗？**

## 核验发现

实测环境：`legado-0.2.42-all.jar`（含上述未提交改动，fatJar 22:39 重建），
`start.mjs --port 12345 --no-open`，临时数据目录，`kotlinx.coroutines.io.parallelism=200` 已生效（`jcmd VM.system_properties` 确认）。

### 1. 门禁照样红，而且是「答不上来」而不是「答得慢一点」

```
PASS 基线：轻请求本身是快的  — /healthz 5ms · /api/sources 4ms
FAIL 停读客户端不许把轻请求拖慢到不可用  — 15045ms（基线 5ms）
FAIL 停读客户端不许让数据库读接口饿死    — 15028ms（基线 4ms）
stalled-client-check: PASS 4 / FAIL 2
```

连跑两次，两次都是 15.0 秒（15036 / 15045ms）——**正好是 curl 与门禁自己的超时值**，不是真答完的时间。

### 2. 卡住的是「原生阻塞写」，而且每条连接精确占一条 IO 线程

停读期间抓 `jcmd Thread.print`：**恰好 24 条**线程停在

```
sun.nio.ch.SocketDispatcher.write0   (Native Method)
  → CIOWriterKt$attachForWritingDirectImpl$1.invokeSuspend
  → kotlinx.coroutines.internal.LimitedDispatcher$Worker.run
```

即 CIO 的直写路径在 `Dispatchers.IO` 上做**阻塞**写，一个停读对端钉死一条线程。
抓取当时 37 条 dispatcher 线程（24 条卡在写、其余 parked 空闲），**没有**任何 `waiting to lock` 记录。

### 3. 不是死锁，是排队：放开超时等它，33.8 秒后答得出来

```
curl -m 40 /healthz   → 200, 33.82s
curl -m 40 /healthz   → 200, 0.013s   ← 队列一泄，立刻恢复
```

所以修的方向是「别让阻塞写占着线程」，而不是「把卡住的线程杀掉」。

### 4. 关键反证：把写超时关掉，卡顿一模一样

把 `LEGADO_SLOW_CLIENT_WRITE_TIMEOUT_MS=600000`（等于让那段超时逻辑失效）重启，再压 24 个同形对端：

```
000 2.17s / 000 2.01s / 000 2.18s / 200 0.70s / 000 2.01s ...
```

10 次采样 9 次 2 秒超时，和开着 1 秒超时时没有区别。**这个旋钮既不解决也没拖累**——
它在应用层拿一个正在 `write0` 里阻塞的协程没有任何办法：取消 Job 是协作式的，
取消 `call` 的 Job 也不会替 CIO 把那条 socket 关掉。停读对端的 socket 从未被服务端主动关闭
（`park.mjs` 里的 close 回调一次都没打印）。

### 5. 附带发现：停读对端一多，后面的连接连响应体都拿不到

同一段脚本三次跑，「真的读完开头就停手」的对端数是 **24 / 8 / 10**。
后两类说明相当一部分连接**根本没收到大响应**（读到的字节数是 0）——卡住的写已经把那一路堵住了。
所以门禁里「确实造出 N 个停读连接」这条判据本身也会随负载漂，读它的人要知道这点。

## 追加实测：换 Netty 引擎，门禁全绿

同日 23:5x 在同一份代码上做了一次引擎 spike（独立 worktree `E:/legado-out/spike-netty`，从 `8b1ecb7` 拉出，
只改两处：`build.gradle` 加 `io.ktor:ktor-server-netty:3.4.3`、`Application.kt` 把 `embeddedServer(CIO, …)` 换成 `Netty`）：

```
PASS 基线：轻请求本身是快的              — /healthz 16ms · /api/sources 102ms
PASS 确实造出了 24 个"读完开头就停手"的连接 — 每个只读了约 65751B
PASS 停读客户端不许把轻请求拖慢到不可用     — 9ms（基线 16ms）
PASS 停读客户端不许让数据库读接口饿死       — 24ms（基线 102ms）
PASS 客户端全部撤掉之后服务立刻恢复正常     — 5ms
NOTE 归因：0 / 3 条工作线程此刻卡在 socket 写上（24 个对端停读）
NOTE 60 个停读对端：/healthz 8ms · /api/sources 8ms · 卡在写上的线程 0 / 3
stalled-client-check: PASS 6 / FAIL 0
```

连跑两次都是 6/0（第二次 /healthz 7ms、/api/sources 7ms）。两个关键差别：

1. **卡在 socket 写上的线程从 24 变成 0** —— Netty 的写是非阻塞的，对端不读只让那一路停在「可写未就绪」，
   不再占线程；
2. 停读对端这次都**读到了 65751B**（CIO 时最多 8192B、甚至 0B），说明响应真的发出去了，只是没人继续收。

顺带确认接口正常：`/healthz` 返回 `0.2.42 / build 55 / sha 8b1ecb7`，`/api/sources` 200。

构建耗时 8m33s（含首次拉 netty 依赖），`:app:fatJar` BUILD SUCCESSFUL。随后按同一方案落到主树，见文末「落地」。

## 决策与取舍

- **不要**把「应用层写超时」当成任务 #36 的解法继续推。它证明无效：写卡在原生调用里，取消是协作式的。
  这份未提交改动如果要留，只能留成「记录性的旋钮」，不能当成修复，更不能据此把门禁标绿。
- **也不该**回到「只要抬 `io.parallelism` 就完事」。提交 `ea90a89` 的说明写「/healthz 从 15 秒回到 0.6 秒」，
  在当前门禁形状下（24 个同时停读、`setBufferSize(256)` + pause）复现不出来——今天仍是 15 秒。
- 真正的解法只剩 gates-guide §6.3.1 早就写下的那条：**换非阻塞写的引擎（Netty）**，
  让「对端不读」变成「OP_WRITE 未就绪」而不是「占住一条线程」。这属于改运行时，单独排期。

### 引擎换掉之后，容易坏的四面都验过（主树，真数据目录）

| 面 | 探针 | 结果 |
|---|---|---|
| gzip 压缩 | `GET /api/sources` + `Accept-Encoding: gzip` | 200，`content-encoding: gzip`、`vary: Accept-Encoding`，341ms（~1MB 书源清单） |
| WebSocket | 裸握手 `GET /api/search/stream` + `Upgrade: websocket` | `HTTP/1.1 101 Switching Protocols` |
| SSE | `GET /api/sources/{id}/debug`（`Accept: text/event-stream`） | 200，`text/event-stream; charset=UTF-8`、`cache-control: no-store`，首帧 `event: start` 立刻到 |
| 静态资源 | `/healthz` 的 `ui` 字段 vs 磁盘 `dist/assets` | 都是 `index-BOK0oZB-.js` |

踩坑一条：书源的 `id` 就是 URL，拼进路径**必须先 `encodeURIComponent`** ——
第一次没编码直接拿到 404，差点误判成"Netty 不支持 SSE"。


## 遗留

1. **把 Netty 换上去**（spike 已证明有效，见上一节）：主树改两行即可，但要单独一轮做完整验证 ——
   后端 `:app:test`、前端 `web test`、`version:check`/`docs:api-check`/`changelog:check`，
   以及 TTS / WebSocket / 压缩这几个引擎相关面（CIO 的 `connectionIdleTimeoutSeconds` 这类配置没有搬过去）。
2. 门禁判据「确实造出 N 个停读连接」会随负载漂（24/8/10），建议改成「至少一半」之外的更稳形状，
   或把这个漂移写进 NOTE。
3. 若以后有人再提「给响应写加超时」，先看本文档 §4：那条路在应用层无效，除非换成能中断原生写的机制（Netty 引擎，或主动关掉那条 socket）。
