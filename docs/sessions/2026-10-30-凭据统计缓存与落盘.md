# 凭据管理「N 个书源用到」：从每次全表扫到落盘 + 触发器版本

## 背景与目标

`GET /api/cookies` 打开时要给每个凭据桶标一句「N 个书源用到」。这一句是全库统计：
每本书源的 payload 里有哪些 http(s) 地址、归到哪些注册域。0.2.0 期间它被改成了
「每个源只扫一次」，但仍然是**每次打开就重算**，界面要等 2~3 秒；冷启动第一次打开能到 6 秒以上。
目标是把打开面板的等待压到无感，并且冷启动不再背着一次全表扫描。

## 核验发现

在同步到 5,598 本书源（payload 合计 24 MB）的库上量到的：

| 环节 | 耗时 |
| --- | --- |
| 只读 5,598 行 payload（`getBytes`） | 0.34 s |
| 手扫字节找 `http(s)://` 主机名 | 0.29~0.30 s（预热后） |
| 正则 `HOST_IN_URL.findAll` 找主机名 | 2.85 s |
| 老的整条扫描（正则 + 每个主机走 URI 解析） | 4.9 s（预热后） |
| 老扫描在**启动竞争**下的冷 JVM | 3~13 s（两次实测 3.07 s / 13.09 s） |

两处意外的成本：正则的大小写不敏感让 java.util.regex 走了最慢的路径（24 MB 要 2.8 秒）；
每个主机名再走一趟 `java.net.URI` 解析，又把时间加上去。扫描本身（逐字节循环）在 JVM 上是 0.3 秒级。

## 决策与取舍

- **字节扫描替代正则**：只认 `http`/`https` + `://` 前缀，主机名按与正则同一套结束符收边
  （`/ \ 空白 " ' < > : ? #`，非 ASCII 字节照收，UTF-8 解码只发生在命中的那一小段）。
  拿整库 5,598 本逐桶对照，差异 0。代价是这段逻辑要自己维护，所以补了 `SourceBucketsTest`
  盯大小写、端口、模板地址、中文域名、协议相对地址、多段后缀、IP 这些分叉点。
- **不扔旧值（stale-while-revalidate）**：书源一写就把统计标记过期，但旧数继续给人看，
  后台线程 1.5 秒防抖后重算。这是「N 个书源用到」的一句提示，晚几秒更新没人会在意，
  让人点开面板等一秒会。
- **结果落盘，配触发器维护的 `source_revision`**：冷启动读一行 JSON（67 KB）就够，
  不再扫全库。版本号用 `source` 表上的 INSERT/UPDATE/DELETE 触发器维护 —— 它在写入的
  同一个事务里加一，「数据改了、版本没动」的窗口不存在，所以启动时敢直接信落盘结果。
- **放弃「表指纹」**：试过用「行数 + payload 总长度」推断书源改没改，被自己的测试逮住：
  删一本、换一本等长地址的书源，指纹一模一样，统计就永远停在旧数上。宁可多算一次，
  也不留一个看起来在缓存、其实已经过期的数。
- **落盘先写 JSON 再写版本号**：中途崩溃时版本号还是旧的，下次启动对不上就重算；
  反过来写会留下「版本对得上、内容却是旧的」这种没法自愈的状态。

## 落地改动

- `data/CookieDao.kt`：`scanSourceMentions` 改走字节扫描（`sourceBucketsIn`，带跨源主机备忘）；
  `cookieBucketMentionsNow` 在扫描前读 `sourceRevision` 并在发布成功后落盘；
  新增 `loadPersistedMentions`（启动后第一次用到时读落盘结果）、`readPersistedMentions`、
  `persistMentions`；`CookieMentions.publish` 改为返回是否落地，新增 `loadedFromDisk`；
  `MentionsWarmer.schedule` 加 `delayMs`（启动传 0，写入仍走 1.5 秒防抖）。
- `data/Database.kt`：DDL 增加 `app_meta` 与三条 `source_revision_*` 触发器；
  新增 `sourceRevision()`；`invalidateSourceCaches()` 同时让凭据统计过期并排一次预热。
- `Application.kt`：启动时 `MentionsWarmer.schedule(database, delayMs = 0)`。
- 测试：`SourceBucketsTest`（10 条，字节抽取口径）、`CookieMentionsPersistenceTest`（4 条，
  版本号、落盘复用、作废、等长地址替换）、`CookieMentionsTest` 保留缓存语义的三条。

## 验证

- 后端 `./gradlew :app:test`：747 条全绿（新增 14 条）。
- Web `npm --prefix web run check|test`：811 条全绿；`docs:api-check`、`version:check`、`changelog:check` 全绿。
- 实机（`E:\legado\product`，5,598 本书源）：
  - 稳态 `GET /api/cookies` 0.05~0.27 s（以前 2~3.5 s）。
  - 写一次书源（`set_group`）后立刻打开：0.048 s（发旧值，后台重算）。
  - 落盘后的重启：第一次打开 0.89 s（其余是 Ktor/JSON/JIT 的首次成本，不再是扫描等待），
    第二次起 0.16~0.27 s。
  - 真库上确认 `app_meta` 有 `source_revision` / `cookie_mentions_revision` / `cookie_mentions_json`
    （67 KB），写一次书源后两个版本号同步前进。

## 遗留

- 启动那次扫描在极端竞争下仍可能到 10 秒以上（只发生在书源刚改过之后的第一次启动），
  已经在低优先级守护线程里跑，不阻塞服务就绪。
- 落盘 JSON 每次重算整份重写（约 67 KB），没有按桶增量更新；以当前扫描频率不值得更细。
