# 书源脚本的 java 桥缺口（0.2.5 / 0.2.6 / 0.2.7 三批）

## 怎么发现的

0.2.4 之后继续按类型实跑（`tmp/type_live.py`，0 文本 / 1 音频 / 2 漫画 / 3 文件 / 4 视频）。
type-3（文件源）连着两份在**搜索阶段**就红，报错是一句完全看不出门道的：

```
searchUrl JS 计算未返回有效地址：TypeError: 未找到对象默认值。 (rule.js#2)
```

打开源看脚本，写的其实只是 `java.encodeURI(key, 'gbk')`。于是把全库扫了一遍：
**启用源引用了、而我们 `java` 桥上不存在的方法**有多少份 —— 结果是最值得做的一类缺口
（`tmp/java_bridge_gap.txt`）：

| 引用份数 | 方法 | 上游在哪 |
|---|---|---|
| 226 | `java.getElement` | `AnalyzeRule` |
| 170 | `java.getElements` | `AnalyzeRule` |
| 146 | `java.toNumChapter` | `JsExtensions` |
| 100 | `java.getString(规则, 内容)` | `AnalyzeRule`（第二参被我们丢了） |
| 91 | `java.encodeURI` | `JsExtensions` |
| 72 | `java.getStringList` / `java.setContent` | `AnalyzeRule` |
| 59 | `java.timeFormatUTC` | `JsExtensions` |
| 53 | `java.connect` | `JsExtensions`（还没做） |

## 关键的一条口径：`java` 到底是谁

上游 `AnalyzeRule.evalJS` 里 `bindings["java"] = this` —— **脚本里的 `java` 就是规则解析器实例本身**
（`AnalyzeRule : JsExtensions`，所以两类方法都在同一个对象上）。
这条决定了怎么补：`java.setContent(x)` 换的是解析器的 content，
之后的 `java.getString` / `java.getElements` / `java.getStringList` 解析的都是 x，而不是页面原文。
我们原来把 `java` 做成一个纯工具袋，缺的就是这半套"再入"。

## 这一版补了什么

`JsSandbox` 的 java 桥上：

- `setContent(内容[, 地址])`、`getElements(规则)`、`getElement(规则)`、`getStringList(规则[, 内容[, 是否当地址]])`、
  `getString(规则[, 内容[, 是否当地址]])`；内容存在 `JsExecutionContext.bridgeContent/bridgeBaseUrl`
  （一次调用一份，不跨源、不跨调用污染）。
- `encodeURI(值[, 字符集])`（上游就是 `URLEncoder.encode`，默认 UTF-8；
  91 处写在 `searchUrl` 脚本里 —— 这就是文件源那句 TypeError 的直接原因）。
- `toNumChapter(标题)`（新增 `rules/ChapterNumbers.kt`，逐分支照上游 `stringToInt`/`chineseNumToInt`/`fullToHalf`）。
- `timeFormatUTC(毫秒, 格式[, 小时偏移])`。

`getElements` 与 `getStringList` **不是一回事**，照上游分开：前者给条目本身（HTML→outerHtml、
JSON→JSON 文本，见 `NodeValue.bridgeText`），后者给**每个元素的取值**（末段是属性名时逐元素取属性、
去重、按行拼 —— 上游 `AnalyzeByJSoup.getStringList` 的 `else -> element.attr(lastRule)` 那一支）。
`城堡小说` 的 `tocUrl` 正是 `java.getStringList(".dropDown@li@data-p")`，要的是 `data-p` 的列表。

## 三处刻意的偏差，写清楚免得被当成笔误

1. **`timeFormatUTC` 的第三个参数按小时换算成毫秒。** 上游写的是 `SimpleTimeZone(sh, "UTC")`，
   把小时当毫秒传 —— 等于这个参数在上游从来没生效（番茄系那些 `, 8` 白写）。
   界面显示的时间差八小时比"和上游一样"更糟，所以按作者意图实现，并在这里记下偏差。
2. **`toNumChapter` 只回「第…章」这一段匹配**，标题后面的文字会被丢掉 —— 这是上游的行为，
   社区源都拿它处理纯序号，不"顺手改好"，否则目录就跟上游 App 对不上了。
3. **JS 传进来的 `true` 三种形状都要认**（Boolean / 数字 / 字符串），Rhino 不帮我们归一。

## 踩到的两个坑（都值得记住）

- `Context.newArray(scope, …)` 必须给**顶层作用域**。`BaseFunction.call` 收到的 `scope` 是函数自己的
  激活作用域，拿它建数组直接 `IllegalArgumentException` —— 表现和"没补方法"一模一样，
  只是错误换了个位置。判据里那条 `列表再入在引擎侧就能取到条目（不过 Rhino）`
  就是为了把"规则算错了"和"Rhino 桥接错了"分开，不用来回猜。
- 测试脚本返回 null 时，断言只写 `expected … but was null` 等于没写。
  `eval()` 现在把 `sandbox.lastError` 带进断言消息，一次就看出是脚本语法错还是桥没生效。

# 0.2.6：响应对象、加密族，以及"注释里藏脚本"

## 桥补到哪儿，失败就前移到哪儿

0.2.5 之后同一批候选（256 份）再全量跑一遍分阶段调试（`tmp/bridge_live_final2.txt`）：

| 阶段 | 0.2.4 后 | 0.2.5 后 | 0.2.6 后 |
|---|---|---|---|
| 仍卡在脚本报错 | 32 | 20 | **15** |
| 只剩站点侧失败（超时 / 403 / 404 / 没这本书） | 217 | 230 | **234** |
| 取到目录或正文 | 5 | 6 | **7** |

剩下 15 家的根因：11 份 `ReferenceError: “org”`（脚本写 `org.jsoup.Jsoup.parse(result).select(...)`，
要的是**白名单 Jsoup 包装**，不是放开 `Packages` 反射）、2 份 JSON.parse 顶罪的 SyntaxError、
1 份脚本自己取 null 属性、1 份拿着我们的异常文本当正文。

## 一、响应对象：`java.get/post` 的结果两种用法都得保住

量出来的事实：库里 **116 处**在 `java.get/post` 结果上继续调字符串方法
（`.split()`、`.indexOf()`、`.replace()`），另有 **115 处**调响应方法
（`.body()`、`.statusCode()`、`.headers('Location')`）。上游回的是真对象，我们回的是字符串 ——
两边只能保一边，这不是设计，是缺陷。

做法（`JsSandbox.responseView`）：让 Rhino 自己 `new String(正文)`，再把响应成员挂在这个实例上。
**不能继承 `NativeString`**（Rhino 里它是包内私有且 final，编译直接拒），走构造函数是唯一干净的路。
这样字符串该有的一切仍走 `String.prototype`，`body`/`url` 是"字段与方法同名"（`CallableBody`），
`statusCode()`/`header(名)`/`headers()`/`raw().request().url()` 由我们补。
`java.connect`（53 处）、`java.head`（13 处）、`java.getStrResponse`（9 处）用同一个形状。

**不往沙箱里放任何 Java / OkHttp 对象** —— `setClassShutter { false }` 那条 RCE 防线不为几个源开口子。

## 二、`sourceComment` 从来没递进沙箱（这批最值钱的发现）

现象：繁星小说、♨️满孟小说、🗂🙈顶通漫画、狸猫故事、猫眼看书…报
`ReferenceError: “sign” 未定义 (rule.js#3)` —— 看着像源自己写错变量。

真因：这类源把可执行代码藏在 `bookSourceComment` 里，规则只写一句
`eval(String(source.bookSourceComment))`；而我们建 `JsExecutionContext` 时只填了
`sourceId/jsLib/database`，**`sourceComment` 一直是空**，于是那句 eval 拿到空串、
签名变量从没被赋值。全库扫：**69 处**脚本读 `source.bookSourceComment`，
其中 **43 处**注释里确实是可执行代码。修法是建上下文时把 `sourceName`/`sourceComment` 一起填上
（`RuleRunner.sourceContext`），判据在 `SourceCommentEvalTest`：
注释里算出的 MD5 签名必须出现在真正发出去的搜索地址上。

## 三、加密族

`ScriptCrypto.kt`（新）+ 桥上的 `createSymmetricCrypto` / `digestHex` / `digestBase64Str` /
`HMacHex` / `HMacBase64` / `base64DecodeToByteArray` / `hexDecodeToByteArray` / `strToBytes` /
`bytesToStr`，以及上游标了 @Deprecated 但源还在调的 `desEncodeToBase64String`
（阅友小说整条搜索签名就这一行）等同名便捷函数。
语义逐条照上游 `SymmetricCryptoAndroid`/`CryptoUtils`：变换没写 `/` 补成 `ALG/ECB/PKCS5Padding`、
DES/DESede 密钥超长截断、`decrypt(String)` 先判十六进制再判 base64、hex 一律小写。
`base64DecodeToByteArray` 给的是**真 JS 数组**（源会 `.slice(0,16)` 切 iv），不是 Java 数组。
**3DES 那一对没做**：启用库 0 处在用，且上游是**五参**签名，照四参顺手写只会留个"看着对其实错"的坑。

摘要/HMAC 的期望值是**用独立工具算出来的**（python hashlib/hmac），
不是拿我们自己的实现回推 —— 否则参数顺序写反了也测不出来。

## 四、顺手修掉的一处自伤：`JSON.parse` 兼容包装顶罪

两个问题一起暴露：
1. 脚本里 `JSON.parse(没解码的串)` 失败时，报错写成 `SyntaxError: … (sandbox-compat#1)` ——
   因为兼容包装函数定义在那个名字的脚本里，Rhino 把来源名按它报了，看着像我们引擎坏了
   （🎨丁斐🅰 两家就是这一类，其实是源数据没解码）。
2. 更要紧的：新的"字符串形状响应对象"`typeof` 也是 `"object"`，被那句
   "是对象就直接返回"的补丁**当成了已解析对象**，于是 `JSON.parse(java.get(url))` 全线拿不到字段。
   现在先问 `valueOf()`：能拿到字符串就按文本解析，只有真对象才原样返回。

## 五、0.2.6 的账

- 后端 `:app:test`：**834 例全绿**（0.2.6 新增 21 例：`JsCryptoResponseBridgeTest` 15、
  `SourceCommentEvalTest` 2、上一批的 `JsRuleReentryBridgeTest`/`ChapterNumbersTest` 继续绿）。
- 实测样本：奇书网络 `java.connect(...).raw().request().url()` 跑通到站点 TLS 层；
  趣书网 `java.post(...).headers('Location')` 跑通到站点 403；
  阅友小说签名与 DES 参数全算出来、接口回「Success」；
  繁星小说/满孟小说/顶通漫画从"变量未定义"变成站点连接层失败（本机连不上它们的站）。
- 踩到又改回来的两个坑：Rhino 的 `newArray` 要给**顶层作用域**（给函数激活作用域会抛
  `IllegalArgumentException`，症状和"桥没生效"一模一样）；`BaseFunction.call` 那些**用不到的形参**
  不能声明成非空（Rhino 会传 null 进来，Kotlin 的非空检查先炸）。

# 0.2.7：整段结果被吞掉的那条判据，与 `org.jsoup` 白名单

## 一、「文本里有 return 就包 IIFE」把结果吞了

`JsSandbox` 原来这样决定要不要包：`Regex("\\breturn\\b").containsMatchIn(rawScript)` 为真就套
`(function(){ … })()`。包了以后 **completion value 就没有了** —— IIFE 里没有顶层 `return`，
整段的值取不到，而且一声不吭。最小复现：

```js
[1,2].map(function (x) { return x * 2; }).join(',')   // 返回 undefined
```

量法不靠自己写扫描器：V8 的 `new vm.Script(src)` 对**顶层** `return` 直接报
`Illegal return statement`，函数内部的 `return` 合法 —— 这正好是判据要的语义
（`tmp/shape_census.mjs`，读线上库 5599 份启用源；按 RuleRunner 的取法先剥掉
`@js:` / `js:` / `@javascript:` 前缀与 `<js>…</js>` 块再判）：

| 形态 | 份数 | 片段数 |
|---|---|---|
| 旧口径会被误包（`return` 只在函数里、整段本身可解析） | **373** | **712** |
| └ 其中片段还写了 `function` 关键字（上一轮报过的窄口径） | 296 | 582 |
| 剥完标记确有顶层 `return`（真该包） | — | 0 |
| 剥完仍解析不了（跨段拼接 / 只是表达式，不参与上面两行） | — | 162 |

**这批里没有一段可解析脚本把 `return` 写在顶层** —— 旧判据在这 5599 份上只会误包，不会漏包。
判据换成 Rhino 自己的 AST：`JsScriptShape.hasTopLevelReturn` 解析出 `AstRoot`，沿 `parent` 链看
`ReturnStatement` 是否落在 `FunctionNode` 里；解析不了才退回旧的文本判断（保守）。
上一轮我按「片段里有 `function` 写法」报过 210 份，以这次全量剥标记的 373 份为准。

## 二、`org.jsoup` 白名单包装（`rules/JsoupBridge.kt`）

0.2.6 末尾剩下的报错候选里 **11 份是 `ReferenceError: “org” 未定义`** —— 脚本写
`org.jsoup.Jsoup.parse(result).select('#congutxt').text()`，要的是 Jsoup，不是反射。
这轮给它一个只读包装：`Jsoup.parse/parseBodyFragment` + `Element/Document/Elements` 的读方法
（`text/wholeText/ownText/html/innerHtml/outerHtml/data/attr/hasAttr/hasText/className/id/tagName/
baseUri/select/selectFirst/getElementsByTag/getElementsByClass/getElementById/get/getAllElements/
children/child/parent/parents/nextElementSibling/previousElementSibling`，Document 另有
`title/location/head/body`）。

三条刻意的边界：
- **不给 `Jsoup.connect`，也不给 `Document.connection()`** —— 网络出口桥里已经有一条 `java.get`，
  不该再从 DOM 对象后面偷偷发请求。
- **不开反射洞**：`setClassShutter { false }` 是底线，测试里专门钉一条 `typeof Packages…` 仍然取不到。
- `Elements` 做成**数组形状**：数字索引要**同时**写 int 键和字符串键，只写一种时脚本里 `list[i]` 取不到
  （这是踩出来的：只写字符串键，`els[0]` 就是 undefined）；另挂 `size/get/first/last/attr/text/html/select/each`。

实跑（`tmp/jsoup_live.py`，口径：用了 `Jsoup.parse` 且**不**依赖 `Packages`/`Jsoup.connect`/`webView`/
`startBrowser`/`getVerificationCode` 的启用源 257 份，逐份走分阶段调试）：

| 落点 | 份数 |
|---|---|
| 读到正文（七点小说 3244 字、天籁小说 35641 字、追书神器 2186 字、露露书屋 1974 字…） | **6** |

`ReferenceError: “org”` —— **一份都没有**。剩下 213 份的失败点在站点与规则层（连不上、被拒、

## 三、订阅地址解析不了回 400，不是 500

# 0.2.8：响应对象补 Cookie，抓取失败只递一句话

`Response.cookie(名)` 的那 1 份**，以及**把 Java 堆栈当正文递给脚本**的那一类
（丁斐两条顶着 `(sandbox-compat#1)`，笔趣阁ai 直接甩出
`io.legado.rules.RuleExecutionException … at io.legado.rules.RuleRunner.fetchDetai…`）。

## 一、Cookie：`headers` 里每名字只留第一个值

`Fetched` 原来只有 `url/body/status/headers`，而 `headers` 是
`response.headers().map()` 取 `values.firstOrNull()` 压出来的 —— 一个名字只剩第一个值。
Cookie 恰恰相反：同一趟里 `Set-Cookie` 可以有多条、重定向每一跳还会各给各的。
所以单靠 `headers` 无论如何拼不出 `cookies()`，必须单独带一份**原文列表**。

- `Fetched` 新增 `setCookies: List<String>`；`fetchDetailed` 在**跟随重定向的每一跳**
  把 `allValues("set-cookie")` 累积进 `cookieJarTrace`，到落地那一跳一起交给响应对象。
  上游 Jsoup 的 `Connection.Response` 就是这个口径：重定向那一跳给的 Cookie，落地时照样能读。
- `responseView` 挂 `cookie(名)` / `cookies()`：按第一个 `;` 切出 `name=value`，后面
  Path/Domain/Expires/SameSite 都是属性；值两侧的双引号按 RFC 6265 去掉。同名以**后到的那条**为准
  （与浏览器覆盖同名 Cookie 一致）；没有这个名字时给 `undefined` 而不是空串，脚本
  `if (hmkey)` 这类判空才成立。
- 顺手补了 `charset()`：从 `content-type` 取 `charset=`，参数名大小写不敏感
  （站点会写 `Charset=GB2312`），引号可有可无。

刻意没做的：不把 Cookie 塞进脚本可枚举的全局对象，也不开任何 Java 反射口子 ——
仍然只是"字符串形状的对象 + 挂几个成员"。

## 二、抓取失败：四个注入点，一开始只改了三个

`java.ajax/post/get` 失败时原来递 `it.stackTraceToString()`。这是照上游
`AnalyzeRule.ajax`（它确实把 stackTrace 当字符串回给脚本）抄的，但我们的类名与行号
对用户毫无意义，而且会被脚本当正文继续往下走。改成 `fetchFailureText()`：
沿 `cause` 链取**第一句非空说明**（最多 5 层，cause 成环也不会转死），没有说明才退回
类名，前缀统一 `抓取失败：`。

改完 grep 了一遍 `stackTraceToString`，发现 `java.connect` / `getStrResponse` 那一处
**漏了**（它走的是 `getOrElse { responseView(..., it.stackTraceToString()) }`，
和 ajax 不是同一个写法）。四个注入点现在统一：ajax、post、get、connect。

## 三、`(sandbox-compat#1)` 不该露给用户

Rhino 会把抛出点按 `(脚本名#行)` 缀在异常文本尾巴上。`rule.js#7` / `jsLib.js#12`
是**书源自己的脚本**，行号对用户有用，留着；`sandbox-compat#1` 是我们注入的
JSON.parse 兼容层，缀上去读起来像"引擎自己坏了"。`eval` 的 catch 里只擦
`sandbox-compat` / `json-compat` / `shape-probe` 这三类内部来源名，其余原样。
