# 0.8.4：收口 80373ff 的重排残留

## 背景与目标

`80373ff`（`server/` → `app/`）之后，仓库处于「构建脚本半迁移」状态。目标是找出所有漏改的
路径引用并修好，顺带处理两个更根本的问题：真实用户数据被跟踪入库、接口文档没有可复现的来源。

## 核验发现

动手前先量，结果与「上一轮已全部改完」的印象不符：

| 项 | 预期 | 实测 |
| --- | --- | --- |
| `:server` 任务名残留 | 0 | Dockerfile 1 处、coverage-report.mjs 1 处 |
| `server/build` / `server/src` 路径 | 0 | Dockerfile 3 处、coverage-report.mjs 2 处、.gitignore 2 处 |
| 门禁白名单里的死路径 | 0 | opensource-hygiene-check.mjs 1 处（2 个文件名） |
| `app/data/` 下的 sqlite | 不入库 | **3 个文件 tracked，WAL 552KB 真实书架数据** |
| API-REFERENCE 的生成脚本 | 存在 | **从未入库**（文档头却写着由它生成） |

两个此前没人发现的问题：

1. **用户数据入库**：`80373ff` 改名时 `.gitignore` 只锚了 `/data/` 与 `/server/data/`，
   新路径 `/app/data/` 漏了。这是隐私问题，不是洁癖问题。
2. **文档无可复现来源**：`docs/API-REFERENCE.md` 首行写着「本文由运行中的 `GET /api/catalog`
   实时生成（`node scripts/gen-api-reference.mjs`）」，但那个脚本在全部历史与全部分支里都不存在。

## 决策与取舍

**Dependabot 的 4 个提交不直接 rebase。** `origin/main` 领先 4 个提交（agp 8.13.2→9.4.1、
metadata-action v5→v6），但它们的基线是重构前的旧路径（`Dockerfile.server`、
`compose.server.yml`、`server/**`）。直接 rebase 会让 `80373ff` 的目录重命名在中途把
`server/` 重新检出、`app/` 变成 untracked —— 实测遇到过，已 abort 回 `2e310da`。
改用 **merge** 一次解决分歧：不逐提交重放，就不存在中途树结构错乱。结果干净无冲突，
`docker.yml` 保留了我们的 `app/**` / `Dockerfile` / `compose.yml`，同时收入 `metadata-action@v6`。

**agp 升级留着不动。** 本项目 `settings.gradle` / `build.gradle` / `app/build.gradle` 只用
`kotlin.jvm` + `kotlin.serialization` + `application` + `jacoco`，没有任何
`com.android.application` 插件。`libs.versions.toml` 里的 `android-*` alias 是上游遗留、
从未被引用。升级无效但无害；要删得连带清理一串 alias，属另一件事，建议另开提交。

**「server」字样不一律改。** `ServerConfig.kt`、`ServerPortModal.tsx`、`server.log`、
`/api/server/port` 路由、`baselines/server-test-failures-47.txt`、
`snapshot.mjs` 的 `legado-server_版本备份` 目录名、Dockerfile 的 `server-build` 阶段名 ——
这些是功能概念（服务端口、服务日志、构建阶段）或历史锚点，不是产品名。改了反而对不上历史。

**`.gitattributes` 加 `eol=lf` 但 `.bat`/`.cmd` 例外。** 此前 307 个文件 `i/lf w/crlf`、
52 个 `w/mixed`（同一文件两种行尾）。Windows 批处理解释器要求 CRLF，一刀切会坏。二进制
（png/jpg/jar/sqlite）显式标记，避免被当文本转换。加完后 `git add --renormalize .`
零纯行尾变更，说明与现有状态兼容。

## 落地改动

所以构建侧本来就是对的 —— 只有 Dockerfile 没跟上。

## 验证

| 项 | 结果 |
| --- | --- |
| 后端 `:app:test` | 535 条，1 条失败 |
| 前端 `npm test` | 667/667 |
| 编译 main + test | 通过 |
| `gen-api-reference --check` | exit 0 |
| `opensource-hygiene-check` | PASS 11 / FAIL 0 / NOTE 1 |
| 旧路径残留扫描 | 0 |

**零回归判定**：唯一失败是 `E2EScenariosTest > scenario 2`（2000 章并发缓存，
`Condition not met within 20000ms` 超时）。归一化类名后与
`tools/verify/baselines/server-test-failures-47.txt` 逐条比对，确认它在基线集合内
（Windows 删不掉被占用的 SQLite 所致）。失败数从基线 47 条降到 1 条。

> 注意：比对时必须把类名从 `io.legado.E2EScenariosTest` 归一化成 `E2EScenariosTest`，
> 否则会误报成「基线之外的新失败」。

**门禁有效性实测**：注入假漂移 → `--check` exit 1；只改生成时间 → exit 0；恢复 → exit 0。
三项都对，才敢接进 CI。

- **Docker 未实际构建**：开发机没装 Docker，只做了静态核对（`:app:installDist` 任务存在、
  `settings.gradle` 有 `include ':app'`、`app/docker-entrypoint.sh` 在且不引用旧 jar 名、
  门禁的 jar 名判据仍通过）。真正验证要等 CI 的 `docker.yml` 跑一次。
- **`libs.versions.toml` 的 `android-*` alias**：无人引用的上游遗留，建议另开提交清理。
- **`stash@{0}`**：rebase 中途的安全网快照（543 文件）。内容已被 HEAD 完全覆盖，
  但作为保险保留着，确认无需要后可弃。
- **`docs/sessions/` 是本轮新建的**：`CHANGELOG.md` 开头一直承诺工程细节记在那里，
  但目录此前不存在。本次补上 README 说明命名与骨架。
