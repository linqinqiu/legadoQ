# 正则列表模式、列表前缀与响应字符集（0.2.4）

## 背景与目标

用户指令：「继续研究重点检验书源，包括文本漫画音频文件源」。做法是把本机库里的启用源按缺陷形状分组，
逐份跑分阶段调试（`GET /api/sources/{id}/debug`，SSE，五个阶段：结构 / 搜索 / 详情 / 目录 / 正文），
按落点找引擎缺陷，改完拿同一批源复跑。这一轮共改六处，全部由实跑暴露，不是照文档猜的。

工具：`tmp/regex_live.py`（23 份 `:` 正则列表源）、`tmp/prefix_live.py`（18 份带 `-`/`+` 前缀的搜索源）、
`tmp/debug_source.py`（单源逐阶段打印）、`tmp/regex_census.py`（正则源清单）。

## 一、AllInOne 正则列表模式（列表规则以 `:` 起头）

**症状**：天涯知识（优+）`http://3g.sbkk8.com`

```json
"ruleToc": {
  "chapterList": ":a href=\"(.*?)\"\\s+target=\"_blank\">(.*?)<",
  "chapterName": "$2",
  "chapterUrl": "$1"
}
```

以前整串被当 CSS 选择器交给 Jsoup，报 `SelectorParseException：Could not parse query ':a href=…'`，
该源永远 0 章。启用库里这种形状的有 23 份（🌿起点中文（男频）、九五小说🎃、黑岩小说①、💫新浪小说网、
快眼小说、🔖食在广州、鬼吹灯🎃、豆豆小说、阅读书库…）。

**上游口径**（`tmp/AnalyzeRule.kt:539`、`tmp/AnalyzeByRegex.kt`）：

- `splitSourceRule(ruleStr, allInOne = true)`：只有首字符是 `:` 才置 `Mode.Regex`，并把实例的 `isRegex = true`。
  `isRegex` 粘在 AnalyzeRule 实例上，于是**后续每条字段规则**同样是 Regex 模式。
- `AnalyzeByRegex.getElements(res, regs)`，`regs = rule.splitNotBlank("&&")`：非最后一级把**所有匹配的整段文本**
  （`resM.group()`）串起来交给下一级；只有最后一级产出条目，每条是 `[group0, group1, …]`，未参与的可选分组为空串。
- `AnalyzeRule.getString` 的 `when (mode)` **没有 Regex 分支** → `else -> rule`：`makeUpRule` 把 `$N` 替换成分组文本后，
  **那条字面量本身就是值**，不再当选择器 / JSONPath 求值。引用正则 `\$\d{1,2}`，即 `$0`…`$99`（`$0` 是整段匹配），
  越界不插入任何字符。`@js:` / `<js>` 代码里的 `$N` 同样会被替换 —— 起点中文的 `<js>java.timeFormat($3)</js>` 就是这么工作的。

**实现**：

- `RuleRunner.nodes()` 首字符 `:` → `regexNodes()`；`&&` 分级必须排在并集切分**之前**
  （快眼小说 `:正文卷[\s\S]*?/ul&&href="([^"]+)">([^<]+)` 的两级语义当成并集就错了）。
- `RuleValue.NodeValue` 增加 `groups` 表示「一次匹配的全部分组」，字段规则改走 `regexItemValue()`；
  `##` 替换、`@put:`/`@get:{}`、`{{}}`、`@js:`、`<js>` 照旧生效。
- `$N` 替换排在 `{{}}` 展开**之后**：分组文本是站点原文，不能再被当成模板 / 脚本展开一次。
- 写坏的正则如实抛 `RuleExecutionException("正则列表规则无法编译：…")`：静默返回空列表的话，
  「规则写坏了」与「站点真没这本书」在体检与调试面板里就再也分不开。

**实测**：天涯知识 目录 351 章 / 正文 337 字；九五小说🎃 100 条命中 → 69 章 → 2,327 字；
黑岩小说① 20 条 → 166 章 → 1,269 字；🎃鬼吹灯🎃#3 100 条 → **808 章**（`nextTocUrl` 翻页也跑通）；
🌸快眼看书™ 100 条 → 11 章 → 2,253 字。

## 二、列表规则开头的 `-` / `+`

`-`/`+` 是目录的排序标记，`chapters()` 自己会剥；可真实源把它抄进了**搜索**规则：
uu书盟 `+@css:.item`、四小说网 `+@css:.bookbox`、🌸快眼看书™ `+@css:.librarylist li`、
免费小说 `-@JSon:$.data.bookList`、笔下文学③④ `+@js:…`、🖼微博博主 `+<js>…</js>`。启用源里 18 份。
前缀占了首字符，两个后果：`isJsRule()` 认不出这是 JS 列表规则（整段脚本被丢给 Jsoup）、
`@css:` 标记被挤到第二位而失效（`selectLegadoSegments` 只认开头的标记）。
报错还是一句完全看不出门道的 `SelectorParseException：String must not be empty`。

**实现**：`stripListPrefixMarkers()` 在 `bookItems()`、`rssArticles()`、`nodes()` 入口统一剥
（`chapters()` 先读 `-` 的反转语义，再交给它，语义不变）。

**实测**：这 18 份源**不再有一条 `SelectorParseException`**，🌸快眼看书™ 全链路通、优·书荒荒 搜索 50 条；
其余失败都是上游本身：域名解析不了、HTTP 404、证书过期、连接超时。

## 三、没配 `ruleBookInfo` 不再抛错

以前缺 `ruleBookInfo` 直接抛异常，而本机 **189 个启用源连这个键都没有**。
`/api/books/chapters` 直取失败时正是靠 `details()` 回落拿 `tocUrl`，一抛就整本目录取不到；
体检也只看到「该书源未配置 ruleBookInfo」，看不到这些源真实的目录与正文表现。
上游 `BookInfo.analyzeBookInfo` 是**逐字段跳过**（每条规则都包在 `if (rule.isNotEmpty())` 里），
现在按同一口径：标题沿用搜索结果，`tocUrl` 退回书页地址。

## 四、纯 `<js>` 段字段规则不再拿整页原文兜底

🔖食在广州 `ruleBookInfo.name` = `<js>result.match(/"book">[^>]+>([^<]+)/)[1]</js>`，
页面没这个结构时脚本抛 TypeError，而这里回退成**整页原文**，书名就成了
《<!doctype html> <html lang="zh-CN">…》，一路脏进书架与阅读记录，调试面板还显示「取到值了」。
上游把 `<js>` 与 `@js:` 一视同仁（都是 `Mode.Js`，`result` 绑当前内容），脚本失败结果就是空。

现在：没有前缀段的 `<js>` 走同一条 `evaluateJs`，取不到就如实为空；
并把正则条目的 JS 绑定也对齐上游 —— `result` 绑的是**这个条目本身**（全部分组列表，脚本可写 `result[2]`），
不再只有 `$0`。库里只有 💫新浪小说网的 `nextTocUrl` 是无 `$N` 的纯脚本，风险面已核。

## 五、远程响应的字符集

同一次实跑发现食在广州取到过《绗16章》—— 「第16章」的 GBK 字节按 UTF-8 解。
`decodeBody()` 只看请求选项里的 `charset`，**没声明就一律 UTF-8**，既不看响应头 `Content-Type: …; charset=`，
也不看页面自己写的 `<meta charset>`。这种错**不抛异常**，只在界面上留下满屏乱码，最难被发现。

按上游 `BookSource.getCharset` 立了优先级（`resolveBodyCharset`，拆成 internal 便于逐条钉判据）：

1. 源在这次请求里声明的 `charset`（作者的话最该先听）；
2. 页面自报的 `<meta charset>` / `<meta http-equiv="Content-Type" content="…;charset=">`；
3. 响应头 `Content-Type` 里的 `charset=`；
4. UTF-8。

响应头排在页面自报**之后**的理由：`charset=iso-8859-1` 常常只是服务器默认值，而 ISO-8859-1 解码**永不报错**，
信它就把整页变成乱码。上游更极端 —— `getCharset` 的响应头那一支实际只在值是 `"utf-8,utf-8"`
这种垃圾串时才命中，等于全靠 meta。

选定之后先**严格**解；解不动再交回 0.2.3 的 `TextDecoding.decodeTextAuto`（BOM → 严格 UTF-8 → 声明 → GB18030），
这样声明错了也还能读。两条护栏：

- 嗅探只对**标记文档**做（第一个非空白字符是 `<`）：JSON 接口的字段里常带 HTML 片段，
  那里的 `<meta charset=…>` 是数据不是这份响应的编码声明。
- 正则限定在 `<meta` 起头的那个标签里、名字以字母起手，正文里裸写的 `charset` 不算声明。

`UrlOptions.charset` 由「默认 UTF-8」改成**可空**，才能区分「没声明」与「声明了 UTF-8」。

## 六、下一轮最大的缺口：书源脚本调用了我们沙箱没有的 `java.*`

按类型抽检（`tmp/type_live.py`，0 文本 / 1 音频 / 2 漫画 / 3 文件 / 4 视频）时，type-3（文件源）
连续两份卡在 `searchUrl` 的脚本上，报错是一句看不出门道的 `TypeError: 未找到对象默认值。 (rule.js#2)`，
脚本里写的是 `java.encodeURI(key, 'gbk')`、`java.connect(url).raw().request().url()`。
把全库扫了一遍（`tmp/java_bridge_gap.txt`）：启用源里引用了、而我们 `java` 桥上**没有**的方法，

份数在这里，是下一轮性价比最高的一块。

音乐-网易（type1）搜索 100 条、`ruleContent` 能算出 mp3 直链，但 `ruleToc.chapterList`
选的是 song 页面里由 JS 渲染的 `id.song-list-pre-cache`，服务端抓不到 —— 上游同样取不到章节，不是我们的差异。

## 七、已知不做

- **豆豆小说**（www.ddkanshu.com）`searchUrl` 的脚本用 `Packages.java.net.*`：沙箱
  `setClassShutter { false }` 一律禁 Java 反射，这是**安全前提**，不为了单个源开洞。

  新浪小说网回的是首页 —— 这些是源或站点的状态，不是引擎缺陷；现在调试面板会把
  「上游说：…」/「页面标题：…」原样带出来，一眼能分开。
