# 请求体编码：不再把 GBK 中文静默存成替换字符

## 背景与目标

排查 0.2.1 遗留数据时发现，真库 `source.source_group` 里有一条 `体检异常`
变成了 4 个 U+FFFD 加残字，接口当时返回 200。目标是让这类请求**在边界上被拒绝**，
并给出人能照做的错误信息，而不是把坏字节写进用户数据。

## 根因

Ktor ContentNegotiation 的 `KotlinxSerializationConverter.deserialize` 走的是
`readRemaining().readText(charset)`：JDK 的 `String` 构造解码默认 `CodingErrorAction.REPLACE`，
无法解码的字节直接变 U+FFFD，既不抛错也不报告。于是 GBK 编码的「体检异常」以合法 JSON
字符串的形式（内容已损坏）进入业务层，`decodeFromString` 当然成功，写库也成功。

上一个会话里测试脚本经 bash 传中文时被 MSYS 转成 GBK，正是通过这条路径把测试数据写坏了。

## 修改

新增 `http/StrictJsonConverter.kt`：只接管**请求方向**，用
`charset.newDecoder().onMalformedInput(REPORT).onUnmappableCharacter(REPORT)`，
解码失败抛 `BadRequestException`，消息里写明「按 UTF-8 重新发送；确实要用其它编码就在
Content-Type 里声明 charset」。响应方向仍委托给 `KotlinxSerializationConverter`，
同一份 `Json` 配置，序列化行为零改动。对非 kotlinx 类型回落到原转换器。

配置方式从 `json(...)` 改为在 `install(ContentNegotiation)` 里
`register(ContentType.Application.Json, StrictJsonConverter(jsonFormat))`。

`Application.kt` 的 StatusPages 补了一层消息穿透：Ktor 的 `convertBody` 会把转换阶段
抛出的任何异常包成 `BadRequestException("Failed to convert request body to …")`，
3.4.3 实测**包两层**。原先的处理器取链条上第一个 `BadRequestException`，正好拿到最外层
那句毫无信息的类名。改为 `Throwable.deepBadRequestMessage()`：沿 cause 链走到底，
取最内层带 message 的 `BadRequestException`。`ContentTransformationException` 分支同理。

## 行为边界

- `Content-Type: application/json`（无 charset）+ GBK 字节 → 400，消息含「UTF-8」。
- UTF-8 中文 → 200，值原样写入。
- `Content-Type: application/json; charset=gbk` + GBK 字节 → 200，按声明解码后原值写入。
  即：编码不是被禁，而是必须**说清楚**。
- 拒绝发生在反序列化之前，库不会被改一半。

## 验证

- 后端 `./gradlew :app:test`：750 条全绿（新增 `StrictJsonRequestTest` 3 条：
  GBK→400 且分组保持空、UTF-8→200 且值正确、显式 charset=gbk→200 且值正确）。
- 实测修复后真库中 `source_group` 与 `book_source_name` 的 U+FFFD 行数为 0；
  被写坏的 `https://www.00xiaoshuo.net/` 分组已通过接口恢复为「体检异常」。

## 遗留

- 只处理 JSON 请求体。表单/multipart 的编码由 Ktor 参数解析负责，路径不同，
  若将来出现同类问题需要单独加闸。
- 客户端库（前端）目前始终发 UTF-8，无需改动。
