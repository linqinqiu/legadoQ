## 青阅 · 1234 端口产品继承了解

> 生成时间：2026-10-19
> 依据：`.` 仓库实读 + 本机端口/接口实测
> 结论先行：**`127.0.0.1:1234` 是青阅的“成品本体”，继承工作应当围绕它做，不要再另起一套前端。**

---

### 1. 一句话定位

青阅是一个**本地单机小说/漫画阅读服务**：Kotlin + Ktor 后端，内置 SQLite 数据库、Legado 书源规则引擎和一套 React Web UI，全部打进一个 fat jar。启动后监听 `127.0.0.1:1234`，浏览器打开就是完整产品，同时对 AI/脚本暴露 130 条 HTTP 端点。

它不是一个“框架半成品”——**1234 上跑的就是可用的成品**。

### 3. 1234 上到底有什么

#### 3.1 技术栈

| 层 | 实现 |
|----|------|
| HTTP | Ktor 3.4.x，默认绑定 `127.0.0.1:1234` |
| 语言 | Kotlin / JVM（随包带精简 JRE） |
| 存储 | SQLite（WAL 模式），单库文件 |
| 规则引擎 | Rhino JS + Legado 书源语义（CSS 选择器、`||`/`&&`/`%%`、`@tag.`/`@id.`/`@children`） |
| Web UI | React + Vite 构建的 SPA，产物内置进 jar 的 `static/` |
| AI 接入 | `GET /api/catalog` 机器可读端点目录 + `docs/AI-AGENT.md` |
| 实时搜索 | `WS /api/search/stream` |

#### 3.2 API 面（130 条，按面分组）

`/api/catalog` 自述覆盖：

> 书源管理 / 发现页 / 搜索 / 登录与凭据 / 内置浏览器 / 阅读 / 书架 / 离线缓存 / 分章规则 / 净化规则 / 图片与媒体 / 进度与笔记 / 朗读 / RSS / 书源订阅 / 备份 / 系统

主要读写链路（继承时最常用）：

```
GET  /healthz                      → 版本与存活
GET  /api/catalog                  → 全量端点目录（AI 接入入口）
GET  /api/sources                  → 书源列表
GET  /api/bookshelf                → 书架
GET  /api/books/{...}              → 详情 / 目录 / 正文
POST /api/search                   → 搜索（另有 WS 流式）
GET  /api/explore/...              → 发现页
```

#### 3.3 安全模型（必须记住）

- **没有账号体系，绑定地址就是唯一的门**：只监听 `127.0.0.1`。
- **同源写门**：GET/HEAD 放行；POST/PUT/DELETE 要求 `Origin == Host`，否则 403。本机脚本无 Origin 头时放行。
- 把 `LEGADO_HOST` 改成 `0.0.0.0` ≈ 把整库写权限交给局域网。
- 结论：**继承开发期间不要改绑定地址，也不要把 1234 暴露到公网。**

### 5. 版本与产物流转（改代码后怎么生效）

```
legado-server/web/src  --npm run build-->  web/dist
        --Gradle 打包-->  server/build/resources/main/static
        --fat jar-->  server/build/libs/legado-server-<ver>-all.jar
        --启动-->  127.0.0.1:1234（或探针端口）
```

- 版本号**唯一来源**：`legado-server/server/build.gradle` 的 `version`；Gradle 写进 jar 清单，服务端读出来经 `/healthz` 报给 UI。
- 当前三处版本并不齐：
  - 1234 实际跑：**0.8.1**
  - 新构建：**0.8.2**（只在 1399 探针上）
  - 父仓库 `src/web`：**0.9.0-alpha**（未接入）
- 因此“继承 1234”的第一条纪律：**先确认你要改的是 0.8.1 的现状，还是把 0.8.2 扶正到 1234。**

---

### 6. 0.8.2 已经做了什么（CHANGELOG 实读）

0.8.2（2026-10-19）修的是**书源列表规则的解析语义**：

1. **`&&` 与 `%%` 按 Legado 语义解析**
   - 以前只认 `||`；`&&` 整串被当成一个 CSS 选择器 → `SelectorParseException` → 该源搜索/目录全空（极速漫画即此故障）。
   - 现在：`&&` 取各支并集，`%%` 按位交错，`||` 仍取第一个有结果的。
2. **列表规则支持 `@tag.` / `@id.` / `@children` 方言段**
   - 字段规则一直支持，列表规则此前不支持；本机 11,280 条非 JS 列表规则中，2,164 条带 `tag.`、1,063 条带 `id.`、30 条带 `children`。
3. **写坏的选择器仍然报错**（带原文），不静默变成“0 条”——区分“规则写坏”与“站点没内容”。

0.8.1 则补齐了 AI 接入面：`/api/catalog` 从 46 条扩到 130 条，并逐条实测回包形状。

### 8. 继承 1234 的正确姿势

#### 8.1 先做的三件事

1. **确认目标版本**：是继续修 0.8.1 的线上问题，还是把 0.8.2 扶正到 1234。
2. **确认改动面**：
   - 改 UI → `legado-server/web`（1234 真正加载的那套），不是 `src/web`。
   - 改接口/规则引擎 → `legado-server/server`。
   - 只是调用/自动化 → 直接打 1234 的 HTTP API，不动代码。
3. **确认提交位置**：`legado-server` 是嵌套 git 仓库，后端改动必须在它自己的仓库里提交，父仓库只把它当未跟踪目录。

#### 8.2 推荐动线

```
读 /api/catalog 与 docs/AI-AGENT.md
  → 用真实接口跑通 搜索 → 详情 → 目录 → 正文
  → 定位问题属于「规则引擎 / 接口 / UI」
  → 改对应源码
  → cd legado-server/web && npm run build（改 UI 时）
  → ./gradlew :server:build（打 jar）
  → 用 1399 之类探针端口先起新 jar 验证
  → 验证通过后再替换 1234 的进程与产物
```

#### 8.3 重启 1234 的注意点

- 当前 1234 是**独立 java 进程**，不是 Docker；停它要先确认没有别的任务在用（有 ESTABLISHED 连接）。
- 替换 jar 前先备份 `dist/qingyue-0.8.1` 与数据库。
- 新 jar 先用非 1234 端口起，确认 `/healthz` 版本、`/api/catalog` 条数、书架数据可读，再切换。
- 切完必须复验：`/healthz`、`/api/bookshelf`、一次完整“搜索→目录→正文”。

---

### 9. 已知雷点

1. **不要再造平行前端**。历史上另起 `frontend-react/` + 独立部署脚本被明确否决；1234 自带 UI 才是成品。`src/web` 是遗留的另一条线，未接入 1234，别默认它是主线。
2. **`git clean -fd` / `git reset --hard` 绝对不要执行**：父仓库有大量未跟踪的新代码（`src/web`、`app`、`legado-server`、`_probe`），一执行全没。
3. **父仓库当前是“重构半完成”状态**：旧 `src/*.ts` 已 staged 删除，新目录未跟踪；不要随手 `git commit` 收尾。
4. **根 `package.json` 仍是旧 rulekit**，在 `.` 根跑 `npm test` 必失败；前端命令要先 `cd src/web`。
5. **109MB 的 `qingyue-ai-framework-v0.8.1-local-backup.tar.gz` 不要入库。**
6. **版本号三处不一致**（0.8.1 / 0.8.2 / 0.9.0-alpha），对外描述时必须说清指哪一个。
7. **1299 已停止；1399 是 0.8.2 探测实例**，不要把它当成第二个产品，也不要在它上面做正式数据写入。
8. **1399 的“新骨架界面”挂载点为空**：`next/index.html` 不存在，0.8.2 目前仍回落到旧 UI。若要推进新 UI，这是明确的下一步入口。

---

### 10. 我对“继承”的理解（一句话版）

> 1234 是青阅的**唯一成品与验收基准**；继承 = 在 `legado-server` 这套源码上继续修规则引擎和内置 UI，用探针端口验证新 jar，确认无误后再替换 1234；所有工作以 1234 的真实接口和真实书架数据为准，不新建平行前端、不改绑定地址、不动未跟踪代码的清理。
