## 我方规则引擎实现定位与差距清单

> 范围：`E:\legado\legado`（青阅 0.8.6）。只描述**当前源码真实行为**，行号以本次核对为准。
> 用途：与 [`upstream-rule-engine.md`](研究-书源规则引擎.md) 对照，定位要补的洞。

### 摘要

引擎主体在 `rules/RuleRunner.kt`（1617 行），取值层 `rules/RuleValue.kt`，`@put/@get` 拆分在 `rules/RuleSplit.kt`，
`地址,{JSON}` 的切割在 `content/LooseJson.kt`。已确认 **5 个具体差距**：逗号后空白不容忍、
`extractTail` 取到字符串结尾、详情阶段 `@put` 传不到目录、详情 trace 的失败标记恒为真、
`downloadUrls` 后端不读。目录为空时**无兜底**。

### 1. 搜索结果的 bookUrl 链路

**入口**：`app/src/main/kotlin/io/legado/rules/RuleRunner.kt:161`

```kotlin
val url = item.value(rule.string("bookUrl"), jsSandbox, body, sourceUrl)?.absolute(sourceUrl)
    ?: return@mapNotNull null
```

**`absolute()`**：同文件 `RuleRunner.kt:1455-1471`

```kotlin
private fun String.absolute(base: String): String = try {
    val cleanBase = base.substringBefore("##").substringBefore("#").trim()
    val withoutSlash = trim().removePrefix("/")
    if (withoutSlash.startsWith("http://", ignoreCase = true) || withoutSlash.startsWith("https:// ignoreCase = true)) {
        return withoutSlash          // ← 已是绝对地址：原样返回，尾巴保留
    }
    ...
```

**结论**：`地址,{JSON}` 形态**能完整穿过搜索→详情链路**。
漫画源 `ruleSearch.bookUrl` 的 JS 规则返回 `"https://…?comic_id=…&client-type=android&…," + JSON.stringify(b)`，
`absolute()` 原样返回，`,{"method":"GET","headers":{…}}` 尾巴不丢。
（这与上游 `NetworkUtils.getAbsoluteURL` 对绝对地址原样返回的行为一致。）

**但仍存在的差异**：上游 `paramPattern = Regex("\\s*,\\s*(?=\\{)")` **容忍逗号前后空白**；
我们 `LooseJson.extractTail` 用 `value.indexOf(",{")`，**只认逗号后紧跟 `{`**。
源里写成 `地址 , {"method":"POST"}`（逗号后有空格）时，我们切不开，整串被当成 URL。

### 2. `splitUrlOptions` / `LooseJson.extractTail` 支持的形态

**文件**：`app/src/main/kotlin/io/legado/content/LooseJson.kt`

**`extractTail`（第 144-168 行）**：

```kotlin
fun extractTail(value: String): Pair<String, String?> {
    val start = value.indexOf(",{")
    if (start < 0) return value to null
    // 按花括号配对往后找闭合 }
    ...
    return value.substring(0, start) to value.substring(start + 1, index + 1)
}
```

函数自己的注释已承认两个限制（第 139-143 行）：

> - 返回 `Pair(去掉尾巴的 URL, 尾巴文本)`；没有 `,{` 或括号不闭合时尾巴为 null。
> - **现有实现是「取到字符串结尾」**，源里 `,{...}` 后面还跟着别的东西时严格 JSON 直接解析失败。

**`splitUrlOptions`（`RuleRunner.kt:976-1008`）**：先 `LooseJson.extractTail` 拿尾巴，
再 `jsonOption(tail)`（严格）→ `jsonOption(LooseJson.toStrict(tail))`（宽松），
解析出 `method / body / headers / charset / webView`。两次都失败则整串当 URL。

**`toStrict` 覆盖的非规范写法**（注释第 9-16 行，基于本机 4876 源实测，严格 JSON 失败 1571 处）：
单引号键值、裸标识符键、全角引号、字符串里裸换行/制表符、尾随逗号、`//` 与 `/* */` 注释。

**差距**：
1. 逗号后空白不容忍（上游容忍）。
2. 括号不闭合 → 尾巴整体丢弃（上游 `paramPattern.find` 至少能切出地址部分）。
3. `MAX_LENGTH = 8192`，超长尾巴直接返回 null。

### 3. `@put` / `@get` 变量表与跨阶段传递

**存储**：`RuleValue.kt:252-256`

```kotlin
internal fun snapshotVariables(): Map<String, String> = ruleVariables.toMap()
internal fun seedVariables(initial: Map<String, String>) {
    if (initial.isNotEmpty()) ruleVariables.putAll(initial)
}
```

变量表活在**单个 NodeValue** 上（`ruleVariables`），跨调用靠 `RuleRunner` 手动存取。

**键的规则**：`rememberRuleData(url, vars)` / `recallRuleData(url)`，**按 URL 字符串做键**。

**详情 → 目录的传递（`RuleRunner.kt:483-485`）**：

```kotlin
val tocUrl = value("tocUrl")?.absolute(bookUrl) ?: bookUrl
// 目录那一侧（chapters）拿到的是 tocUrl，把变量也挂到 tocUrl 上 —— chapterUrl 常写 `@get:{bid}`
rememberRuleData(tocUrl, recallRuleData(bookUrl))
```

**这是已确认并已修复的缺陷**：原来只回灌了 `recallRuleData(bookUrl)`（即**搜索阶段**存的变量），
**详情这一步新 `@put` 的变量没有并进去**。

漫画源正是这个形态：
- `ruleBookInfo.name = $.comic_name@put:{cid:$.comic_id}`（详情阶段 put）
- `ruleToc.chapterUrl = @js: cid='@get:{cid}' …`（目录阶段 get）

结果 `cid` 取空 → 拼出 `.../getchapterdata?comic_id=&chapter_id=…` → 上游回 **422**，
界面上只看到「上游返回 HTTP 422」，看不出是变量没传过去。

**已修复**（`RuleRunner.kt:485`）：`rememberRuleData(tocUrl, recallRuleData(bookUrl) + root.snapshotVariables())`。
判据 `RuleVariableHandoffTest`（2 条，用 `responseFetcher` 注入假响应免网络）：
修复前精确复现 `cid=&path=/c1`，修复后通过；第二条守住「搜索阶段 put 仍能传到目录」不回归。

### 4. `ruleBookInfo.init` 的执行时机与语义

**`RuleRunner.kt:456-467`**：

```kotlin
// init 常写成「JS + 后置取值路径」的规则链（如 <js>…</js>$.data）：必须求值，不能当路径用。
val root = when {
    initRule.isNullOrBlank() -> baseDoc
    initRule.contains("<js>") || initRule.trimStart().startsWith("@js:") || initRule.trimStart().startsWith("js:") ->
        runCatching { baseDoc.value(initRule, jsSandbox, body, bookUrl) }.getOrNull()
            ?.takeIf { it.isNotBlank() }?.let { NodeValue.document(it) } ?: baseDoc
    else -> baseDoc.at(initRule)
}
// at() / NodeValue.document() 会另起一个节点，变量得再灌一次
root.seedVariables(seedVars)
```

**语义**：`init` 的返回值**替换 base document**，后续字段规则都基于这个新 root 取值。
这解释了两件事：
1. 漫画源 `init` 用 `java.aesBase64DecodeToString` 解出真 JSON 后，`$.comic_name` 才有值 —— 我们补上 AES 桥后详情/目录立刻通了。
2. `init` 失败时 `runCatching{}.getOrNull()` 返回 null → **安静退回 `baseDoc`**（原始密文），
   于是后续 JSON 路径取不到值，报的却是 `Unexpected End Of File position 36020` 这类和真因无关的错。

### 5. `bookSourceType` 在引擎里的分叉

**读取点**：`RuleRunner.kt:1475-1476` 与 `1580-1581`


### 1. `地址,{JSON}` 请求描述符在哪解析

**文件**：`app/src/main/java/io/legado/app/model/analyzeRule/AnalyzeUrl.kt`

处理链在 `initUrl()`（第 164-172 行）：


`analyzeUrl()`（第 235-301 行）是关键：


**切割正则是**（第 799 行）：

```kotlin
val paramPattern: Regex = Regex("\\s*,\\s*(?=\\{)")
```

即：**逗号（前后可有空白）+ 后面必须紧跟 `{`** 才切。这一点比我们宽松。

`UrlOption` 的字段（第 876-923 行）：`method / charset / headers / body / origin / retry / type / webView / webJs / dnsIp / js / bodyJs / serverID / webViewDelayTime`。

**先严后松两次解析**：`GSONStrict` 失败再退 `GSON`，并打日志提示格式不规范。这和我们 `LooseJson.toStrict` 的思路一致，但上游是「严格优先 + 宽松兜底 + 告警」，我们是「自己规范化成严格 JSON」。

#### `getAbsoluteURL` 对绝对地址的行为

`NetworkUtils.getAbsoluteURL(baseUrl, relativePath)`：**当 relativePath 已是绝对地址（http/https 开头）时原样返回**，只有非绝对地址才做 URL 拼接。

这条决定了 `地址,{JSON}` 形态能否活到后面：只要前面那截是绝对地址，`,{JSON}` 尾巴就不会被拼接逻辑破坏。

### 2. `@put` / `@get` 变量的生命周期

**文件**：`app/src/main/java/io/legado/app/model/analyzeRule/RuleData.kt`（全文 30 行）

```kotlin
class RuleData : RuleDataInterface {
    override val variableMap by lazy { hashMapOf<String, String>() }

    override fun putBigVariable(key: String, value: String?) {
        if (value == null) variableMap.remove(key) else variableMap[key] = value
    }

    override fun getBigVariable(key: String): String? = null

    fun getVariable(): String? =
        if (variableMap.isEmpty()) null else GSON.toJson(variableMap)
}
```

配套接口 `RuleDataInterface.kt`（未逐行读，存在 `putVariable` / `getVariable`）。

**在 AnalyzeUrl 里的落地**（第 409-428 行）：

```kotlin
fun put(key: String, value: String): String {
    chapter?.putVariable(key, value) ?: ruleData?.putVariable(key, value)
    return value
}

fun get(key: String): String {
    when (key) {
        "bookName" -> (ruleData as? Book)?.let { return it.name }
        "title" -> chapter?.let { return it.title }
    }
    return chapter?.getVariable(key)?.takeIf { it.isNotEmpty() }
        ?: ruleData?.getVariable(key)?.takeIf { it.isNotEmpty() }
        ?: ""
}
```

**要点**：
- 变量表挂在 `ruleData`（书这一级的运行时对象）上，**不随单次解析消亡** —— 所以「搜索时 put、目录/正文时 get」合法。
- `chapter` 优先于 `ruleData`：章节级变量覆盖书级。
- `getVariable()` 把整表序列化成 JSON，用于跨进程/跨调用传递。

### 6. 加密与编码能力（AGENTS.md / CLAUDE.md 明确记载）

- **Hutool 5.8.22 固定在 classpath**，两个用途：
  1. 作为**书源 JS 的运行时加密库**（书源直接 `Packages.cn.hutool.*`）；
  2. `help/crypto/CryptoUtils.kt` 的 base64 **解码**统一走 `cn.hutool.core.codec.Base64.decode`，
     以兼容缺 `=` 填充等宽松输入（Kotlin 严格填充会导致部分书源取章名/正文回归）。
- 应用内部加密主体用 JCA（`javax.crypto` / `java.security`）+ `help/crypto` 路径。
- `help/crypto/` 目录实际文件：`AsymmetricCrypto.kt`、`CryptoUtils.kt`、`Sign.kt`、`SymmetricCryptoAndroid.kt`、`README.md`。

**对我们的意义**：书源 JS 里能调 `Packages.cn.hutool.*`，意味着大量源把加解密、Base64、散列都托管给 Hutool。我们补 `java.aesBase64DecodeToString` 是对的，但** Hutool 那一整层是更大的兼容面**（本次未展开核对）。

### 7. 其他工程约束（AGENTS.md 原文，对我们有参考价值）

- **jsoup 不得升过 1.16.2**：新版行为影响 `AnalyzeByJSoup.kt` 与 JsoupXpath（jsoup#2017）。
- 代码 namespace `io.legado.app`，但 `applicationId` 是 `io.legato.kazusa`，不要混用。

## 四类书源实测与失败模式清单

> 环境：青阅 0.8.6（`legado/app/build/libs/legado-0.8.6-all.jar`），临时实例 1243，临时库 `legado/tmp/dbg-data`。
> 样本：用户提供的 4 个源（`shareBookSource(5).json`，文本/音频/漫画/文件各一）。
> 核对时间：2026-10-25。所有结论均来自本次实跑，含原始返回。

### 摘要

**2/4 全通，1/4 差最后一步，1/4 卡在目录**。全部失败的根因都不在站点，而在我们的引擎：
详情阶段 `@put` 的变量传不到目录（漫画源正文 422）、目录为空时没有"书籍页即一章"的兜底（音频源 0 章）。
另有一个**调试信息误导**：详情 trace 在取值成功时也标记「取到空值」，本轮排查被它带偏过。

### 3. 全免漫画（优）· bookSourceType=2 · ⚠️ 差最后一步

#### 现状

| 步骤 | 结果 |
|---|---|
| 搜索 `斗破` | **5 条命中** |
| 详情 | **200**（AES 桥补上后通的） |
| 目录 | **50 章** |
| 正文 | **502 `上游返回 HTTP 422`** |

#### 根因：详情阶段 `@put` 的变量没传到目录

调试流（`GET /api/sources/{id}/debug`）里看得清清楚楚：

```
[详情] 《沉香破》｜三福动漫 | ok: true
    · name ← $.comic_name@put:{cid:$.comic_id} => 沉香破
    · tocUrl ←  =>（空）
[目录] 50 章 | ok: true
    · 第1话｜https://api-cdn.kaimanhua.com/…
[正文] 失败：第1话 | ok: false | 上游返回 HTTP 422
```

源规则：

```
ruleBookInfo.name = $.comic_name@put:{cid:$.comic_id}     ← 详情阶段 put cid
ruleToc.chapterUrl = @js: cid='@get:{cid}'; …             ← 目录阶段 get cid
```

我们的 `RuleRunner.kt:485` 只回灌**搜索阶段**的变量：

```kotlin
rememberRuleData(tocUrl, recallRuleData(bookUrl))   // 缺 root.snapshotVariables()
```

于是 `cid` 取空，拼出 `…/getchapterdata?comic_id=&chapter_id=…`，上游回 422。

**期望行为**：详情阶段 `@put` 的变量应随 `tocUrl` 一并传给目录（上游 `RuleData` 挂在书这一级运行时对象上，天然跨阶段存活）。

#### 附带发现：`bookUrl` 的 `,{JSON}` 尾巴**没有**丢

搜索返回的原始 bookUrl（完整）：

```
https://api-cdn.kaimanhua.com/comic-api/v2/comic/getcomicdata?comic_id=86351&client-type=android&productname=qmmh&client-channel=xiaomi&platformname=android&client-version=1.4.8erciyuan2020,{"method":"GET","headers":{"User-Agent":"okhttp/4.9.1","m-request-id":"<md5>"}}
```

尾巴在。`RuleRunner.absolute()` 对绝对地址原样返回，`splitUrlOptions`/`LooseJson.extractTail` 能切开。
**（本轮前的怀疑「签名头丢失导致 402」不成立。）** 直接拿这条原始字符串请求详情也是 200。

### 4. 五丁音乐（优+）· bookSourceType=1 · ❌ 卡在目录

#### 现状

| 步骤 | 结果 |
|---|---|
| 搜索 `周杰伦` | 10 条，首条 bookUrl `http://5sing.kugou.com/yc/2104925.html` |
| 详情 | 200 |
| 目录 | **0 章** |

#### 根因：目录规则匹配不到，且无兜底

源规则：`ruleToc.chapterList = .view_tit`、`chapterName = text`（在歌曲页 HTML 上找）。
我们的目录链（`ReadingRoutes.kt:90-117`）是三级兜底：
`bookUrl 试 → 空则 details → tocUrl 试 → 4 秒超时 → fallbackFromContent`，
**三级全空就返回 `[]`，没有「把书籍页本身当一章」的兜底**。

站点本身正常（`curl` 直连搜索接口 200、返回 `{"list":[…]}`，`bookList: list` 修好后能取到 10 条）。

**期望行为**：目录为空时，至少把书籍页当成单章节，让阅读器能进去（音频源常见形态：一本书 = 一首歌）。

### 5. 本轮顺带修掉的（已验证）

| 问题 | 现象 | 处置 |
|---|---|---|
| JSON 裸键列表规则 | `bookList: list` 被当 CSS，搜索 0 条 | `RuleRunner` 补 `$.` 前缀，5sing 搜索从 0 → 10 条 |
| 缺 AES 解密桥 | 加密源详情 502 `Unexpected End Of File position 36020` | `JsSandbox` 补 `java.aesBase64DecodeToString`，漫画源详情/目录通 |
| `,{JSON}` 尾巴不容忍空白 | `地址 , {"method":"POST"}` 切不开 | `LooseJson.extractTail` 容忍逗号前后空白（对齐上游 `paramPattern`） |

### 6. 排查中被误导的一处（已确认是显示 bug）

详情 trace 对**每个成功取到值**的字段都标了 `✗ 取到空值`：

```
· name ← $.comic_name@put:{cid:$.comic_id} => 沉香破 ✗ 取到空值
· author ← $.author_name => 三福动漫 ✗ 取到空值
· lastChapter ← $.lastchapter_title => 最终话 ✗ 取到空值
```

`RuleRunner.kt:476-477`：

```kotlin
failure = outcome.exceptionOrNull()?.let { … }
    ?: outcome.getOrNull()?.let { "取到空值" }.orEmpty(),
```

`outcome.getOrNull()` 拿到非空值也进第二个分支 —— **成功时也报「取到空值」**。
本轮排查一度据此以为字段全没取到。该 trace 不可信，需要修。

### 7. 已落地：详情 `@put` 变量传给目录

**改动**：`app/src/main/kotlin/io/legado/rules/RuleRunner.kt:485`

```kotlin
// 改前：只回灌搜索阶段的变量
rememberRuleData(tocUrl, recallRuleData(bookUrl))
// 改后：把详情这一步新 put 的变量一并带上
rememberRuleData(tocUrl, recallRuleData(bookUrl) + root.snapshotVariables())
```

**判据**：`app/src/test/kotlin/io/legado/RuleVariableHandoffTest.kt`（2 条）
- 用 `RuleRunner(responseFetcher)` 注入假响应，`details()` → `chapters()` 跑真链路，不碰网络
- 修复前精确复现：`目录 URL 里应带上详情阶段 put 的 cid，实际：https://c.example/ch?cid=&path=/c1`
  —— 与线上漫画源 422 的 URL 形态（`comic_id=&chapter_id=…`）一致
- 第二条守住原能力：搜索阶段 `@put` 仍能传到目录（不回归）

**仍待验证**：真实漫画源的正文链路（需要外网 + 那个微信源文件，本机已不可用）。
判据层面已证明变量传递修好，但「422 是否因此消失」要在真源上复测。
