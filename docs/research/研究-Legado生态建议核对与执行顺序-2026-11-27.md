## 3. 本仓能力逐项核对

### 3.1 并发、流式和超时：有实现，但必须区分两条入口

当前页面真实调用链：

`LibraryPage → useSearchStore/startSearch → streamSearch → WS /api/search/stream → SearchSession → searchSourceOutcome`。

- `LibraryPage.tsx:73,95-105` 使用共享搜索状态并发起搜索。
- `lib/searchStore.ts:306-316` 调用流式 API，按结果包追加内容；`:361-379` 停止时发送 cancel 并关闭连接。
- `lib/api/domains/search.ts:40-45` 实际连接 WebSocket。
- `http/SearchSession.kt` 使用固定数量 worker 按已排序索引领取书源，并逐源发结果事件，因此“几百源目前只能串行”不成立；原每源 launch 争 Semaphore 的首波竞态也已修复。
- `AppConfig.kt` 已有并发最小/最大值环境配置（默认 16/32）、单源配置 30 秒与整批配置 60 秒。后续切点让 WS/POST 共用整批配置；这是源级并发预算，不是固定线程数，也不是当前设置页已有调节控件。

**本次确认的差异：**

| 行为 | POST `/api/search` | 页面所用 WS `/api/search/stream` |
|---|---|---|
| 有界并发 | 有 | 有 |
| 逐源先出结果 | POST 聚合返回 | 有，结果事件逐包回传 |
| 单源包装 | 共用 `searchSourceOutcome` | 共用同一包装 |
| 健康/权重/耗时排序 | `SearchRoutes.kt:63` 调 `orderByHealth` | 修前直接传源清单；本轮在 `:108-112` 调相同的 `orderByHealth` 后传给 SearchSession，真实 WS 回归通过 |
| 整批截止后返回部分结果 | `collectWithDeadline(searchTotalTimeoutMs)`；仍为历史独立 scope 收集模型 | `SearchSession(totalTimeoutMs)`；取消子任务后发 `done.truncated/message`，保留已回传结果 |
| 用户主动停止 | 请求生命周期路径 | cancel 帧或 incoming 正常/异常结束均取消 streaming；前端停止、异常断连进度刷新及旧 socket 隔离有判据 |

`SearchRoutes.kt` 的 `searchSourceOutcome` 后续改为 `withTimeoutOrNull { RuleIoCancellation.run { runner.search(...) } }`：仅本层单源超时计失败，父级取消继续传播。`RuleIoCancellation` 以线程中断处理头等待，并注册/关闭正在读取的响应流；规则多跳重试前检查取消，避免脚本吞错后再次发起请求。

受控本机 HTTP 实验显示：仅线程中断能退出头等待，响应体读取仍可能阻塞；补流关闭后由同一生产 helper 的回归验证。取消后才抵达的响应流也必须立即关闭。关闭流产生的 IOException 不得掩盖父级取消，否则会被误记为书源失败。测试专用客户端显式允许回环，生产 SSRF 策略未放宽。实验确认规则调用线程退出与响应体关闭，尚未证明 PinnedProxy 上游连接及代理线程立即退出。任意忽略中断的第三方代码仍不能保证到毫秒即退出；WS 在结构化并发收尾后发 done，POST 历史收集模型则到预算返回而不等待全部收尾。

本轮回归 `SearchStreamHealthOrderTest` 用五组假源（未体检、失败、健康低权重、健康同权重稍慢、健康高权重低延迟），每组填满配置的并发名额，用 latch 记录真正启动的第一波。修前优先启动未体检组而失败；修后首波全为优选组，最终五组全部返回，证明排序没有过滤源。测试不联网，也不以结果到达顺序替代调度证据。

原路线图的“新增并发流式搜索”已收敛为：**接通排序、整批截止和取消资源退出**。默认超时和并发数保持原值；WS done 增加可选字段以兼容旧客户端。多跳规则和需登录的源仍要用样本测成功率与资源占用；单次超时不等于跨请求熔断器。

### 3.5 手机备份互通与 WebDAV：格式、传输、同步分开验收

`backup/BackupImporter.kt:43-48,99-140` 已认当前/旧版 zip 及裸 JSON；`BackupExporter.kt:42-57` 有 bookSource、replaceRule、bookGroup、rssSources、bookshelf 条目，以及当前工作树新增的 sourceSub。`BackupExportRoundTripTest.kt` 纳入本轮后端全量执行范围；sourceSub 的导出增量是开始时已有改动，不能算本轮新成果。本仓自往返也不代表手机兼容性已通过。

备份入口 `http/BackupRoutes.kt:37-40` 明确是浏览器直传包恢复。当前核查的备份、设置与 API 清单没有显示可用的 WebDAV 客户端配置/同步闭环；旧注释提到 WebDAV 不是当前双向同步已经可用的证据，也不据此断言全仓绝无任何相关字符串。

建议分为三张验收单：

1. **格式互通**：手机样本导入 → 本仓导出 → 手机或独立兼容实现恢复，逐域逐字段比对。把本仓自往返与真正手机往返分开；书签/笔记、凭据和不消费条目等边界要单列。
2. **WebDAV 备份传输**：列目录、上传/下载快照、凭据保存、失败重试、恢复预览；先提供手动快照流程。
3. **双向状态同步**：定义同书身份、章节身份、冲突、副本、删除墓碑与撤销；支持两端离线编辑后再合流。不能把“最后修改时间大”或“章节索引大”直接当成正确合并。

只有第一张完成、且有真实跨设备使用需求，才值得安排第三张；无需为了 Web 架构先建立多人账户体系。

### 6.1 书架与进度冲突策略、数据库预测及提交前检查

新界面默认保留本机书架信息，只采用有效正时间且严格较新的进度；同时间或缺时间保留本机。用户可分别选择采用备份信息、不恢复进度或强制采用备份进度（允许回退）。强制采用且缺时间时使用导入时间；不会把进度时间冒充元数据修改时间。明确携带第 0 章可以恢复，没有进度字段不生成进度。所有策略保留删除墓碑与已有书本机分组，同键重复书取包内最后一条。

`libraryDiff` 只预测书架与进度的处理，更新数表示策略选中已有记录，不逐字段判断内容是否变化；模块括号内仍是包内数量。预览借读连接建立快照，不调用写步骤；`previewToken` 绑定文件、策略与相关书架/进度/墓碑完整行，确认时在同一事务、任何域写入前重算。相关变化返回 `409 backup_preview_changed`，不写入任何模块；未选书架不因书架变化阻断其他模块，但仍校验文件与策略。凭证用于检查变化，不是访问授权。

前端改变密码或策略须重新预览；确认失败也要求刷新，避免不确定的网络结果被直接重放。旧客户端同时省略策略与凭证时维持旧导入行为，其他模块冲突规则不变。实现规范见 `product/docs/import-conflict-policy.md`，最终测试与边界见 facts.md §20。

### 6.4 冲突书源的可恢复留档

本切点保留既有运行身份，只在备份包含同标识冲突且选中书源时强制保存恢复证据。留档保留全部原始书源对象、顺序、书架对象与原始引用，并用索引标明每个冲突组的胜出版本；文件按内容 SHA-256 定址，可以从备份页现有下载入口取回，不自动套用。预览不产生文件，确认留档失败时所有数据库域回滚；相同备份重复导入复用文件，不覆盖其他备份的留档。

直接把 `#` 注解升级为新运行 ID，会同时影响规则执行产生的 `sourceId`、书架、进度、删除记录、登录态与缓存。现有归一化载荷已经缺少原始注解，不能凭空恢复关联，也不能把旧凭据复制给所有变体。因此本轮先保护原始证据，之后再做带用户确认的版本激活和书架重关联。恢复证据包含原始字段，可能含请求头/凭据，须按原备份私密保管；当前六域导出仍不包含它，不能代替原始 ZIP。最终实测与跨存储边界见 facts.md §23。
