## 3. `useReaderNotes` 为什么不能干净切出（卡点）

研究文档 4.2 把 `useReaderNotes` 列在 `useReaderChrome` 之后。动手时发现三处耦合，任何一处硬抽都会把
导航或划线渲染的逻辑迁到不自然的边界：

### 3.1 跳转原语是「笔记」与「搜索命中」共用的
- `jumpToNotePosition`（`ReaderScreen.tsx:1043`）是分页/滚动两种模式下的落点算法，被 `jumpToNote`(L849) 与 `jumpToSearchHit`(L868) **同时调用**。
- `pendingNoteJumpRef`（`ReaderScreen.tsx:200`）跨章跳转时挂目标位置，被 `jumpToNote`(L845)、`jumpToSearchHit`(L864)、章节恢复(L1052)、首屏恢复(L1652) 共四处写入。
- 消费点在 L1074–1079 的 effect（正文挂进 DOM 后才滚）。这条 effect 属于**导航**，不该跟着 note 状态搬走。

→ 抽 `useReaderNotes` 必须把这俩导航原语当依赖传入，跳转函数（`jumpToNote`/`jumpToSearchHit`）留在 `ReaderScreen`。可抽，但不是「纯笔记 hook」。

### 3.2 划线高亮在正文渲染深层调用
- `renderNoteHighlights`（`ReaderScreen.tsx:875`）按 `excerpt` 在段落里定位高亮，被正文渲染路径调用（经 `renderContentBlock` 之类）。
- 它闭包引用 `notes`（`ReaderScreen.tsx:877`）和 `openNote`(L823)。若把 `notes` 搬进 hook，就得把 `renderNoteHighlights` 也穿进 `ReaderBody` 的渲染管线——一层层透传，回归面大。

→ 这是拆 `useReaderNotes` 风险最高的点：动它等于动段落渲染，那 9 个阅读器判据（`Note`/`ReaderMenu`/`RefreshChapters`/`ReaderChrome` 等）最容易哑火。

### 3.3 `readLogicalPosition` 被「笔记」与「进度保存」共享
- `toggleBookmark`（`ReaderScreen.tsx:769`）用 `readLogicalPosition(chapter)`(L771) 取当前读到的位置。
- 同一函数被 `persist`（进度落库，L1091）使用。把它塞进 hook 只是多一层依赖，不致命，但说明「笔记」与「进度」共用同一套逻辑位置算法。

## 4. 推荐的收口顺序（仍属 4.2，每步单提交 + 补判据）

1. **先抽导航原语**：把 `jumpToNotePosition` + `pendingNoteJumpRef` + L1074–1079 的 effect 收进 `useReaderPositionJump`（或 `useReaderNav`），**搜索命中跳转也改用它**。这一步让「笔记」与「搜索」共用同一导航 hook，互不污染，且不动渲染。
2. **再抽 `useReaderNotes`**：此时 hook 只需 `currentBook`/`chapter`/`content`/`paragraphStarts`/`positionChecksum`/`readLogicalPosition` 等纯状态依赖，`renderNoteHighlights` 暂时**留在 `ReaderScreen`**（作为接收 `notes`+`onOpenNote` 的纯函数视图），等第 3 步。
3. **最后把 `renderNoteHighlights` 提成 `NoteHighlights` 展示组件**（收 `notes` + `onOpenNote`），从 `ReaderBody` 渲染路径接出，把 `notes` 状态彻底赶出 `ReaderScreen`。

第 1 步是解耦关键，且只动导航、不碰渲染，风险最低，应优先做。
