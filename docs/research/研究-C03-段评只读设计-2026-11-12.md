## 1. 背景与现状

- 服务端目前对 `ruleReview` **零执行**：`grep ruleReview app/src/main` 仅 `SourceCodec` 告警一处。
- 前端书源编辑器 `bookSourceFields.ts` 的「段评」分栏**已完整保留 gedoor 字段**（改存不丢配置），
  共 21 项，分三层。compatibility.md §4 据此记「段评规则不执行」。
- C-03 目标（ROADMAP §4.1）：**至少只读展示**。不做的：发帖/点赞/点踩/删除等写操作。

## 2. gedoor 三层读模型（我们已存储的字段）

| 层 | 字段 | 含义 |
|----|------|------|
| 统计层 | `reviewSummaryUrl` / `summaryListRule` / `summaryParagraphIndexRule`(-1=章评,1+=段落) / `summaryCountRule` / `summaryParagraphDataRule` | 每章/每段「有多少条段评」的徽章数据 |
| 详情层 | `reviewDetailUrl` / `reviewDetailNextPageUrl` / `detailListRule` / `detailIdRule` / `detailAvatarRule` / `detailNameRule` / `detailBadgeRule` / `detailContentRule` | 某段落下的段评列表（真正的评论内容） |
| 回复层 | `reviewQuoteUrl` / `replyListRule` / `replyIdRule` / `replyAvatarRule` / `replyNameRule` / `replyBadgeRule` / `replyContentRule` | 段评下的子评论 |

`detailContentRule` / `replyContentRule` 是**内容协议**（编辑器 hint 明示键）：
`text / replyToName / img / audio / time / likeCount / replyCount`。

## 3. 第一刀范围（垂直切片，单独提交）

**只做详情层只读列表**——这是用户真正想看的「段评内容」，且可独立测试。

- IN：执行 `reviewDetailUrl` → `detailListRule` 取节点 → 逐项 `detailIdRule/detailAvatarRule/detailNameRule/detailBadgeRule/detailContentRule` → 返回 `List<ChapterReview>`；阅读器只读浮层展示。
- OUT（后续切片，文档明示）：统计层段落徽章、回复层子评论、`reviewDetailNextPageUrl` 翻页（第一刀 page 参数预留但只取首页）、一切写操作。

### 3.1 内容协议解释（判据钉死，实现时以 gedoor 源码复核）

`detailContentRule` 求值结果按 **JSON 对象**解析出 `text/img/audio/time/likeCount/replyCount/replyToName`；
**非 JSON 时整段回落为 `text`**（兼容只写纯文本规则的源）。键与编辑器 hint 一一对应。
→ 这是合理且可测的解释；若复核 gedoor 发现差异，改判据不改架构。

## 4. 后端落点

- 模型：`model/Models.kt` 增 `ChapterReview(id, avatar, name, badge, content: ReviewContent)`、
  `ReviewContent(text, img, audio, time, likeCount, replyCount, replyToName)`（可空字段从缺）。
- 引擎：`rules/RuleRunner.kt` 增 `fun reviews(sourceJson, urlTemplate, page=1): List<ChapterReview>`，
  **逐字镜像 `rssArticles`**（:343）的 URL 解析链：`isJsRule/evalRuleJs → applyUrlScripts → splitUrlOptions →
  mergeOptions(parseSourceHeaders) → renderUrl().absolute() → fetchUrl`；列表 `nodeSelection.nodes`/`jsListNodes`；
  逐项 `item.value(rule, jsSandbox, body, pageUrl)`。content 空的条目丢掉；avatar 按 pageUrl 归一。
  缺 `reviewDetailUrl`/`detailListRule` → 抛 `RuleExecutionException`（明确报因，不静默）。
- 端点：`http/ReadingRoutes.kt` 增 `post("/books/reviews")`（镜像 RssRoutes `/rss/articles` :76）：
  `requireSameOriginWrite` → `receive<ReviewsRequest{bookSourceUrl,url,page}>` → `database.getBookSource` →
  `withContext(IO){ runner.reviews(...) }` → 失败 `BadGateway ApiError("reviews_failed", ...)`。
- **契约三处同步（161→162）**：① 代码路由；② `resources/agent-api.json` endpoints 增条目；
  ③ `npm --prefix product run docs:api` 重生 API-REFERENCE。`web/test/ApiCatalog.test.ts` 双向钉住，漏一处即红。
- `SourceCodec.scanIncompatibilities`（:195）告警改写：从「服务端不执行段评」→
  「段评详情列表已只读支持；统计徽章/子评论/发帖未执行」。`SourceValidateWarningsTest` 对应用例翻转。

## 5. 前端落点

- 阅读器只读浮层：仅当书源 `ruleReview.enabled && reviewDetailUrl` 非空时出现入口；
  拉 `/api/books/reviews` 展示列表（头像/昵称/内容/时间/点赞数），**无任何写按钮**。
- 复用现有 overlay 体系（`ReaderOverlays`）与令牌（`--accent-solid`/`--on-accent`），不新增顶级导航。
- 前端判据：断言「无 reviewDetailUrl 的源不出现段评入口」「有则渲染只读列表、无发帖控件」。

**下一刀（前端只读浮层）的关键设计缺口——必须先定，再动手**：
 gedoor 模型里详情地址 `reviewDetailUrl` 通常由**统计层条目**（某段落的 summary id）拼出；
本刀排除了统计层，所以阅读器侧「详情地址从哪来」要先定方案：
- 方案 A（推荐）：服务端加 `reviewsForChapter(sourceJson, chapterUrl, page)`——读 `ruleReview.reviewDetailUrl`，
  按章节地址解析（核实 `renderUrl` 是否支持 `{{url}}`/章节占位，不支持则补一个窄解析器），再走现有 `reviews` 逻辑。
  端点改收 `chapterUrl`（阅读器本就有 sourceId+chapterUrl），前端零规则求值。需补引擎判据 + 一轮 gradle。
- 方案 B：前端懒取书源规则（`api.sources.get`）+ 客户端解析 `reviewDetailUrl`——把规则求值搬前端，重且易漂，不取。
- 章节级段评（`reviewDetailUrl` 直接用章节地址）可先走方案 A 落地；段落级徽章依赖统计层，留后续。

浮层落点：`ReaderOverlays` 增 `dialogs.reviews` + `actions.onCloseReviews`，新建自包含 `ChapterReviewDialog`
（mount 拉 `book.reviews`，只读渲染头像/昵称/内容/时间/点赞，**无任何写按钮**），入口仅在书源配了
`ruleReview.enabled && reviewDetailUrl` 时出现。前端判据：无配置不出入口、有则只读列表无发帖控件。
完成后把 §4/§4.1/告警的「接入中」翻回「阅读器可看」，再随 0.2.40 发版。
