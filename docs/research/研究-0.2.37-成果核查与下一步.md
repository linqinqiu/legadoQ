## 4. 真实缺口（按 ROI 排序）

### 4.1 前端可观测性只做了一半（半天～1 天，风险低）

`performance.ts` 有完整的采集器与测试，但没有接进真实链路：

- API 请求：`lib/api/client.ts:13` 仍用原生 `fetch`，`fetchWithMetrics` 无人调用；
- IndexedDB：`dbTransaction` 无人调用；
- 分页测量：`ReaderScreen.tsx:1894` 调 `calculatePaginationLayout` 前后没有任何计时，
  `STATUS.md` 的「前端分页测量仍无指标」指的就是这里；
- 指标只进内存，`report()` 没有出口（没有 `/api/metrics`，也不落盘）。

**最小改法**：`client.ts` 换成 `fetchWithMetrics`；在分页布局前后各记一次
`performance.now()` 写进同一个 collector；给 `report()` 加一个显式的导出入口
（`window.__legadoPerf` 或开发面板按钮），先不碰后端。

**验收**：`PerformanceMonitor.test.ts` 增 2 条（client 走监控、分页有指标）；
`npm --prefix product/web test` 全绿。

### 4.2 ReaderScreen 拆分（1–2 天，风险中）

3,200 行不是「还没拆」，而是**剩下的部分全是状态**。已经拆出去的是纯函数：
`interaction/`、`content/readerFlow`、`pageTurn`、`logicalPosition`、`typeset/`。
继续拆只有一条路：把状态搬进自定义 hook。

建议顺序（每步单独提交，先补判据）：

1. `useReaderChapterLoad`：`content` / `loading` / `loadedChapterUrl` / 预取 ref / 缓存同步
   （`ReaderScreen.tsx` 约 148–470 行）；
2. `useReaderPagination`：`pageIndex` / `pageCount` / `columnWidth` / `stride` / 双栏与测量
   （约 218–243、1894 附近）；
3. `useReaderNotes`：选区、笔记草稿、书签（`notes/` 已有纯函数）；
4. `useReaderChrome`：工具栏、抽屉、各类弹窗的开关。

**验收**：现有 9 个阅读器测试 + `tools/verify/reader-interaction-check.mjs` 必须保持绿；
每步后 `ReaderScreen.tsx` 行数单调下降。

### 4.3 RuleRunner 拆薄（2–3 天，风险中高）

`rules/RuleRunner.kt` **2,549 行**，职责可按行段切开：

| 行段 | 职责 | 行数 |

最安全的第一刀是 **2095–2436 的取值与列表**：几乎不碰网络与 JS 沙箱，且
`GoldenRuleTest` 的 6 组 fixture 能逐字节比对。第二刀是 **1426–2094 的 HTTP**，
但它和 `JsSandbox(this)` 互相引用（`ajax` 回调），要先抽一个窄接口。登录 UI 最后动。

**注意**：`RuleProcessor` 扩展点已经真的接上了（`RuleProcessor.kt:13-23`），

必须靠 `GoldenRuleTest` + 真库抽样证明等价，不建议和「拆文件」混在一个提交里。
