本文是 `研究-阅读器内部边界与结构门禁盲区-2026-11-19.md` 的续篇。那篇确认了门禁盲区（用户已确认的前提，本文不再论证）；本文回答两个更硬的问题：**① 哪些单一功能改动仍牵动多模块（影响面量化）；② 每处纠缠是必要还是不必要（逐条判定）**。

## 0. 先看结论

1. **五个单一功能，没有一个能只改一个文件。** 最少 6 个（进度、正文），最多 10 个（TTS）。五个功能的总装配点都是同一个 `ReaderScreen.tsx` —— 它是"改一个功能牵动多模块"的结构性原因，而不是某个 hook 写坏了。
2. **真正的"不必要依赖"只有 3 处**：`offlineStatsModal`（全仓零置 true 点的死状态）、`setNotes` 被父组件绕过直写（3 处）、`onLoadedRef`（规避依赖数组的 useEvent 手法，可用稳定回调改造）。其余纠缠判定为**必要**——它们跨渲染周期、跨组件、跨模块，拆成局部状态会丢行为。
3. **所以缺口不是"有依赖"，而是"必要的依赖挤在一个上帝组件里编排"。** 门禁只按目录挡 import，看不见的是：这些必要共享的**装配点**全在 `ReaderScreen`，导致任何一处共享的语义变化都要回到这一个 2389 行文件。这是"测试通过 ≠ 可独立修改"的真正机制——判据锁的是纯函数，改的是共享装配。
4. **最硬的四条交叉点**：`setPageIndex`（五方共写）、`readLogicalPosition`（进度↔笔记↔分页共享语义位置）、`content + positionChecksum`（正文是笔记重锚与进度校验的共同输入）、`persist/changeChapterRef`（进度↔TTS 双向环）。

## 2. 逐条必要性判定

判定三档：**必要**（拆成局部状态/参数传递会丢行为）、**不必要**（零消费者或可简单移除）、**存疑**（可改造但收益/风险需实测）。写方/读方数为全仓 grep 结果。

| 对象 | 判定 | 写/读 | 理由与证据 |
|---|---|---|---|
| `currentRef`（:188） | **必要** | 4/5 | 滚动帧内对 `position` 原地改（:1695/1738/1767），走 state 会每帧重渲染；跨渲染周期记忆"当前章+最新位置" |
| `logicalMetaRef`（:567） | **必要** | 1/9 | 跨 3 模块共享"段起点+checksum"快照（positionJump:54-64、pagination:141/145），真实共享 |
| `pageIndex`（:169） | **必要** | 10/13+ | 跨组件+跨 hook 渲染态，五方写入（详见 §3） |
| `notes` 状态本身 | **必要** | 9/6+ | 跨组件共享（hook、书签、划线、目录面板） |
| 父绕过 `setNotes`（:650/668/2170） | **不必要** | 3 处绕写 | hook 注释（useReaderNotes.ts:17-21）刻意暴露 `setNotes`；把 bookmark/划线回调移回 hook 即可消除这条双向边 |
| `onLoadedRef`（hook:51-52/97） | **存疑** | 1/1 | useEvent 手法绕依赖数组（否则 :88 effect 反复请求）；若父端用稳定 `useCallback` 可去 ref，但要实测 effect 不重跑 |
| `changeChapterRef`（:833/1101） | **必要** | 1/3 | `changeChapter` 调 `stopTts`、TTS 续播又调 `changeChapter`（:1069），ref 打破真环，源码注释明写 |
| 意图位 ref ×7（:104/106/130/194-199） | **必要** | 各 1-3/1-3 | 跨渲染周期的一次性意图，改 state 会引入多次渲染、行为等价性有风险 |
| `offlineStatsModal`（:162） | **不必要** | **0 置 true** | 全仓仅 :2347 读、:2366 置 false，无任何 `setOfflineStatsModal(true)`——死状态，应删 |
| 其余弹层 boolean（:137-151/161/163/626/628） | **存疑** | 各 1-2 | 无"同回调开两个"场景，满足合并前提；但 `notesPanel + activeDrawer='toc'`（:2257）是刻意叠加态，合并成单一 `activeOverlay` 会破坏该组合，收益低改动面大 |

**判定的分寸**：9 类对象里 5 类"必要"、3 类"存疑"、2 类"不必要"（其中 notes 状态必要但 3 处绕写不必要）。**大部分纠缠是真实的跨模块共享，不是坏味道。** 这印证了 §0.3——问题在装配点集中，不在依赖本身。

## 3. 四条最硬交叉点（改一处必连带另一处）

1. **`setPageIndex` 五方共写**：翻页 hook（`useReaderPageTurn.ts:49`）、分页 hook（`usePaginationMeasurement.ts:135/155/171/174`）、TTS 跟读（ReaderScreen:1870）、笔记跳转（`useReaderPositionJump.ts:74`）、ReaderScreen 自身翻页与滑条（:1580/1601/1649）。改页码语义（如从 0-based 改 1-based）五处都要同步。

## 5. 可动与不可动（结论）

- **可动、低风险**：删 `offlineStatsModal`（2 处 + 1 prop）；把父端 3 处 `setNotes` 绕写收回 `useReaderNotes` 的导出回调。这两处是"不必要依赖"，消除不损行为。
- **可动、需判据**：`onLoadedRef` 改稳定回调、10 个 boolean 合枚举（须保留 `notesPanel+toc` 组合态与 fullscreen 镜像 DOM）——这两处"存疑"，改动前要补交互判据。
- **不该动**：§2 判定"必要"的 5 类（currentRef/logicalMetaRef/pageIndex/changeChapterRef/意图位 ref）。把它们拆开不是解耦，是丢行为。
- **真正的杠杆点**：不是上面任何一处删除，而是给 §3 的四条交叉点建立"单一出口"（统一 `setPageIndex` 的写入口、统一语义位置原语、进度/TTS 环改事件总线或 Context）。这属于拆文件之后的阶段，本轮不实施。

本轮结论均来自静态取证与 grep 全仓调用点，未做运行时验证、未跑交互测试。§5 的"可动"清单是判定，不是获准实施。

## 6. 静态探针基线与"纠缠预算门禁"可行性裁决

为验证"能否给门禁加第二类判据（纠缠预算）"，写了一版**一次性静态探针**（`docs/.scratch/reader-entanglement-probe.mjs`，gitignored 草稿，未入库、未接 CI）。运行 `node docs/.scratch/reader-entanglement-probe.mjs`（cwd=`E:/legado`）。实测基线：

- **状态密度**：reader 全目录 75 个 ts/tsx，合计 108 useState / 63 useRef / 66 effect；`ReaderScreen.tsx` 独占 **32S/31R/31E**（第二高的 `RefreshChaptersModal.tsx` 仅 9S）。装配点集中不是印象，是可数量化的 3 倍断层。
- **reader 内部跨子目录 import = 100 条**，门禁一条不计（已在盲区篇确认）。
- **跨文件共享 setter**：`setPageIndex` 4 文件、`setTtsActive`/`setShowTtsSettings`/`setOfflineTtsConfirmOpen` 各 3 文件——与 §3 交叉点一致。

**裁决：纯文本正则做不出可靠的纠缠预算门禁，不要接 CI。** 探针自身暴露两个反例，实测确认：

1. **同名不同源误报**：`setLoading` 被算成 3 文件共享，实为 `useReaderChapterContent.ts:45`（正文加载）与 `BookSearchDialog`、`BackgroundLibrary` 三个无关状态恰好同名。按符号名 grep 的判据必然误报，要做对需真正的作用域/类型解析（TS compiler API），成本远超收益。
2. **无置 true 死状态漏报**：`offlineStatsModal`（:162）全仓只有定义、`:2366` 置 false、`:2347` 读，无任何 `setOfflineStatsModal(true)`；但探针按"setter 出现次数"判定，因 false 那次调用而漏掉——正则抓不到，定向 grep 才抓到。

因此 §0 缺口结论不变，但**手段收窄**：能可靠落地的是"定向 grep 断言"（针对具体符号，如"setPageIndex 写入点白名单"、"禁止新增无置 true 的 boolean"），不是泛化的"状态密度/扇出预算"。泛化预算会因误报变噪音门禁，重蹈本项目"基线只许单调缩小、门禁误报害死人"的覆辙。

**第三处（reportProgress 显示通道）：撤销"合一"待办，判定为必要互补通道（2026-11-19 终判）**。

前几轮把"reportProgress 与落库侧合一"列为待办，是过度判定，现撤销。读透两条通道后：

| 维度 | 落库通道 `useReaderProgress→progressSaver` | 显示通道 `reportProgress` |
|---|---|---|
| 消费者 | `api.saveProgress`（服务端） | `VirtualChapterList` 目录行细进度条（:15 唯一订阅者） |
| 数据源转换 | 存 `scrollPosition` 像素 + `position` 逻辑偏移（恢复用） | 存 `fraction` 0~1 章内比例（显示用） |
| 频率 | 1200ms 防抖 | 随滚动**逐帧**调用、0.002 节流 |
| 不合一的原因 | — | 合一会让目录进度条跟随 1200ms（卡顿）或让落库跟随逐帧（请求爆炸） |

两者读同一真源 `current.position`，但转成**两种用途的表示**。与一般"重复"不同：不是同一份数据的两份拷贝，是同源双投影。`content/readerProgress.ts:1-7` 注释明说单开 store 是"只让订阅者重渲染、不拖累 2800+ 行的 ReaderScreen 整屏重组"。

- **发现的分页精度差（非 bug）**：滚动/漫画模式的 `reportProgress.fraction` 直接取 `current.position`（=精确 `pageProgress`），唯独分页模式 `ReaderScreen.tsx:1753` 用朴素 `pageIndex/(pageCount-1)`。单节时与 `pageProgress` 等价，仅多节分页才有微差——是显示精度取舍，不是缺陷。
- **为何不改**：该 store 的 `reportProgress/getProgress` **无任何行为单测**，只有 source-text 断言钉着（印证本文核心痛点"测试通过 ≠ 可独立修改"）。无行为判据守护时改这条逐帧通道的行为只会埋回归。正确顺序是先补"分页模式进度条显示精确比例"的端到端判据，再决定是否收敛 `:1753`——超出"清理不必要依赖"范围，单列待规划。

**研究闭环**：用户最初问的"哪些单一功能改动仍牵动多模块 / 哪些是不必要的双向依赖与状态共享"到此完整回答——

- 绝大部分纠缠（currentRef/logicalMetaRef/pageIndex/changeChapterRef/意图位 ref）判定为**必要**，拆开会丢行为；根因是必要依赖全压在 `ReaderScreen` 一个装配点，而非依赖本身多余。
- 真能落地的门禁只有"针对具体符号的定向断言"，泛化预算门禁已被探针证明会误报/漏报，不接 CI。
