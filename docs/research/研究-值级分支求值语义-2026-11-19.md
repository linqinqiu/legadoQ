# 值级 `||` 求值语义核对

日期：2026-11-19；分支 `refactor/rebuild`；基线 HEAD `4247199`（研究开始时的 `git rev-parse HEAD`）。
承接 `研究-Legado核心机制与本仓边界-2026-11-19.md` §4 的「建议下一切点：只研究列表/值级 `||` 的求值差异与副作用」。

## 0. 结论

1. **两边实现确实不同**：上游值级 `||` 是短路（命中第一个非空分支就 `break`），本仓是「先算全部分支，再取第一个非空」。
2. **但对真实规则，可观察结果等价**，原因是三个前置步骤把差异抹平了：
   - `{{…}}` 在上游也是**切分分支之前**整条展开，本仓虽按分支展开，但两边都是全量求值；
   - `@put` 两边都在切分之前从整条规则里剥离并执行，与 `||` 是否命中无关；
   - 内建取值路径（JSONPath / CSS / XPath / 正则）两边都把坏规则吞成空值，不会因为多算一个分支而抛错。
3. **因此不建议为此改引擎**。真实差异只剩两处：非首支的额外 CPU，以及自定义 `RuleDispatcher` 处理器会被多调用；两者都不改变内建链路的结果。
4. 上轮建议里「先设计同输入、带计数或变量写入的离线对照」这一步，本轮用**真实语料计数**替代了造例：2,558 条值级 `||` 规则里，非首支带 JS 的 0 条、带 `{{}}` 的 3 条，且这 3 条在上游同样是切分前展开。

## 1. 两边的实现

### 1.1 上游：`||` 短路

- HTML/CSS 值级：`AnalyzeByJSoup.getStringList` 逐分支求值，`results.add(temp)` 后 `if (elementsType == "||") break`。
  `E:/_legado-attic-2026-11-18/legado-out/upstream/.../analyzeRule/AnalyzeByJSoup.kt:88`、`:106`。
- JSONPath：`AnalyzeByJSonPath.getString` 与 `getStringList` 同样在非空时 `break`。
  同目录 `AnalyzeByJSonPath.kt:35`、`:62`、`:101`。
- XPath：`AnalyzeByXPath.getStringList` / `getElements` 同样 `break`。
  同目录 `AnalyzeByXPath.kt:58`、`:68`、`:109`。
- 列表级 `getElements` 也是短路：`AnalyzeByJSoup.kt:139`、`:146`、`:174`。

### 1.2 本仓：值级全算，列表级短路

- 值级：`branches.mapNotNull { branch -> value(branch, …) }` 先把**所有**分支求完，再按分隔符取结果；`||` 只是最后 `evaluated.firstOrNull()`。
  `product/app/src/main/kotlin/io/legado/rules/RuleValue.kt:134`、`:138`、`:146`。
- 列表级：`branches.firstNotNullOfOrNull { branch -> nodes(body, branch).ifEmpty { null } }`，与上游一致是短路。
  `product/app/src/main/kotlin/io/legado/rules/RuleNodeSelection.kt:71`、`:79`。
- `{{}}` 内部的 `||` 另走一条短路实现：`splitLegadoAlternatives(inner).firstNotNullOfOrNull { … }`。
  `RuleValue.kt:231`。

所以上轮文档说的「值级先算全部分支、列表级才短路」属实。

## 2. 为什么真实结果仍然等价

### 2.1 `{{…}}` 在上游也是切分前展开

上游 `SourceRule` 构造时用 `evalPattern` 把整条规则里的 `{{…}}` 全部登记成 `ruleParam`，`makeUpRule` 在进入 `AnalyzeByJSoup` 之前一次性替换（`AnalyzeRule.kt:720` 起；调用点在取值主链的 `sourceRule.makeUpRule(result)`）。
也就是说，`a||{{java.ajax(…)}}` 这种写法在上游**同样会执行** `{{}}` 里的脚本，不会因为 `a` 命中而跳过。本仓按分支展开只是执行顺序不同，副作用次数相同。

### 2.2 `@put` 两边都在切分前剥离

- 上游：`splitPutRule`（`AnalyzeRule.kt:464`）在 `SourceRule` 初始化时把 `@put:{…}` 从规则串里摘掉并求值。
- 本仓：`valueBuiltin` 开头先 `storePutVariables(trimmedRule, …)`，之后才走到 `splitLegadoBranches`（`RuleValue.kt` 的 `storePutVariables` 调用在分支切分之前）。

因此「后面的分支里写了 `@put`，短路就不会执行」这个担心不成立：两边都会执行。

### 2.3 内建取值路径的异常都不外抛

- 本仓：JSONPath 走 `readJson` 的 `runCatching`（`RuleValue.kt:618`）；CSS 每段 `selectLegadoSegment` 包 `runCatching`（`RuleValue.kt:448`）；XPath 的 `xpathTexts` 整体 `runCatching`（`RuleValue.kt:792`）；`##` 正则编译失败返回原值（`RuleValue.kt:584`）。
- 上游：JSONPath 读失败 `catch (e: Exception) { e.printOnDebug() }`；CSS 选择失败抛异常，但上游根本不走到后面的分支，所以不会被坏分支连坐；本仓把坏选择器吞掉，也不会连坐。

结论：本仓「多算」的分支即使写坏，也只会得到空值，不会让已命中的首支失败。

### 2.4 一处有意的口径差：空白分支

本仓过滤的是 `isNotBlank()`（空白也算空），上游是 `!temp.isNullOrEmpty()`（空格算有值）。即上游 `" "` 会短路并返回空格，本仓会继续尝试下一分支。这是本仓更宽松，不是回归；真实库里未见依赖「空白即命中」的写法（本轮普查未单独统计，属未验证项）。

## 4. 还剩什么差异

| 差异 | 是否影响结果 | 说明 |
|---|---|---|
| 非首支的额外求值 | 否 | 内建路径只读、无副作用；失败被吞成空值 |
| CPU | 可能 | 每条目多算 `分支数−1` 次选择器/路径；`nextTocUrl` 频率最高 |
| 自定义 `RuleDispatcher` | 可能 | 处理器在 `value()` 入口被 `claim`，未命中的分支也会被调用；这是扩展点语义，不是上游兼容面 |
| 日志 | 否 | 取值失败不写运行日志，不会出现「未执行分支报错」的噪声 |

## 5. 建议

1. **不为此改引擎**，也不加「值级 `||` 短路」的补丁：它只省 CPU，却会改变扩展点被调用的次数，收益与风险不成比例。
2. 若将来确实要做性能优化，先立判据再改：
   - 用自定义 `RuleProcessor` 计数，断言「首支命中时非首支处理器不再被调用」；
   - 用 `@put:{k:…}` 放在非首支，断言变量在短路后不出现（这条只能证明顺序，不能证明上游一致，因为上游 `@put` 是切分前剥离的）。
3. 真正需要盯的是 `nextTocUrl`（231 条）这类高频字段的总耗时，而不是 `||` 语义本身；要量化应先有 `pagination_measure` / 规则耗时埋点的实测，而不是先改代码。
