## 4. 本轮新增发现：订阅同步未通知共享书源缓存

### 4.1 修复前的完整证据链

1. `features/rss/SourceSubscriptionPanel.tsx:50-70`：单条同步与全部同步在 API 返回成功后都调用 `onSourcesChange()`，然后重新读取订阅列表。
2. `features/rss/RssPage.tsx:27`：实际传入 `onSourcesChange={() => undefined}`，丢弃通知。
3. `app/pages.tsx:36` 已有 `refreshSources`，但 `:52-53` 渲染订阅页时只传 `onOpenBackup`。
4. `main.tsx:690-692` 的 `refreshSources` 已实现 `sourceCatalog.invalidate()`，可以直接复用。
5. `lib/sourceCatalog.ts:75-78`：`load()` 在 `ready` 状态直接返回快照，没有 TTL 或自动重取。
6. `features/source-editor/SourcesPage.tsx:181-183`：挂载只调用 `load()`；切页不能保证重取。
7. `main.tsx:167-172` 持有共享快照，`app/pages.tsx:74-76` 将该清单传给搜索页，所以搜索范围清单也可能陈旧。

后端对照：`http/SubscriptionsRoutes.kt:33-64` 将单条/全部同步交给订阅服务；`subscription/SubscriptionService.kt:56-76` 的同步路径调用 `database.importSources()`。订阅 API 前端封装 `lib/api/domains/sources.ts:296-307` 是直接请求，没有在底层另行通知共享缓存。

这不是订阅完全没同步：服务端可能已经保存成功，界面却仍展示旧的管理清单或搜索范围。不能进一步断言默认全源搜索的后端执行也遗漏新源，那需要单独跟踪搜索端的范围语义。

### 4.2 修复前的触发条件与反证

触发条件：同一前端会话已把清单加载为 `ready`；订阅同步确实新增或修改书源；没有其他并发刷新、手动刷新或整页重载补救。

预计浏览器路径：

1. 打开书源页，等待首次 `/api/sources` 成功。
2. 去订阅页，对包含新源的订阅执行“立即同步”。
3. 观察同步成功后的请求：当前组件只重读 `/api/subscriptions`，没有触发共享 `/api/sources` 刷新。
4. 返回书源页，或去书库查看搜索范围；可能仍看到旧清单。
5. 在书源页手动刷新或重载整页后，新清单出现。

上述浏览器步骤是由代码推导的验收脚本，本轮未实际执行。之后应使用 mock API 与隔离浏览器完成验收，避免修改真实书源。

反证：发现页 `ExplorePage.tsx:58-66` 在挂载时独立请求 `api.exploreSources()`，所以不能把同一个缓存问题扩张为“六页都不更新”。

操作边界也不同：面板 `:38-48` 的新增地址只保存订阅、等待同步；`:74-78` 启停的是订阅任务；`:80-87` 删除地址明确保留已导入书源。不能要求这些动作无条件等同于一次书源导入。

### 4.3 修复前已执行的模块复现

通过 `node --import tsx --input-type=module` 在 `product/web` 执行内存脚本，直接导入实际 `createSourceCatalog`；同时断言订阅页仍传空回调、面板同步成功仍调用回调。

| 步骤 | 实际结果 |
|---|---|
| 第一次 `catalog.load()`，模拟服务端只有 `old` | 缓存就绪，请求计数 1 |
| 模拟服务端新增 `new`，执行当前的空回调，再 `load()` | 仍返回 `[old]`，请求计数仍为 1，断言通过 |
| 对照组执行 `catalog.invalidate()` | 快照变为 `[old,new]`，请求计数 2，断言通过 |

这是实际缓存模块与当前接线事实相结合的模拟复现；没有渲染 React 组件、请求真实后端或验证真实订阅地址。它足以确定通知断点与最小修复方向，不能替代浏览器验收。

React 官方说明 `useSyncExternalStore` 依赖 `subscribe` 的变更通知与 `getSnapshot` 的快照变化。根据这一机制及本仓源码，本问题应先修业务操作到 store 的通知链，而不是替换状态库。

### 4.4 最小修复方案（已实施，验证见 §6.1）

推荐复用宿主既有回调，保持页面层只负责接线：

```tsx
// app/pages.tsx：订阅页分支现已传递刷新回调
return <RssPage
  onOpenBackup={() => ctx.openModal('backup')}
  onSourcesChange={ctx.refreshSources}
/>
```

`RssPage` 已将新增的必传 `onSourcesChange: () => void` 原样传给 `SourceSubscriptionPanel`，替换空函数。面板已在同步成功时触发回调，无需重写同步流程，也无需让它直接依赖全局缓存。

另一个方案是在订阅面板内直接调用 `sourceCatalog.invalidate()`，更少传参但耦合更深；本轮倾向前者，因为 `PageContext` 已有所需能力。

补丁验收标准：

- 单条同步成功后共享清单刷新；全部同步中有成功项时同样刷新。
- 失败路径不显示“所有清单已更新”；重新拉取失败保留旧清单，并提供可见的重试/失败提示。
- 用真实页面接线配 mock API 验证跨页数据更新；保留一条将回调改回空函数就会失败的行为回归。
- 验证批量同步与快速切页，避免旧请求覆盖新清单；已有缓存竞态测试继续通过。
- 全量前端测试、应用类型检查和测试类型检查通过。

服务端定时同步发生在没有用户操作时，如何通知长期打开的前端，是另一项待评估边界。当前最小修复覆盖显式同步，不宣称解决后台自动同步、跨窗口或多设备推送。
