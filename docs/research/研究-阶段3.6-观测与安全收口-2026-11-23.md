## 1. 日志脱敏

### 1.1 出口只有一个，这是好消息

`ops/LogService.kt:75-123` 的 `log()` 是所有结构化日志的**唯一入口**：消息与 context 先过 `oneLine`（`:82-86`），然后同时写三处——SQLite（`:113`）、日志文件（`:140`）、stdout/stderr（`:141-144`）。前端「运行日志」读的是 `GET /api/logs`（`http/system/SystemRoutes.kt:80-85`）。

也就是说：**在 `log()` 里打一次码，三条去向 + 一个 HTTP 出口同时收口**，不需要改任何调用点。这是本次收口成本最低的一块。

### 1.2 秘密实际能从哪进来

| 路径 | 证据 | 泄露内容 |
|---|---|---|
| 书源网络失败上下文 | `rules/RuleHttp.kt:50-54`：`"url" to url.take(120)` | 完整 query（很多源把 `token` / `key` / `sign` 拼在 URL 上），截断到 120 字符**不影响把凭据截进去** |
| Cookie 同步日志 | `http/SourcesRoutes.kt:444`：`log.info("... url: {}", req.url)` | 同步来源页 URL；Ktor logger 走 stdout，不进库但进日志文件/容器日志 |
| 自定义 TTS 失败 | `http/TtsRoutes.kt:148-172`：`log.warn("TTS ... failed: {}", e.message)`；异常消息里带用户填的 URL（`EdgeTtsService.kt` 的 `tts_failed` 路径） | 用户 TTS URL 的 query（`?key=` 是常见形态） |
| 书源调试步骤 | `source/SourceDebugger.kt:57,93,120`：`bookUrl.take(96)` / `tocUrl.take(160)`；模型 `model/SourceModels.kt:352-359` | URL（同样含 query）；经 `/api/sources/debug` 返回，不落库 |

补充事实：`GET /api/logs` **不在同源写门保护范围内**（写门只管非安全方法，`http/Guard.kt:16`），所以：

- 本机任何进程（含恶意扩展调起的本地程序）都能读；
- **Docker 部署下**（`product/Dockerfile:50` 设 `LEGADO_HOST=0.0.0.0` + `LEGADO_ALLOW_EXTERNAL_BIND=1`），能连到该端口的人都能读整张日志表。

### 1.3 建议实现（S1）

在 `LogService.log()` 的 `oneLine` 之后加一步 `redact(text)`，两条规则：

1. **查询串按敏感键打码**：`(?i)(token|key|apikey|api_key|secret|sign|signature|password|passwd|pwd|auth|session|code)=([^&\s]{1,})` → `$1=***`。只匹配键名，不碰路径与普通参数（`page=2` 保持原样），避免"日志再也定位不到问题"。
2. **头样式打码**：`(?i)(authorization|cookie|set-cookie|x-api-key)\s*[:=]\s*\S+` → `$1: ***`（覆盖 `logNetwork` 把 `error.message` 带进来的场景，例如 `HttpClient` 的 `IllegalArgumentException: restricted header name: "Host"` 之类）。

同时把 `RuleHttp.networkContext` 的 `url` 改成"origin + path + 打码后的 query"（或直接复用 `redact`），保证日志里仍能看到"打到哪个站的哪个路径"，这是排障必需的。

**判据**：

- 表驱动单测：12 组输入（`?token=abc`、`?page=2&key=x`、`Authorization: Bearer x`、`Cookie: sid=1`、中文/大小写混合键、超长值、URL 编码）→ 敏感值消失、非敏感部分逐字保留。
- 回归：`GET /api/logs` 返回的 `context["url"]` 里不再出现 `token=` 后的原文；`host` 与 `path` 不变。
- 反向判据（防误伤）：`page=2`、`bookUrl=https://a.com/1.html` 原样保留。

**风险**：日志合并键（`LogService.kt:90`）用 `message|sourceId|host|statusCode|rule`，打码不影响键，去重行为不变。唯一要小心的是**不要把 `host` 打码**——那是定位主键。

## 2. 请求体上限

### 2.1 现状：全局没有，局部的三处里两处是"先读完再判"

```bash
cd product
grep -rn "receive<\|receiveText\|receiveMultipart\|streamProvider().readBytes" app/src/main/kotlin/io/legado --include=*.kt
```

| 点 | 代码 | 判定时机 |
|---|---|---|
| `PUT /api/ui-prefs/{key}` | `http/PrefsRoutes.kt:46-56`（`contentLength()` 先判，再 `receiveText()`） | **正确**：声明长度超 1MB 直接 413，不读 body |
| `POST /api/backup/import` | `http/BackupRoutes.kt:122` 先 `readBytes()`，`:135` 才 `bytes.size > MAX_BACKUP_BYTES`（64MB） | **错误**：64MB 上限是"读完才判"，传 10GB 就先 OOM |
| `POST /api/brand/icon` | `StaticWeb.kt:206` 先 `readBytes()`，`:213` 才判 5MB（注释里明说"形状照 BackupRoutes 那一条"） | **错误**，同上 |
| 其余 `call.receive<T>()`（58 处，另有 2 处 `receiveText()`） | 例：`http/SourcesRoutes.kt` 导入、`http/ReadingRoutes.kt:59`、`http/SearchRoutes.kt:55` | **无任何上限**：kotlinx 反序列化会把整个 body 读进内存 |
| 引擎层 | `Application.kt:76-85`：Netty `connector{}`，未设任何 body 相关限制 | Netty 默认没有总 body 上限 |

### 2.2 影响面（按可达性）

1. **Docker / 外部绑定**：任何人都能 `POST /api/sources/validate`（只读 POST，在同源写门白名单 `http/Guard.kt:34-39` 里，**跨站也放行**）发一个 4GB JSON → 堆爆，进程被 OOM killer 带走。这是最现实的一条。
2. **本机**：恶意页面无法跨站写（写门挡住），但本机任意进程可以。对单机自托管来说威胁模型弱一档，但"一个 bug 把服务打死"仍然成立。
3. **正常用户误操作**：拖错文件（比如把 2GB 的视频拖进"导入备份"）→ 服务卡死而不是报"太大"。

### 2.3 方案

**A. 声明长度闸（必做，覆盖 90% 场景）**

新增全局插件（与 `SameOriginWriteGate` 同层，`Application.kt:273` 之前），只对 `POST/PUT/PATCH` 生效：

```kotlin
val declared = call.request.contentLength()
if (declared != null && declared > limitFor(call)) → 413 + ApiError("body_too_large", ...)
```

`limitFor` 按路径给不同上限（JSON 端点 8MB；备份导入 64MB；图标 5MB），默认 8MB。**不读 body**，零成本。

**B. 未知长度（chunked）需要一次 spike**

Ktor 3.4.3 没有内置 body limit。可选做法：在 `ApplicationReceivePipeline` 上装一个 `ByteReadChannel` 的 `transformBody`，用 `readRemaining(limit)` 计数，超限抛 `PayloadTooLargeException` 由 `StatusPages` 转 413。**这一步没验证过**（见 §5），建议先写一个最小 spike 证明"能拦、不破坏 multipart"，再决定是否上。

**C. multipart 两处改流式（必做）**

把 `part.streamProvider().readBytes()` 换成"边读边计数、超限即中止"（形状直接抄 `tts/EdgeTtsService.kt:490-501` 的 8MB 循环）：

- `BackupRoutes`：先写临时文件并计数，超 64MB 立即 413 并删临时文件；导入器本来就吃 `ByteArray`，可以读完再交给它（64MB 在堆内可接受），关键是**在超限那一刻就停**，不是读满 10GB 才发现。
- `StaticWeb`：图标只有 5MB，直接 `ByteArrayOutputStream` + 计数即可。

### 2.4 判据

- 声明 `Content-Length: 9MB` 的 JSON → 413，且**服务端日志里没有任何 body 读取迹象**（用 `ThreadMXBean` 不现实，退而求其次：断言响应耗时 < 50ms）。
- `Transfer-Encoding: chunked` 的 9MB body → 413（若 spike 成功）；spike 失败则明确记为"未覆盖"。
- multipart 传 100MB → 413，且 `data/` 下没有残留临时文件。
- 正常路径零回归：`ApiRoutesHttpTest` 那批（导入 3 个源、上传 1 张图标、导入 1 个备份）全绿。
- 413 的 `ApiError.code` 固定为 `body_too_large` / `backup_too_large` / `icon_too_large`，前端可区分。

### 2.5 风险

- **413 与 Compression 的顺序**：压缩插件在响应侧，不影响请求；但 413 必须发生在 `ContentNegotiation` 反序列化之前（onCall 阶段天然满足）。
- **WebSocket**：`/api/search/ws` 走 WS 帧上限（`SearchRoutes.kt:177-178` 已有 64KB/64 条），不受 body limit 影响；插件要跳过 `Upgrade: websocket` 的请求。
- **备份导入**：64MB 上限是既有产品口径，不要顺手改。

## 3. 非回环身份（这一块要先决策，不是先写代码）

### 3.1 现状

- 启动闸门：`http/Guard.kt:148-156` `requireLoopbackBind` —— 非回环且未设 `LEGADO_ALLOW_EXTERNAL_BIND=1` 时**拒绝启动**；设了则返回 true，`Application.kt:136-147` 打一条警告。
- 没有任何 token / 账号 / 会话。同源写门只防"浏览器被别的网页驱动"，**不防非浏览器客户端**（`http/Guard.kt:11-13` 明说放行 curl / 扩展 / 服务间调用）。
- Dockerfile 直接把两个开关都打开（`product/Dockerfile:50`），所以**容器部署默认就是"整库对网络开放"**，只有一条启动警告。

### 3.2 与既有产品决策的冲突

`http/Guard.kt:11-13` 的开头就是决策记录：

> 这台服务不设身份：只绑回环、给一个人用，密码、登录页与会话在这里没有意义（用户 2026-09-29：「怎么还有这个功能，删掉；咱们这个是开源的，不要那么多条条框框」）。

所以 3.6 原文的"非回环必须鉴权"**不能按字面实现**——它会把 2026-09-29 的决策直接推翻，而且会让现有 Docker 用户升级后立刻无法访问（`compose.yml` 发布端口、无 token）。

### 3.3 三个选项

| 选项 | 做法 | 默认行为 | 代价 |
|---|---|---|---|
| **A. 保持现状 + 文档**（最小） | 不改代码；把"外部绑定 = 整库裸奔"写进 README/SECURITY，并在启动日志里把警告升级为 ERROR 级 | 零变化 | 容器用户仍然裸奔；3.6 这条永远开着 |
| **B. 可选 token**（推荐） | 设了 `LEGADO_ACCESS_TOKEN` 就要求鉴权：非回环来源的请求必须带 `Authorization: Bearer <token>`（或 `?token=`，给不方便加头的客户端）；回环来源豁免；未设 = 行为完全不变 | 零变化 | 要改前端（fetch 封装加头、首次访问存 token）、`/api/logs` 这类 GET 也要覆盖、写门与 token 的先后顺序要定 |
| **C. 强制 token**（不推荐） | 非回环绑定必须给 token，否则拒绝启动 | **破坏性** | 现有 Docker 用户全部升级即挂；与"开源、少条条框框"的定位冲突 |

**推荐 B**：它把"要不要对外"变成部署方的显式选择，且不动单机用户的任何路径。判据可以写得很硬：

- 未设 token：`GET /healthz`、`/api/logs`、写操作全部与今天逐字节一致（用现有全量测试证明）。
- 设了 token + 绑 `0.0.0.0`：不带 token 的请求 401；带正确 token 200；回环来源（`127.0.0.1`）不带 token 仍 200。
- token 只从环境变量读，不落日志（依赖 S1 的打码，`Authorization` 会被打码）。

### 3.4 决策记录（2026-11-23，负责人已拍板）

1. **做不做 B** → **做 B（可选 token）**。未设 `LEGADO_ACCESS_TOKEN` 时所有行为与今天逐字节一致；设了才对非回环来源要求鉴权。这是对 2026-09-29"不设身份"决策的**增量补充**而非推翻：单机用户无感，只有显式要对外的人才有新义务。
2. **容器用户怎么拿到 token** → **取 (c) 只认环境变量，不自动生成**。理由：
   - 与产品哲学一致——"开源、少条条框框"意味着不引入隐式的 token 文件/生成逻辑；想要鉴权的部署方自己把 `LEGADO_ACCESS_TOKEN` 写进 compose（即 (a) 的使用方式），服务不代劳。
   - (b) 自动生成 + 打印日志会给 S1 脱敏开一个"把凭据写进日志"的白名单口子，与 S1 的宗旨（凭据永不落日志/库）直接冲突；不取。
   - 环境变量是现有全部配置的唯一入口（`AppConfig`），`LEGADO_ACCESS_TOKEN` 与 `LEGADO_ALLOW_EXTERNAL_BIND` 等并列，不新增状态文件、不需要清理逻辑。
   - 未设时不生成、不打印、不落盘——"未设=行为完全不变"这条承诺在容器里同样成立。

**实施补充事实（2026-11-23 读码查实）**：
- 回环来源判定可直接用现成的 `ServerConfig.isLoopbackRemote(remoteHost)`（`ServerConfig.kt:38`），它已正确处理 `127.x` / `::1` / `::ffff:127.x`，且不会把 `2001:db8::1` 误判成本机。请求来源 IP 取 `call.request.local.remoteHost`（Ktor 3.4.3 `RequestConnectionPoint` 确认有此字段）。
- **Docker 语义**：容器内服务看到的 `remoteHost` 是网桥网关 IP（172.x），不是回环——即使 compose 把端口映射到宿主 `127.0.0.1`，宿主访问在容器内仍算"非回环"，会被要求 token。这正是 (c) 要解决的场景，合理。
- `?token=` 查询参数会被 S1 的敏感键规则（`token`）打码，不会落进访问日志——原先担心的"SSE/WS query token 与 S1 张力"实际不存在，S1 正好覆盖。
- 鉴权闸必须**抛异常**而非 `call.respond` 后 return —— Ktor 的 `onCall` 不阻断 pipeline（同 `RequestBodyLimit` 的结论），respond 之后路由仍会跑。装 `StatusPages` 之后，异常转 401。

## 5. 未验证

- **chunked body 能否在 Ktor 3.4.3 的 receive pipeline 上可靠计数**：已 spike 并实施（见 §8）——能拦。判据做了负向对照：注释掉 `on(BeforeReceive)` hook 后，chunked 判据从 413 变 400（body 被读进 `ContentNegotiation`），证明它真实测到 hook 而非 S2a 假阳性。坑在于官方 `PayloadTooLargeException` 会被 `ContentNegotiation` 吞掉根因，必须抛自定义异常。
- **multipart 上传经 HTTP 端到端路径未被这条 hook 误伤**：**仍未验证**。备份/图标的现有测试直调 `BackupImporter` / `saveIcon`，不走 `receiveMultipart()`，不能当作"hook 不破坏 multipart"的证据。`BeforeReceive` 挂在 `receivePipeline.Before`，理论上也会介入 `receiveMultipart()`（累计的是整个 body，按路径上限 64MB/5MB，比 S2b 的单 part 口径更严）；正常备份本身 ≤ 64MB 不会误伤，但这条路径没有专门的端到端判据，若以后动 multipart 上传应先补一条。
- **真实 OOM 复现**：没拿 4GB body 打过活服务（会打断本机环境）。§2.2 的"堆爆"是从代码路径推的，不是实测。
- **日志里真实出现过凭据**：本机库 `product/data/legado.sqlite` 只有 12 条启动日志，没有网络日志样本；"URL 带 token"是书源生态的普遍形态，不是从本机日志统计出来的。
- **`GET /api/logs` 在 Docker 下的实际暴露面**：取决于部署方是否把端口发布到公网，本环境没有容器在跑。
- **token 方案对前端的改动量**：2026-11-23 已读 `web/src/lib/api/client.ts` 查实。主路径很集中——所有 REST 请求收敛到 `client.ts:15` `requestResponse` 里的**唯一** `fetchWithMetrics`（`:26`），加 `Authorization: Bearer` 只需这一处。但 B 方案若要求 SSE/WS 也鉴权，有几条绕过该封装的路径要单独处理：`main.tsx:373` 的 `fetch('/healthz')` 启动探测；`lib/importFromUrl.ts:56` 的裸 `fetchWithMetrics`（打的是**外部** URL，不应带本地 token）；两处 `EventSource`（`ttsEngine.ts:455`、`SourceDebugModal.tsx:41`）与两处 `WebSocket`（`search.ts:39`、`index.ts:98`）——浏览器原生 SSE/WS **不能自定义请求头**，只能走 `?token=` 查询参数，而 query token 会落进访问日志，与 S1 脱敏有张力。另需一个"首次访问存 token"的入口（当前按 2026-09-29 决策无登录页，这本身是冲突点）。据此 B 的真实成本：后端鉴权闸 + client.ts 一处注入 + 4 条 SSE/WS 改 query + healthz 探测 + token 输入 UI + 日志白名单。


## 8. 实施记录（2026-11-23，S2a + S2b + S2c 已完成）

**改动**

- 新增 `http/BodyLimit.kt`，三件事共用一份上限真源 `BodyLimits`（JSON 8MB / 备份 64MB / 图标 5MB，图标直接引用 `BrandStore.MAX_ICON_BYTES`）：
  - **S2a** `RequestBodyLimit` 全局插件：`onCall` 阶段对 POST/PUT/PATCH 按 `Content-Length` 判，超限**抛** `PayloadTooLargeException`。关键取舍：抛异常而非 `call.respond` —— Ktor 的 `onCall` 不阻断 pipeline，respond 之后路由仍会 `receive<T>()` 把 body 读进内存；抛异常才真正让处理器不跑。WS 升级请求显式跳过。
  - **S2c** 同一插件的 `on(BeforeReceive)` hook：无 `Content-Length` 的 chunked body 在 `ApplicationReceivePipeline.Before` 阶段被换成边读边计数的 `ByteReadChannel` 包装（`applyLimit`），超限即抛、不把超限字节读进内存。形状照 Ktor 官方 `body-limit` 插件复刻，但**抛自定义异常**：官方 `io.ktor.server.plugins.PayloadTooLargeException` 会被 `ContentNegotiation` 吞掉根因（沿 cause 链都找不到），只能回 400；自定义类作为 cause 原样保留，`StatusPages` 的 `isBodyLimitOverflow` 沿 cause 链把它认回来转 413。
  - `StatusPages` 新增 `exception<PayloadTooLargeException>` → 413 + `ApiError(code, message)`，装在 catch-all 之前；另在 `BadRequestException`/`ContentTransformationException` handler 里先走 `isBodyLimitOverflow(cause)`，把被包进这两类的 S2c 超限也归位成 413（否则误报 400）。`install(RequestBodyLimit)` 装在 StatusPages 之后，异常才会被这条 handler 接走。
  - **S2b** `readBounded(...)`：multipart 文件流边读边计，超限即抛、不读完；`ByteArrayOutputStream` 累计，缓冲 16KB。
- `http/BackupRoutes.kt`：备份导入的 `part.streamProvider().readBytes()` → `readBounded(..., BACKUP_BYTES, "backup_too_large", ...)`；删掉旧的"读完再判 64MB"块；`dispose()` 挪进 `finally`，超时也释放 part。
- `StaticWeb.kt`：品牌图标上传同样改 `readBounded(..., ICON_BYTES, "icon_too_large", ...)`；删掉旧的"读完再判 5MB"分支。
- 文档：`docs/STATUS.md` §4 安全模型从"五条"改"六条"并新增第 6 条；`docs/ARCHITECTURE.md` 插件链示意、安装清单（步 10）、目录表与"守护与日志"行补 `BodyLimit`。

**判据**

- `BodyLimitTest` 4 项：三路径分档上限与错误码、恰好等于上限完整返回、跨多次小块累计超限即抛且错误码正确（喂一个**永不 EOF** 的流，若退化成 `readBytes()` 会死循环/超时）、空输入返回空数组。
- `BodyLimitHttpTest` 4 项：超声明 JSON 写请求在反序列化前转 413（用非法 JSON 大 body，若被读到会得到 400 而非 413）、图标端点返回专属 `icon_too_large`、正常小 body 写与 `/healthz` 零回归，以及 **S2c** 一条用 `WriteChannelContent`（无 `Content-Length`，Ktor 按 chunked 发）打 `/api/replace-rules` → 413 `body_too_large`。

**改动**

- 前端：`lib/accessToken.ts`（存/取/拼 `?token=`，localStorage 不可用静默降级）、`lib/api/client.ts` 唯一 fetch 处注入 Bearer + 401 时清旧 token 并派发 `legado:unauthorized`、`main.tsx` healthz 探测带 token 且遇 401 快速放行、`components/AccessTokenPrompt.tsx` 监听事件弹输入框（保存后 reload）、四处 SSE/WS（书源调试 EventSource、TTS EventSource、搜索 WebSocket×2）走 `withTokenQuery`。
