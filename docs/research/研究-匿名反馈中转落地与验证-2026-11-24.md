## 0. 一句话结论

五阶段（0–4）的**代码全部落地**，后端 1,071 项、前端反馈相关 11 项全绿，全仓无密钥字符串。
唯一**未在代码层闭合**的是第 3 阶段的后端节流：`/api/feedback` 没有服务端限流，只有前端 30 秒冷却
（可被直接调 API 绕过）。这是 Supabase 免费额度的实际风险点，列为开放项 §5。

实现方式与用户方案**有两点有意偏离**，都有证据（§4）：

1. 建表 SQL 多一条 `revoke update, delete ... from anon`——把「不建 update/delete 策略」升级为显式收回，
   防止将来误加策略时开写口。
2. 查询端点把 `limit 1` 放宽到 `limit 20`，并回 `created_at/category/content`，让「查看我的建议」有实际用途。

## 7. 开放项 / 风险

1. **后端无节流（唯一代码层缺口）**：只有前端 30s 冷却，直接调 `/api/feedback` 可绕过。免费版 anon insert
   对公网开放，任何人可刷写占额度。建议后续在 `RequestBodyLimit` 旁加按 token hash 的滑动窗口，
   或依赖 Supabase 侧限流——**本期未做**，需负责人定夺阈值与存放位置（本地内存 vs Supabase）。
2. **`select own only` 依赖 PostgREST 把自定义头透传进 `request.headers`**：若 Supabase 升级改变头名小写化行为，
   查询会回空。属外部依赖，本地无 Supabase 项目无法端到端验证。
3. **无留存清理策略**：feedback 只增不删，免费额度有上限。可后续加定期导出/归档。
4. **查询放宽到 20 条**是本地决定，若负责人要严格贴合原方案（limit 1）需改 `FeedbackService.kt:85`。
