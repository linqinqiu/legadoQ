> 性质：**研究 / 迁移方案**，本轮不改出站代码。所有行号对应当前 HEAD，命令可复现。
> 依据：`REBUILD_PLAN/21_PHASE1_ARCHITECTURE_DESIGN.md` §3.1 R2b、`09_MIGRATION_ROADMAP.md` §3 切片 3.5。

## 0. 结论

G3 的 6 条基线**不是同一种债**，不能一把梭全改：

| 点 | 判定 | 理由 |
|---|---|---|
| `UpdateCheck.kt:42` | **直接迁** | 只打 GitHub 公共 API，走闸门零行为变化 |
| `WebViewProxy.kt:60` | **直接迁** | 抓的是书源远程页，正是 SSRF 闸门的目标面；有 `WebViewProxyTest` 兜底 |
| `EdgeTtsService.kt:28` | **拆两路**：自定义 TTS 的 HTTP 走闸门（`allowLoopback=true`），Edge 的 WSS 另办 | 用户可填任意 URL（含本机 TTS），不能一律拒回环；`GuardedHttpClient` 目前**不支持 WebSocket** |
| `DesktopLauncher.kt:313/323` | **移出 G3 基线，不算违规** | R2b 原文是「只有 `app/` + `kernel/fetch` 能建客户端」；桌面壳属组合根，且只探回环 `/healthz` |
| `ExternalBrowserLogin.kt:99` | **暂留**，或下沉 `ops/` 本地控制面 | 它连的是本机 Chromium DevTools（`127.0.0.1:<debugPort>`），不是出站抓取；走 PinnedProxy 只会给启动路径加故障点 |
| `GuardedHttpClient.kt` 自身 | 保留 | 它是唯一合法签发点的实现体，不是违规 |

**净效果（若按上表执行）**：G3 基线 6 → **1**（只剩 `ExternalBrowserLogin`）；`DesktopLauncher` 两条按规则本就不该计入。

## 2. 逐点判定

### 2.1 `UpdateCheck`：直接迁，判据是「同一仓库、同一超时」

```kotlin
private val client = NetworkSecurity.newHttpClient(
    connectTimeout = Duration.ofSeconds(8),
    followRedirects = HttpClient.Redirect.NEVER,
)
```

- 行为差异只有一处：请求会经 `PinnedProxy` 回环一跳。GitHub 是公网，闸门必放行。
- 现有 `UpdateCheckTest` 只测版本比较，不触网；迁移后补一条「非法 `LEGADO_REPO`（如 `http://127.0.0.1`）被拒」的判据即可证明闸门真的接上了。
- **注意**：`repository` 是 `val` 且在对象初始化时读环境变量，测试要用可注入的 `check(repository)` 入口，别去改全局状态（与 `ServerIdentity` 同类陷阱）。

### 2.2 `WebViewProxy`：直接迁，先补一条「内网地址被拒」判据

- 它抓的是登录页与书源接口，天然是 SSRF 面；`allowedDomains` 只限域名，挡不住「白名单域名的 DNS 解析到 169.254.169.254」。
- `GuardedHttpClient.send` 的返回类型、`BodyHandlers.ofByteArray()` 用法完全兼容（`WebViewProxy.kt:321`）。
- 风险点：`PinnedProxy` 的 CONNECT 隧道对**大响应 / 流式**是否与直连一致，本环境没有浏览器级回归；现有 `WebViewProxyRouteTest` 是路由层判据，**不覆盖真实出站**。迁移提交里必须附「本机真实登录一次」的人工验证记录，或明确标注未验。
- 迁移后 `WebViewProxy` 不再需要自己的 `HttpClient` 字段，G3 基线删一行。

### 2.3 `EdgeTtsService`：拆两路，不要硬塞进一个 client

现状一个 `client` 同时用于：
- `newWebSocketBuilder()`（`:173`、`:293`）→ `wss://speech.platform.bing.com`（**固定域名**）
- `send()`（`:361`、`:370`）→ 用户自定义 TTS URL（**可控**）

`GuardedHttpClient` 没有覆写 `newWebSocketBuilder()`，`HttpClient` 的默认实现会抛 `UnsupportedOperationException`。所以：

1. **自定义 TTS 的 HTTP** 换成 `NetworkSecurity.newHttpClient(connectTimeout = 10s, followRedirects = NEVER, allowLoopback = true)`。
   - 必须 `allowLoopback=true`：本机 TTS（GPT-SoVITS / ChatTTS 等）是真实用法，一刀切拒回环等于砍功能。
   - 打开后仍拒私网 / 链路本地 / CGNAT / 保留段 —— 云元数据端点照旧进不来。
   - 现有 `EdgeTtsTest` 用 `127.0.0.1` 起 `HttpServer` 并注入 client；默认构造那条要跟着改成 guarded 实例，否则测试会红（这正是判据起作用的证明）。
2. **Edge 的 WSS** 二选一：
   - **推荐**：给 `GuardedHttpClient` 补 `newWebSocketBuilder()` 包装（`buildAsync` 前调 `guard(uri)`，其余方法透传）。约 20 行，能同时把「未来任何 WS 出站」纳入闸门。
   - 备选：把 WSS 拆到独立的 `EdgeTtsWebSocket`，保留一个私有裸 client。缺点是 G3 基线缩不掉（文件里仍有裸构造），等于没还债。
3. 无论选哪条，都要补一条判据：**自定义 TTS 指向 `http://169.254.169.254/` 必须被拒**，指向 `127.0.0.1` 必须放行。

### 2.4 `DesktopLauncher` 两处：按规则不该计入 G3

R2b 的允许面是 `app/` + `kernel/fetch`。桌面壳是组合根，且两个 client 只探 `127.0.0.1` 的健康端点，没有用户可控 URL。建议：

- G3 基线删掉 `DesktopLauncher.kt` 两行；
- 在 `architecture-check.mjs` 的 G3 扫描里把组合根文件加入允许面（`DesktopLauncher.kt`、`Application.kt`），并在注释里写明「组合根允许建客户端，R2b 原文如此」。
- **不要**为了消基线把它接到 `PinnedProxy`：桌面启动探测只有 1.2s，代理懒启动失败会把「双击没反应」这类老问题带回来。

### 2.5 `ExternalBrowserLogin`：回环控制面，暂留并说明

- 用途是驱动本机 Chromium 的 DevTools HTTP API（`/json/version`、`/json/new`），不是抓取外部内容。
- 走 `PinnedProxy` 的收益是零（目标恒为 `127.0.0.1`），代价是多一个可能失败的进程内依赖，且登录是低频但关键的路径。
- 建议保留 G3 最后一条基线，注释改为「本机控制面，非出站抓取；待 `kernel/fetch` 落地后以 `LocalControlClient` 名义收编」。
- 若一定要清零：在 `ops/` 建 `LocalControlClient`，内部校验 host 必须是 `127.0.0.1`/`::1` 后直接建 client，G3 把 `ops/LocalControlClient.kt` 列为合法签发点。这是「显式白名单」而不是「悄悄绕过」。

## 3. 迁移顺序（每步可独立回滚）

1. **G3 规则修正**（2026-11-22 已执行）：组合根加入允许面，并剥掉块注释再匹配；基线 6 → 4（`UpdateCheck` / `ExternalBrowserLogin` / `WebViewProxy` / `EdgeTtsService`）。实测 `node tools/verify/architecture-check.mjs` → G3 基线 4 / 当前 4。
2. **`UpdateCheck` 迁移** + 一条「内网仓库地址被拒」判据。基线 4 → 3。
3. **`WebViewProxy` 迁移** + 一条「白名单域名解析到内网被拒」判据。基线 3 → 2。
4. **`GuardedHttpClient` 补 WebSocket** + 单测（`buildAsync` 指向 `127.0.0.1` 被拒、公网放行）。
5. **`EdgeTtsService` 拆两路迁移** + 自定义 TTS 回环放行 / 元数据端点拒绝两条判据。基线 2 → 1。
6. **`ExternalBrowserLogin` 决策**：保基线并改注释，或建 `LocalControlClient` 后清零。

每步的验收：`node tools/verify/architecture-check.mjs` 绿 + 对应单测 + 后端全量（当前 1,015 项 / 6 跳过；`E2EScenariosTest` 的 300ms 判据在 CPU 争抢时会偶发红，重跑即绿，2026-11-22 实测）。

## 4. 未验证 / 风险

- **没有做真实登录回归**：`WebViewProxy` 走代理后，Chromium 登录页的 Cookie/重定向行为只经路由层测试，未经真机浏览器验证。
- **本机 TTS 未实测**：`allowLoopback=true` 的放行范围（只 127/8 与 ::1）是按 `NetworkSecurity` 现有实现推断，没有起一个本机 TTS 服务端到端跑过。
- **WSS 包装未实现**：`GuardedHttpClient.newWebSocketBuilder()` 的透传方法集（`header` / `subprotocols` / `connectTimeout` / `buildAsync`）需要按 JDK 17 的接口逐一对齐，本文只给方案。
- **`PinnedProxy` 大响应**：`WebViewProxy` 可能拉整页 HTML/图片，代理链路的内存与超时表现未压测。
