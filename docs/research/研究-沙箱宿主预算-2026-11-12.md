# 沙箱宿主预算（审计 E 项）：先能观测，再谈阈值

> 2026-11-12。承接 [`product/docs/rules-sandbox-audit.md`](../../product/docs/rules-sandbox-audit.md) §3 的 E 项
> （"宿主侧调用没有统一预算"）。本文只做研究与方案取舍，**不含实现**；结论是"不该直接上硬预算"。
>
> 写法遵循本目录约定：数字标口径、不复制会变的测试数与版本号。

## 0. 一句话结论

E 说的缺口是真的——**单次 8MB 上限挡不住"多次小额、脚本保留"的累计 OOM**。
但不该按原方案直接给每个入口记账、也不该拍一个 64MB 硬阈值：阈值只能从真实源库的分布里取。
建议按 **参数化 → 三处闸口记账 → 诊断观测 → 定阈强制** 四步走，前两步对现有行为零影响。

## 1. 现状（2026-11-12，`HEAD` 实测）

| 层 | 在哪 | 管什么 |
|---|---|---|
| 单次分配 | `JavaPackages.kt` 的 `requireAllowedLength`（9 个调用点：`copyOf` / 字节数组 / `arraycopy` / Base64 / `nextBytes` / `format` 模板与参数数） | 单次长度 > 8MB 直接拒 |
| 单次分配 | `requireStringBuilderWithinLimit`（`setLength` / `append` / `insert` 共用） | StringBuilder 1e6 |
| 单次分配 | `GzipLimits.unzipBounded` / `gzipBounded` | 解压/压缩 16MB，流式记账 |
| 时间 | `JsGuard.kt` 的 `BoundedContext.observeInstructionCount` | 每 20k 条指令查一次墙钟，默认 30s |
| 宿主阻塞 | `BoundedJs.deadlineOrNull()` → `RuleRunner.fetchResponse(deadlineMs=…)` | 只覆盖网络那一类（审计 D 项） |
| 桥面规模 | `createJavaBridge` 的 `putProperty(api, …)` 共 **106 处**（12 个 `fn{}`、48 个 `object : BaseFunction()`、其余由 helper 生成） | 全部宿主入口 |

复现：`grep -c 'putProperty(api, "' product/app/src/main/kotlin/io/legado/rules/JsSandbox.kt`

## 2. 缺口到底在哪

**per-call 上限 × 循环次数**。`Arrays.copyOf([1], 8M)` 单次完全合法；脚本把它塞进 JS 数组保留下来，
几十次就是数百 MB —— Rhino 的 `NativeArray` 持有这些 Java 数组，GC 不会回收。

30 秒墙钟**不构成保护**：一次 8MB 拷贝是毫秒级，指令数也远低于 20k 的检查粒度。
这正是审计里说的"第 3 层盲区"：不耗指令、不阻塞、只是稳定地把内存搬进宿主。

> 本文**不给**"30 秒能分配多少 GB"的实测数字。原因写在审计 §4：在判据里构造十几 MB 的 payload
> 喂 Rhino，会被按元素装箱，17/20/24MB 三种都触发过 `Native memory allocation (mmap) failed`，
> 挂掉的是 Gradle 测试执行器。这台机器的页面文件也扛不住这类压测。

## 3. 为什么不在 106 个入口逐个记账

审计原文已经点出失效模式："漏记一处等于没有" —— 和手写白名单是同一个问题，只是换了一层。
**真正的放大都收敛在 3 个闸口**（上表前三行），记账应该落在闸口，而不是入口：

- 凡是"长度由脚本给、开销在宿主"的路径，今天都必须过 `requireAllowedLength` / `requireStringBuilderWithinLimit` / `GzipLimits`；
- 剩下的大对象都来自**已经在内存里的 JS 字符串**（`bytesOf` 的 `toByteArray`，放大约 2–3 倍），不构成无界放大。

## 4. 三个方案

| 方案 | 做法 | 代价 |
|---|---|---|
| **A 硬预算** | 定 64MB，闸口直接记账并抛错 | 一行代码，但阈值没有依据。批量解码图片/长章节正文的**合法**源可能超；症状是"某些书偶尔解析失败"，只在长章节出现，属于最难查的回归 |
| **B 参数化 + 观测**（推荐） | 预算作为参数（与 `timeoutMs` 同一套路），默认无限；先只记账不拦，诊断里暴露"本次执行累计宿主字节"；用真实源库跑一轮取分位数，再定默认值 | 多两步，但阈值有据；前两步行为零变化 |
| **C 不做** | 接受风险 | 理由站得住（导入源本就不可信、有 30s 上限），但一旦命中就是进程级 OOM，代价不对等 |

## 5. 分步任务（每步单提交 + 判据）

1. **B1 参数化**：`BoundedJs.enter(timeoutMs, hostByteBudget = Long.MAX_VALUE)`，`BoundedContext` 增
   `hostBytes` / `chargeHostBytes(n)`。判据：默认值下后端全量测试全绿（行为零变化）。
2. **B2 记账**：上面三个闸口各记一笔；超限抛 `IllegalArgumentException`（沿用现有口径——
   脚本能 `runCatching` 兜住并降级，**不打掉线程**）。判据：注入 1MB 预算后，循环 `copyOf` 必须被中断，
   且沙箱随后仍可用。
3. **B3 观测定阈**：`/api/diagnostics` 增每执行累计字节（峰值/次数），跑真实源库一轮，
   按分位数 ×3 定默认预算，再开强制。

## 6. 判据怎么写（沿用既有三份判据的纪律）

- **用注入的小预算**，不构造真实大 payload（见 §2 的坑）。
- **既断言"被拦住"，也断言"沙箱仍可用"** —— 只证明抛了错不够，还要证明线程没被打掉。
- 中断必须抛 `Exception` 而不是 `Error`，否则 `runCatching` 兜不住，表现是整条规则链失败而不是降级。

## 7. 本轮为什么没动手

B1 要改 `BoundedJs.enter` 的签名，而它是**所有** JS 路径（含现有判据）的唯一入口；
在拿到观测数据之前引入这个参数，只是把"拍阈值"从代码里挪到接口上，没有解决任何问题。
真要推进，B1 + B2 应该同一笔提交，B3 单独一轮。

## 8. 不建议做的事

- 在 106 个入口逐个 `charge`（失效模式同上）。
- 用 `WeakHashMap` 之类的 GC 依赖方案兜内存（审计 A 项已论证：回收时机不可断言，判据写不出来）。
- 为了"验证"在 CI 里真跑 OOM（会挂测试执行器，不是被测代码）。
