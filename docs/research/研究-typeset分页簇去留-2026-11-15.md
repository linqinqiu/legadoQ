# 研究：typeset 分页簇去留（N-1）

> 日期：2026-11-15 ｜ 仓库：`E:\legado` ｜ 起点 `main` @ `777a343`
> 承接：[研究-外部建议核对-2026-11-14](研究-外部建议核对-2026-11-14.md) §3 的 N-1
> 性质：**只读实测 + 决策建议**。未改产品代码（仓库内只新增本文与索引/状态行）。

## 0. 结论（先看这里）

**建议整簇删除，不接入生产。** 理由是三条，按强度排序：

1. **成本理由已不成立**：真实章节长度下，现有 DOM 量栏实测中位 **1.6 ms**、p99 场景 **4.6 ms**，
   连"一章 2.7 万字"的极端单章也只要 **6.2 ms**。它根本不构成性能问题，也就没有"必须换掉 DOM 测量"的动机。
2. **纯数学引擎无法复刻真实排版**：`charWidth` 把 ASCII 一律当 `0.6em`、CJK 当 `1em`，
   `letterSpacing` / `textIndent` / 实际字体（7 套内置字体）**完全不参与计算**，图片只认 markdown 语法、
   段落间距按"整行"取整。这些偏差会直接变成页数与页码漂移。
3. **它是第二套事实源**：真源已经是 CSS 分栏 + DOM 量栏；接入等于要求一套并行的排版模型
   长期跟上 7 字体 × 字号 × 字距 × 版心 × 图片混排，维护成本远大于它省下的那 1–5 ms。

**删除清单**（一行一刀、单独提交）：
`web/src/features/reader/typeset/`（3 文件 264 行）、`web/src/features/reader/content/paginationCache.ts`（179 行）、
`web/test/LayoutEngine.test.ts`、`web/test/PaginationCache.test.ts`，并同步 `docs/ARCHITECTURE.md:494-497`
与 `product/docs/restructure/frontend-host.md:724` 的"已实现但未接入"表述。

## 2. 证据 A：真实章节有多长（本机库快照）

口径：把 `product/data/legado.sqlite`（含 WAL）复制到临时目录后只读查询 `book_content_cache`，
不触碰使用中的库。

```
select count(*), round(avg(length(content))), min(length(content)) from book_content_cache;
→ 715 | 2058 | 3
p50 = 2147 字 ・ p90 = 3465 ・ p99 = 6704 ・ max = 27039
平均每章 76 个换行（≈ 76 段）
```

也就是说：**一屏阅读窗口（锚点章 + 前后各一章）绝大多数在 6–10k 字、200–300 段**。
2.7 万字的巨章在 715 章里只出现一次。

## 3. 证据 B：DOM 量栏实际成本（Chrome 实跑）

方法：用 puppeteer-core 驱动本机 Chrome（`C:\Program Files\Google\Chrome\Application\chrome.exe`），
页面**复刻生产的分栏结构与 CSS**（`.reader-paginated-wrap/-viewport/-track/-column-body` 的 `column-fill:auto`、
`.reader-page-chapter` 的 `padding-top:2.2em` + 相邻 `margin-top:1.6em`、`h1{break-before:column}`、
`p{margin-bottom:1.15em; text-indent:2em; text-align:justify}`），字号 19px / 行高 1.95 / 版心 860px（均为默认值）。
计时函数与 `usePaginationMeasurement.ts:88-116` 同构：两遍 `Range.getClientRects()`，并额外触发一次 `body.scrollWidth`。
每个场景预热 1 次、取 7 次中位数。

| 场景（单栏 860px） | 段数 | 行碎片 | 页数 | 第 1 遍 | 第 2 遍 | 合计（中位） | 最差 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 章 p50（2,147 字） | 66 | 134 | 5 | 0.4 ms | 0.3 ms | **0.7 ms** | 1.2 ms |
| 窗口 3 章 p50 | 198 | 402 | 15 | 0.8 | 0.8 | **1.6 ms** | 2.7 ms |
| 窗口 3 章 p90 | 318 | 642 | 24 | 1.3 | 1.2 | **2.4 ms** | 2.9 ms |
| 窗口 3 章 p99 | 612 | 1,230 | 45 | 2.4 | 2.3 | **4.6 ms** | 5.4 ms |
| 单章 max（27,039 字） | 820 | 1,642 | 59 | 3.2 | 3.0 | **6.2 ms** | 7.4 ms |
| 窗口 3 章 max（极端） | 2,460 | 4,926 | 177 | 9.8 | 8.7 | **18.1 ms** | 19.5 ms |

结论：**只有"连续三章都是 2.7 万字巨章"这种不存在的场景才会超过一帧（16.7 ms）**。
现实窗口里量栏 1–5 ms，且只在换章 / 改排版 / 窗口尺寸变化时跑一次。与之相比，切到数学引擎
省下的是个位数毫秒，却要付出 §4 的漂移风险。

## 4. 证据 C：纯数学引擎的偏差来源（静态审查，可复核）

`typeset/layoutEngine.ts` 的模型（`charWidth:34-42`、`layout:44+`）：

| 真实排版因素 | 引擎处理 | 后果 |
| --- | --- | --- |
| 7 套内置字体 / 用户字体（`fontLibrary`） | `fontFamily` 入参但**不参与宽度计算** | 换字体页数不变，屏幕上的真实页数会变 → 页码漂移 |
| `letterSpacing`（-0.25 ~ 1.5px，设置项） | 完全不参与 | 1.5px × 45 字/行 ≈ 67px，版心宽 8% → 每行少一个字，累积到整章差若干页 |
| `textIndent: 2em` | 不参与 | 每段首行少 2 字，短段章节偏差更大 |
| 段落间距 `1.15em` | 按 `ceil(spacing/lineH)` = **整行**建模 | 实际只占 0.59 行，整章最多虚增 40% 行数 |
| 内嵌图片（`reader-paragraph-image`，高度随图变化） | 只认 markdown `![...](url)` | 图多的章（漫画/插图源）完全失真 |
| 两端对齐的标点挤压、`text-wrap: pretty`、禁则 | 自写一套行首禁则 | 与浏览器断行结果不一致 |

这些不是"实现不完整"，而是**流派问题**：不测量就不可能等于测量。唯一能修的办法是把真实字体度量喂进去
（等于重新实现一个排版引擎），成本远超收益。

## 5. 与"改字号保持位置"的关系（常见反驳）

有人会问：`paginationCache` 不是用来做"改字号后位置保持"的吗？现状已用另一条路解决了：
`usePaginationMeasurement.ts:139-158` 用**语义位置**（章节 + 字符偏移 + 内容 checksum）恢复，
不依赖任何分页缓存；缓存只会在排版参数变化时整体失效，本来就救不了"改字号"这一场景。

## 6. 本轮限制（如实声明）

- **数学引擎的端到端准确率没跑成**：本机 shell 执行器在跑完 DOM 基准后卡死（`echo hi` 也超时），
  `tsx` / `esbuild` 两次尝试都无输出。§4 是静态审查结论，不是"同文本比对页数"的实测数字。
  这**不影响结论**：即使数学引擎准确率满分，它省下的也只有 1–5 ms（§3）。
- DOM 基准是**合成页面**复刻生产 CSS，不是真应用内测；真机若有字距/图片混排，成本只会更高，
  但也只是毫秒级——方向不变。
- 未删除任何代码。删除动作按 `AGENTS.md` §7 纪律另起一刀，并须跑
  `npm --prefix product/web test` + `npm run check` 后单独提交。
