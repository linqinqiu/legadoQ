可直接沿用的只有：**§11 的八条决策原则**、**§4.1 的兼容性口径**、**§5 的安全模型**。
需要重写的是：分层表、基线数字、待办顺序。

## 3. 按当前仓库重排的待办

> 以下是**依据当前代码**重排的，不是报告的 §10。

### 已完成，勿再立项

- [x] `rules` → `Database` 宽句柄收口（`port/PortBundle`）
- [x] `rules → data/source/http` 横穿清零（基线 `emptySet`）
- [x] `SourceUrlProbe` 入库并断环
- [x] 日记门面下沉 `port/Logging.kt`

### 真正还开着的

1. **`engine → infra` 剩余 4 条**（`source/WebViewProxy.kt` ×2、`rules/RuleRunner.kt`、`source/ExternalBrowserLogin.kt`）。
   其中 2 条只是"顺手拿了出站闸门 `NetworkSecurity`"，2 条是 Cookie 域名的纯安全判定。
   清法测试注释已写明：能力类下沉 `port/`，纯判定搬进 engine。**这条报告完全没有。**
2. **4 对包间 2-环**，`data<->source` 是唯一跨层真环，优先级最高。
3. **`docs/STATUS.md` 仍是 0.2.14 的数字**（它自己已加过期警告），要么刷新、要么降级为历史文档。
4. **工作树不干净**：11 个 M + 约 18 个未跟踪文件，其中根目录堆了 9 个未跟踪 `.md`
   （`SUMMARY.md`、`OPTIMIZATION-*.md`、`PROJECT-STRUCTURE.md` 等），与仓库既有的 `docs/` 治理约定冲突。
5. **AI 工具数量没有被断言钉住**：报告说 57 条，当前**实测仍是 57**（`BuiltinTools.kt` 55 处
   `ToolMeta(` + 运行时 `tool.search`/`tool.call`），但 `ApiCatalog.test.ts` 只钉**端点**条数
   （161），不钉工具条数。要沿用"文档里写数量"的做法，应补一条对 `BuiltinTools.all().size` 的绝对计数断言 ——
   这正是报告 P3 结论想要的形态（`AGENTS.md` 已写明"全量条数不在这里写，权威值只有测试里那一条断言"）。

## 4. 使用建议

1. **不要**把这份报告当作施工清单直接执行 P1 —— 那一节已经完成。
2. 把 §11 的八条原则保留为长期纪律；把 §3.1 分层表替换成 `product/docs/restructure/backend-layering.md`
   的现行版本。
3. 任何"基线数字"引用前先跑一遍：
   ```bash
   ./gradlew :app:test --tests "*ArchitectureBoundaryTest"
   ```
   该测试的断言是**相等**，基线里的每一条都必须与实测完全一致，因此它本身就是最可靠的事实源。
4. 规模数字一律以 `product/docs/restructure/facts.md` 为准 —— 该文件要求带命令、带时间戳。
