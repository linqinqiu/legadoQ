# 阶段 3.5 剩余两点评估：WebViewProxy 与 EdgeTtsService

> 日期：2026-11-22 ｜ 承接 [`研究-阶段3.5出站收口-2026-11-22.md`](研究-阶段3.5出站收口-2026-11-22.md)
> 性质：**评估，不改代码**。上一份给的是逐点判定，这一份回答"到底能不能迁、迁了会坏什么、判据是什么"。

---

## 0. 结论

| 点 | 能不能迁 | 关键前提 | 迁移后 G3 |
|---|---|---|---|
| `WebViewProxy` | **能，建议先做** | 补一条真实登录回归；接受 PinnedProxy 的"每请求一条连接" | 2 → 1 |
| `EdgeTtsService` 的 **WSS** | **能** | 先给 `GuardedHttpClient` 补 `newWebSocketBuilder()`；只支持 `wss://` | 不变（同文件还有自定义 TTS） |
| `EdgeTtsService` 的**自定义 TTS** | **不能直接套 `NetworkSecurity`** | 现有文档明确"有意放行内网"；需要先定策略 | 见 §2.3 |

一句话：**WebViewProxy 可以直接迁；EdgeTts 不是"一个文件"的迁移，而是"两条链路 + 一个产品决策"**。

---

## 1. WebViewProxy：可迁，收益是 DNS 固定而不是"从无到有"

### 1.1 现状（已读源码）

- 裸 client：`source/WebViewProxy.kt:60`，10s 连接超时、`Redirect.NEVER`。
- 所有请求走 `requestFollowing`（`:257`）→ `send`（`:295`）；`send` 用 `BodyHandlers.ofByteArray`，8MB 上限在 `:322`。
- **SSRF 检查已经存在**：`validateTarget`（`:361`）对入口和每一跳重定向都调 `NetworkSecurity.resolveAndValidateSafeHttpTarget`；`requestFollowing` 在 3xx 分支里逐跳重验（`:277-290`）。
- gzip 手动解压（`:498`），Cookie 从响应 `Set-Cookie` 吸收，重定向按浏览器语义把 302/303 的 POST 降级成 GET。

所以它今天**不是**一个"裸 client 直连内网"的漏洞；迁移的增量收益只有两条：
1. **连接级 IP 固定**：`validateTarget` 解析一次、JDK 发送前再解析一次，中间仍有 DNS TOCTOU 窗口；`PinnedProxy` 关掉它。
2. **出站收口统一**：以后审计只看一个签发点。

### 1.2 迁移后的行为差异

| 维度 | 现在 | 迁到 `NetworkSecurity.newHttpClient` 后 |
|---|---|---|
| 请求头/方法/body | 原样 | 原样（`GuardedHttpClient` 只代理 `send`） |
| Cookie / Set-Cookie | 原样 | 原样（PinnedProxy 转发除逐跳头外的全部头） |
| gzip | 手动解 | 不变（代理不改 `Content-Encoding`） |
| 重定向 | 手动逐跳 | 不变（仍 `NEVER`） |
| 错误文案 | "无法访问目标站点：…" | 代理建连失败会变成"连不上 host:port（出站代理建连失败）"，`WebViewProxy` 仍包成 `WebViewException` |
| 连接复用 | JDK 连接池 | **PinnedProxy 每请求一条到源站的连接，响应 `Connection: close`** |

### 1.3 风险（按严重度）

1. **性能未测**：登录页通常带几十个子资源，每个都要经代理新建一条 TCP/TLS。功能上不会错，但首屏可能变慢；本环境没有可用的真实登录页做对比。
2. **测试覆盖是空的**：`WebViewProxyTest` 只测 `rewriteHtml`/域名归桶等纯函数；`WebViewProxyRouteTest` 只验证路由方法，不发出站请求。迁移后"代理链路真的能取回页面"没有任何自动判据。
3. **错误分类**：`GuardedHttpClient` 把代理建连失败还原成 `UnreachableTargetException`，`WebViewProxy` 的 `catch (Exception)` 会把它包成"无法访问目标站点"，用户能看懂，但日志里少了"是被闸门拒还是网络不通"的区分。

### 1.4 建议的迁移切片

- 给 `WebViewProxy` 加一个 `internal` 构造参数（默认 `NetworkSecurity.newHttpClient(...)`），只用于测试注入假 client；生产路径不变。
- 判据：
  - `validateTarget` 拒绝 `127.0.0.1` / `169.254.169.254` / 私网（现有行为，补一条直接单测）。
  - 用注入的假 `HttpClient` 验证 `send` 的请求头（UA/Referer/Cookie/Accept-Encoding）与 8MB 上限不变。
  - `WebViewProxyRouteTest` + `WebViewProxyTest` 全绿。
  - **人工**：本机真浏览器登录一次，确认页面能打开、Cookie 能吸回（这是唯一能覆盖 PinnedProxy 真实链路的判据）。
- 完成后 G3 基线 2 → 1。

## 2. EdgeTtsService：一个 client 服务两条完全不同的链路

### 2.1 现状

`tts/EdgeTtsService.kt:28` 的 client 同时用于：

1. **Edge TTS 的 WSS**：`newWebSocketBuilder()` 在 `:173`、`:293`，目标是固定域名 `wss://speech.platform.bing.com/...`。
2. **自定义 TTS 的 HTTP**：`client.send` 在 `:361`、`:370`（`followCustomTtsRedirects`），URL 由用户在朗读设置里填，支持 GET/POST、自定义头、逐跳重定向、流式 `ofInputStream`。

关键政策（不是实现细节）：`product/docs/ARCHITECTURE.md:617` 写明「自定义 TTS **有意**放行内网（常见用法就是指向本机合成服务）」。`assertSafeTtsTarget`（`:342`）只校验协议与主机非空，**不拦内网**。

### 2.2 WSS 可以迁：JDK 17 的 WebSocket 确实走 ProxySelector

不是猜的，JDK 17 源码（`lib/src.zip`）里：

- `jdk/internal/net/http/websocket/BuilderImpl` 持有 `Optional<ProxySelector>`，`buildAsync` 把它带进 `OpeningHandshake`；
- `OpeningHandshake` 里 `Proxy proxy = proxyFor(b.getProxySelector(), b.getUri())`，随后 `request.setProxy(proxy)`。

所以 `wss://` 会先向 `PinnedProxy` 发 `CONNECT host:443`，之后是盲 TLS 隧道，握手头（`Upgrade`/`Sec-WebSocket-*`）在隧道里原样到达源站。**wss 可迁**。

但 `ws://`（明文）不行：PinnedProxy 的明文转发把 `upgrade` 与 `connection` 当逐跳头剥掉（`ops/PinnedProxy.kt:253`），WebSocket 握手会失败。Edge TTS 只用 `wss://`，所以不受影响；如果以后支持明文 ws，需要单独给代理开一条"保留 Upgrade"的路径。

### 2.3 自定义 TTS：三条路，必须先选政策

| 方案 | 做法 | 结果 | 代价 |
|---|---|---|---|
| **A. 专用签发点**（推荐，若目标是 G3=0） | 新建 `ops/CustomTtsClient`：允许回环 + RFC1918/ULA，**封掉 169.254/16、fe80::/10、CGNAT、组播/保留段** | 本机与局域网 TTS 都能用；云元数据端点被堵；G3 可到 0 | 多一个显式签发点；要写策略单测；若要 DNS 固定还得给 PinnedProxy 加"允许私网"模式 |
| **B. 保持现状** | EdgeTtsService 继续持有裸 client，G3 留 1 条基线并写明原因 | 行为零变化 | G3 永远差最后一条；与"出站收口"的目标不一致 |
| **C. 直接用 `NetworkSecurity(allowLoopback=true)`** | 只放 127/8 与 ::1 | 本机 TTS 能用，**局域网 TTS 断掉** | 与 `ARCHITECTURE.md:617` 的承诺冲突，属于产品行为变更 |

**不建议 C**：文档已经把"放行内网"写成有意的能力，静默收紧会让"我把 TTS 放在 NAS 上"这类用户直接坏掉。

方案 A 的策略边界建议（需要负责人确认）：
- 放行：`127.0.0.0/8`、`::1`、`10/8`、`172.16/12`、`192.168/16`、`fc00::/7`；
- 拒绝：`169.254.0.0/16`（含 `169.254.169.254`）、`fe80::/10`、`100.64/10`、`0.0.0.0`、组播与保留段。
- 逐跳重定向校验保留（`followCustomTtsRedirects` 现有逻辑不动）。

### 2.4 流式风险

自定义 TTS 的流式路径用 `BodyHandlers.ofInputStream()`（`:484`）。如果走 PinnedProxy 的明文转发，代理是"每请求一条连接 + `Connection: close` + 60s 单次读超时"（`PinnedProxy.kt:248`）。短音频没问题；长时间不产字节的合成服务会先撞 60s。**未实测**，迁移前应拿一个真实的本地/局域网 TTS 跑一次流式。

---

## 3. 建议顺序

1. **先迁 WebViewProxy**（G3 2→1）：独立、收益明确、可回滚。
2. **给 `GuardedHttpClient` 补 WebSocket**：`newWebSocketBuilder()` 包装，`buildAsync` 前把 `ws/wss` 映射成 `http/https` 过 `guard`；失败要返回 `CompletableFuture.failedFuture` 而不是同步抛。补单测：`wss` 公网放行、`ws://127.0.0.1` 被拒（或明确报"明文 ws 不支持"）。
3. **Edge TTS WSS 改用受控 client**：此时自定义 TTS 仍是裸 client，G3 不变。
4. **最后定自定义 TTS 政策**：选 A 则新建 `CustomTtsClient` 并把 G3 打到 0；选 B 则把 EdgeTtsService 作为唯一显式例外写进门禁注释。

## 4. 未验证

- 自定义 TTS 流式经 PinnedProxy 的长连接行为，未测。
- 本机/局域网真实 TTS 服务，本环境没有可用的。
