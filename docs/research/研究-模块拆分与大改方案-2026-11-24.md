# 研究：模块拆分与大改方案（2026-11-24）

> 承接：`docs/engineering/audit/ROADMAP.md` 第四阶段「架构与契约治理」（截至本日**完全未动工**）。
> 触发：用户要求「大方向改、可动根基」，目标是让**框架、源码、模块更好编辑**。
> 性质：只读依赖分析 + 目标设计。**本文所有数字与依赖关系为本日实测**，非文档抄录。

---

## 0. 一句话结论

**本仓三大巨型文件（`JsSandbox` 2100 / `RuleRunner` 1858 / `JavaPackages` 1415 行）不是问题本身，问题是没有物理边界。**
包级隔离不阻止 import —— 这就是为什么 `http/` 能有 81 处直接 `import io.legado.data.*`。
上游 Legado 同类功能只用 ~2,600 行（我们 5,373 行），且把规则引擎切成 11 个职责单一的小文件。

**第一刀应该是 Gradle module 拆分，不是继续拆文件**：让编译器强制边界，后续所有拆分都变容易。

## 2. 上游 Legado 的对照（证据链）

来源：`star2005/legado` master（`gedoor/legado` 已于 2026-06 清空，`CCSNE/legado` contents 接口 404）。

| 维度 | 上游 | 本仓 | 倍数 |
|---|---|---|---|
| 规则求值 | `AnalyzeRule.kt` 849 行 | `RuleRunner.kt` 1,858 行 | 2.2× |
| JS 宿主 API | `JsExtensions.kt` 888 行 / 75 方法 | `JavaPackages.kt` 1,415 行 | 1.6× |
| JS 沙箱 | **无独立类**，`evalJS()` 内联 | `JsSandbox.kt` 2,100 行 | — |
| 合计 | ~2,600 行 | 5,373 行 | **2.1×** |

**上游 11 个小文件（`app/src/main/java/io/legado/app/model/analyzeRule/`）：**

| 文件 | 职责 |
|---|---|
| `RuleAnalyzer.kt` 14KB | **只做规则字符串切分**（`//` `@` `&&` `\|\|` `%%` 栈式 parser），零 IO |
| `AnalyzeUrl.kt` 26KB | 网络 + URL 模板 + JS 请求体 |
| `AnalyzeByJSoup/XPath/JSonPath/Regex.kt` | **四个同构选择器后端**，接口一致 |
| `AnalyzeRule.kt` 29KB | 求值门面，`: JsExtensions` |
| `RuleData.kt` / `RuleDataInterface.kt` | 纯数据载体 |

**上游三处不可照抄：**

1. **无 DI** —— `val appDb by lazy {}` + `splitties.appCtx` 静态 Context。与本仓「全局 43 个 object + 18 处可变状态」同根，Ktor 多线程下是竞态。
2. **模块划分极弱** —— 仅 3 个 module（`:app` `:modules:book` `:modules:rhino1.7.3`），**规则引擎仍在 `:app` 里靠包隔离**。这正是巨型文件的土壤。
3. **`bindings["java"] = this` 全实例暴露** —— 任何方法都能被书源规则调用，含副作用方法。本地单机能忍，不是好设计。

## 3. 目标模块结构

```
product/app/                    ← 现状：单一 :app（源码 30,443 行 / 133 文件）
```

目标：

```
:core:model    ← 纯 DTO，零内部依赖（现状 model/ 已满足）
:core:rules    ← 规则引擎 + JS 沙箱（不依赖 Ktor / JDBC / okhttp）
:core:ops      ← NetworkSecurity / Metrics（零内部依赖，可整份下沉）
:data          ← DAO / Repository（依赖 :core:rules 做 SourceRepository 编排）
:server        ← Ktor 路由 + 插件装配
:app           ← 仅 DesktopLauncher / main 装配
```

**验收判据（可机器检查）：**

1. `:core:rules` 编译产物**不允许**出现 `io.ktor.*` / `java.sql.*` / `okhttp3.*` 的 import（编译期即失败，不靠人自觉）。
2. `:core:model` 零内部依赖（现状已达成）。
3. `http/ → data/` 直接 import 从 **81 处**单调下降到目标 0（继承 `tools/verify/depth-check.mjs` 的「基线只许单调缩小」纪律）。

## 4. 迁移步骤（每步独立可编译、独立可回滚）

| 步 | 动作 | 风险 | 判据 |
|---|---|---|---|
| **S1** | 新建 `:core:model`，把 `model/` 整体迁入 | 低（零依赖） | 编译通过 + 全量 1,059 项 |
| **S2** | 新建 `:core:ops`，把 `ops/NetworkSecurity.kt` + `ops/Metrics.kt` 迁入 | 低（零内部依赖） | 同上 |
| **S3** | 断 `content → rules`：把 `ContentProcessor` 的 `JsSandbox` 参数改成 `port` 接口 | 中（需改签名与调用点） | 同上 |
| **S4** | 新建 `:core:rules`，迁 `rules/` + `port/` + 依赖的 `content/` | 中 | 编译通过 + **GoldenRuleTest 逐字节一致** |
| **S5** | 新建 `:data`，迁 `data/` | 中 | 全量后端测试 |
| **S6** | 新建 `:server`，迁 `http/`，并开始消 `http → data` 直连 | 高（81 处） | 边界判据单调下降 |

**先做 S1+S2（今天可完成）**：`model/` 与 `ops/NetworkSecurity`+`Metrics` 都是零内部依赖，是唯一零风险的起点，且直接解掉 `rules → ops` 那两个缺口。

## 5. 与上游「利于编辑」的三样资产

排序按「边际收益 / 改动成本」：

1. **`RuleAnalyzer` 式纯函数切分** — 上游把规则切分（`//` `@` `&&` `\|\|` `%%`）独立成零 IO 文件，可穷举单测。本仓 `RuleRunner` 里这段最该先抽。
2. **单一 `JsJavaBridge` 接口** — 上游 75 个 `java.*` 方法收在 `interface JsExtensions`（888 行），`AnalyzeRule` 只花 12 行桥接。本仓 `JavaPackages`(1415) 应收敛成单一接口 + 白名单 + 按域拆分（string/crypto/time/network）。
3. **书源调试器升级** — 上游有 `RuleComplete`（规则自动补全，纯正则表，可直接移植）+ 原始 HTML 落盘复用 + 按 sourceUrl 分桶的 `Debug.log`。本仓调试器现仅 131 行，按 5 阶段流式推送。

## 6. 未验证 / 风险

- **S4 的 `GoldenRuleTest`** 是 `rules/` 迁模块后唯一的行为安全网，且**本机真实库为空**（`product/data/legado.sqlite` 4KB / 0 条源），无法做真实源抽样回归。
- **S6 的 81 处** `http → data` 直连需要逐域消化，不是一次能推平的（审计原话：书架域起步）。
- 模块拆分会影响桌面打包脚本（`scripts/package-desktop.mjs` 与 Gradle 产物路径），需同步核对。

## 8. 实施记录（2026-11-24，S1 `:core:model` 已完成）

**改动**

- `model/` 10 个文件从 `app/src/main/kotlin/io/legado/model` 迁到 `product/core/model/src/main/kotlin/io/legado/model`（独立 Gradle module）。
- `settings.gradle` 加 `include ':core:model'`；`app/build.gradle` 加 `api project(':core:model')`。
- `core/model/build.gradle`：`kotlin("jvm")` + `kotlin("plugin.serialization")`，仅依赖 `kotlinx-serialization-core:1.7.3`（**编译器现在强制 model 层零框架依赖**）。
- 9 处跨模块 smart cast 修复（K2 不再对另一 module 的 public 属性做 smart cast）：`BookCacheService`/`ShelfDao`/`SourceRepository`/`ReplaceRulesRoutes`/`TocRulesRoutes`/`RuleLogin`——统一模式是引入局部 `val` 捕获后判空，无行为变化。
- 前端 3 个测试引用了后端 model 源文件路径（`VersionTracks`/`SearchJump`/`PagingGate`），同步改为 `core/model` 新路径。

**实测**

- `:app:compileKotlin` 通过（6m47s）。
- 后端全量：`--max-workers=2` 下 **149 suite / 1,059 项 / 0 失败 / 0 跳过**，与迁移前完全一致。注：不加 `--max-workers=2` 会出现约 20 个 `UncompletedCoroutinesError`（worker 争用，单跑即绿，非回归，此前基线也有此现象）。
- 前端全量：**1,125 项 / 0 失败**；`tsc -b` 通过。
- 三门禁全过：version:check / docs:api-check（145 条 18 组一致）/ changelog:check。

**已知取舍**

- model 模块用 `kotlin("plugin.serialization")` 而非仅 core——`@Serializable` 注解需要 plugin 处理，与 app 的 Kotlin 版本对齐（2.4.10）。
- `ArchitectureBoundaryTest` 的「model 包不得 import 其他领域包」判据仍然全绿——迁移只是物理位置变化，包名未动，边界判据无需改基线。
