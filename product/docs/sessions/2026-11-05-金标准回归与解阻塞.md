# 金标准回归落地与编译解阻塞（0.2.17 / build 14 → 17）

## 背景

- `RuleRunner` 2405 行、21 个公开方法，跨搜索/详情/目录/正文/登录/JS 六条链路；被 32 个主源码文件、43 个测试文件引用。
- `RuleDispatcher` 与 4 个 processor 是占位契约，`RuleRunner` 零引用——拆分的入口有了，但没有等价性判据。
- 现有 952 项测试里没有「固定输入 → 固定输出」的规则语料；「搜索少一条结果」「目录少一章」这类退化看不出来。
- 工作树被另一个 agent 的未提交改动阻塞：`JsGuard.kt` 编译红持续 43 分钟（22:21 → 23:04）。

## 做了什么

### 1. 解阻塞（一行）

`JsGuard.kt:30` 的 `BoundedContext` 引用了 `DEFAULT_TIMEOUT_MS`，而该常量定义在 `object BoundedJs` 内，作用域不可见。改为 `BoundedJs.DEFAULT_TIMEOUT_MS`。

这是对另一个 agent 半成品的**最小修复**，没有改它的语义（超时仍由调用方传入，默认 30s）。

### 2. 金标准测试骨架

| case | 覆盖 | 断言 |
|---|---|---|
| `search-css` | CSS 列表定位、`@text`/`@href` 字段提取 | 条数、顺序、书名/作者/详情地址三元组全等 |

### 3. SearchFlow 接入搜索链路

`RuleRunner.searchWithReason` 现在只有一行：`searchFlow.search(sourceJson, keyword)`。流程搬进 `SearchFlow`，原语留在 `RuleRunner`。

依赖面实测：原方法直接用到 12 个私有原语（`sourceContext`、`withSourceContext`、`applyUrlScripts`、`splitUrlOptions`、`mergeOptions`、`parseSourceHeaders`、`renderUrl`、`fetchUrl`、`bookItems`、`responseClue`、`sourceType`、`JsSourceRunner`）。逐个传进去会让 Host 膨胀到 12 个方法——那说明切分点不在这层。所以收敛成 **6 个粗粒度步骤**：

| Host 方法 | 对应流程 |
|---|---|
| `isJsSource` | 分支判断 |
| `jsSourceSearch` | JS 书源分支 |
| `inSourceContext` | 整段在书源上下文内执行 |
| `fetchSearchPage` | URL 脚本 → 选项 → 渲染 → 抓取 |
| `parseSearchItems` | 列表解析（将来接 Dispatcher 就换这里） |
| `describeResponse` / `sourceType` | 响应线索 / 书源类型 |

`SearchFlow` 负责的是**顺序与错误文案**（缺 `searchUrl` / `bookSourceUrl` / `ruleSearch` 报哪句），不碰 HTML/JSON 解析、不拼 URL、不发请求。

判据：编译通过、`GoldenRuleTest` 4/4、`ArchitectureBoundaryTest` 6/6。

### 7. 阅读器全崩修复 + 冒烟判据（0.2.17 / build 18，2026-11-06 10:44）

**现象（运行态实测，不是推测）**：Chrome 打开 `http://127.0.0.1:1234` → 书架 → 点任意一本书：

```
阅读器崩了
useTts 必须在 <ReaderTtsManager> 内部使用
```

控制台堆栈落在 `index-WpCwxxOG.js`（build 16 的包）。

**根因**：11-04 的 `d8f683d`（“ReaderScreen 拆出 TTS”）把 Provider 放进了 `ReaderTtsManager`，
而 `ReaderScreen:997` 仍然 `useTts()` —— 父组件读不到子组件提供的 Context。React 里这不是“可能”，
是必抛。`tsc` 通过、当时 118 份前端判据全绿，因为**没有一份渲染过阅读器**；这正是“编译通过 +
判据全绿 + 核心功能全崩”同时成立的那种失效。

**修复（所有权归并）**：

| 位置 | 之前 | 现在 |
|---|---|---|
| `ReaderScreen` | `useTts()` 消费 | `useReaderTts({...})` 调一次 + `<TtsContext.Provider>` 下发 |
| `ReaderTtsManager` | 调 hook + 提供 Context + 另存一份 `showTtsSettings` / `offlineTtsConfirmOpen` | 只 `useTts()` 消费；重复的两份状态删掉（hook 里本来就有） |
| `TtsContextValue` | hook 返回值 + `remainingSeconds` | 就是 hook 返回值；`remainingSeconds` 归朗读条自己算 |

**新增判据** `web/test/ReaderScreenSmoke.test.ts`：① `renderToStaticMarkup` 必须画出章名 / 书名 /
五个入口，且不含兜底文案；② 结构断言：hook 只能有一个实例、Provider 必须在阅读器这一层、
浮层不许再提供 Context。

## 环境坑（下次直接照做）

本机提交内存不足（Windows `errno 1455`），Gradle daemon、Kotlin daemon、测试 JVM 都会在启动阶段崩，表现是：

- `Gradle Test Executor finished with non-zero exit value 1`，但没有测试 XML；
- `hs_err_pid*.log` 里写 `insufficient memory ... Chunk::new`。

可用的跑法：

```bash
# 1) 停掉服务（Xmx1g）腾提交内存
npm run stop

# 2) 用低内存 + 关 jacoco 的 init script 跑单类测试
cd product
./gradlew :app:test --tests "*GoldenRuleTest" \
  -I D:/AI-Agent/data/tmp/limit-test.gradle -x jacocoTestReport \
  --no-daemon -Dorg.gradle.jvmargs="-Xmx512m -XX:MaxMetaspaceSize=384m -XX:ReservedCodeCacheSize=128m -XX:+UseSerialGC" \
  -Dkotlin.compiler.execution.strategy=in-process

# 3) 跑完把服务拉起来
npm start
```

`limit-test.gradle` 把 Test 堆降到 448m、关掉 jacoco agent。这是环境适配，不是仓库配置变更。
