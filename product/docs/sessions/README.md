# 工程日志（sessions）

这里放「为什么这样做、量到了什么、哪条判据盯着它」。`CHANGELOG.md` 只写用户能看见的变化，
两者分工写在它的开头：把工程日志写进更新日志，使用者就找不到「这版对我有什么变化」。

## 命名与内容

一份文件对应一次有实质决策的工作轮次，文件名 `YYYY-MM-DD-<主题>.md`。
每份按下面的骨架写，没有的一节直接删掉，不要留空节：

```markdown
# <主题>

## 背景与目标
这次要解决什么、为什么是现在。

## 核验发现
动手前量到了什么。与既有结论不符的要显式写出来 —— 那正是最有价值的部分。

## 决策与取舍
选了哪条路、放弃了什么、为什么。写「不做什么」比写「做了什么」更能防止后人重复纠结。

## 落地改动
文件级的清单，每条说清改前改后。

## 验证
跑了什么、结果如何。失败与失败原因同样要记。

## 遗留
没做的、建议另开提交的、需要他人决策的。
```

## 与其它文档的关系

| 文档 | 管什么 |
| --- | --- |
| `CHANGELOG.md` | 用户可见的变化 |
| `docs/sessions/`（本目录） | 工程决策、量测数据、踩坑 |
| `AGENTS.md` | 长期有效的部落知识与工作记忆表 |
| `docs/*.md` | 面向使用者/贡献者的现行说明 |

判据的**现行口径**永远以 `web/test/` 与 `tools/verify/` 的实现为准；这里记的是当时为什么那样定。
