# 规则引擎扩展点接入（0.2.34 / build 47）

## 背景

`docs/STATUS.md` 的「已知缺口」第一项：`RuleProcessor` / `RuleContext` / `RuleDispatcher` 只是契约。
`RuleRunner` 的构造函数里有个 `ruleDispatcher` 参数，注释写着「缺省时按原有内置逻辑走（向后兼容）」——
**但那个参数从来没被读过一行**，`processor/` 下四个实现全是「尚未实现（阶段 2 占位）」。
于是新写一种解析方式可以编译、可以单测，规则求值时永远走不到它：扩展点是装饰。

`RuleRunner` 2464 行、`RuleValue` 747 行，跨搜索/详情/目录/正文/登录/JS 六条链路。原迁移方案
（`docs/rule-processor-migration-plan.md` §3 P1–P7）要求先把 Jsoup / Rhino / JSONPath 的解释逻辑
整体搬进处理器 —— 那是一次带金标准语料的独立重构，一步走错的表现是「某个源少一条结果」。

这一轮换了个更小的做法：**先问处理器，没人认领再走内联**。

## 做了什么

| 位置 | 改动 |
|---|---|
| `NodeValue.value(rule)` | 求值前 `dispatcher.claim(rule)`；认领了就由处理器给值，**认领即拥有** |
| `RuleRunner.nodes(body, rule)` | 列表规则先问 `claimNodeRule`（只问声明了 `producesNodes` 的） |
| `RuleRunner.dispatcher` | 公开可注册；构造函数里的 `ruleDispatcher` 参数改成真的会被读的 `dispatcher` |
| `RuleRuntime`（internal） | 调度器 + 日志出口，随每个 `NodeValue` 往下传（子节点、`at()`、内建重建的文档都带） |
| `RuleInput.evaluateBuiltin` | 处理器可以「先按老规则取个值再加工」，走内联、不经过扩展点（不会自递归） |
| `RuleResult` | 单值填 `text`，列表填 `nodes`（字段按 JSONPath 取） |
| `processor/` 包 | 删掉四个「尚未实现」的占位类；`demo/` 两个示例改成新契约并真的能跑 |

### 四个刻意的决定

1. **内建四种类型不搬进处理器。** 扩展点的价值是「能加新类型」，不是「必须把老类型重写一遍」。
   把 CSS/XPath/JSONPath/JS 搬进处理器再让处理器调回同一批底层件，收益是目录更整齐，
   代价是任何一处搬错都只能靠金标准语料发现。这一轮不做。
2. **认领即拥有，不落回内联。** 否则自定义类型会被内建当成 CSS 选择器，报一句看不懂的
   `SelectorParseException`，而且「处理器返回空」与「处理器没接上」在行为上无法区分。
3. **`producesNodes` 显式声明。** 列表规则与单值规则的返回形状完全不同；一个 `canHandle` 写得很宽
   的值型处理器如果能接管列表规则，症状就是「整源 0 条」——沉默故障。列表只问声明过的那批。
4. **不用线程变量传调度器。** 解析会在同一线程里层层嵌套，线程变量要层层保存/恢复，
   漏一层就是某条路径上扩展点静默失效。节点本来就随规则链传递，挂在它上面最不容易漏。

### 顺带修的一个用户可见 bug

`@css:` 前缀在值规则里早就认（`RuleValue.valuePlain` 的 `removePrefix("@css:")`），列表规则这一侧不认：
`@css:.librarylist li` 被整串喂给选择器方言，抛异常、整源 0 条。现在 `nodes()` 也剥这个前缀。
这条是这一版唯一写进 CHANGELOG 的（其余是开发者可见的接口改动）。

## 判据

`app/src/test/kotlin/io/legado/RuleProcessorTest.kt`（7 项）：

| 判据 | 证明什么 |
|---|---|
| 值级扩展点 | 注册前后同一个源，作者从「空」变成「《天蚕土豆》」—— 是处理器给的 |
| 列表级扩展点 | 声明 `producesNodes` 的处理器给出 2 个条目，字段用 `$.title` 取到 |
| 值型处理器不接管列表 | `canHandle` 认所有规则的处理器注册后，条目数仍是 2 |
| 认领即拥有 | 认领一条**内建本来取得到值**的规则并返回空 → 作者为空（没落回内建） |
| 处理器抛异常 | `execute` 抛 / `canHandle` 抛，都只影响那一条规则，其余字段与条目照常 |
| `@css:` 两侧一致 | 列表规则写 `@css:div.result` 与 `div.result` 等价 |
| 注册/覆盖/摘除 | 同 type 覆盖不叠加，`unregister` 生效 |

等价性：`GoldenRuleTest`（6 个离线金标准语料）+ 后端全量 1003 项 —— 内建链路一个字节都没动，
这些必须先绿；它们是「没改坏」的唯一证据。

## 没做的

- **P4–P7 的迁移**（把内联实现搬进处理器、最后删掉 `RuleRunner` 里的内联分支）仍是可选项，
  动机从「让扩展点生效」变成「把 2464 行拆薄」。方案留在 `docs/rule-processor-migration-plan.md`。
- **处理器拿不到书源上下文**：`RuleContext` 只有 `log`。取值发生在解析热路径上，同步接口；
  需要联网/长耗时的能力应该放在宿主层，而不是塞进一条字段规则。
