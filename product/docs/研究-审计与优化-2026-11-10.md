## 1. 已修（每条都能被一条判据拦住）

### 1.1 脚本缓存从库里回填时丢掉 deadline（后端 · P0）

- **证据**：`rules/ScriptCache.kt:39` 的 `putMemory` 恒写 `Entry(value, 0)`（0 = 永不过期），
  而 `:62` 的"库读回填"正好调它；`data/ScriptCacheDao.kt` 读了 `deadline` 却只返回 `value`。
- **影响**：任何被读两次的键（token / 图片样式 / API 结果）在进程内从此不再过期 ——
  与 `ScriptCache.kt:15-17` 自称"内存层也照 deadline 判"正好相反。用户的体感是
  "源换了 token 但一直用旧的，重启服务才好"。
- **改法**：端口 `ScriptCacheStore` 增加 `getScriptCacheEntry`（`port/StorePorts.kt`），
  DAO 增加同名扩展（`data/ScriptCacheDao.kt`），`ScriptCache.get` 回填改走
  `putMemoryEntry(..., deadline)`。`putMemory` 仍是"脚本的 `cache.putMemory`"（不设过期）。
- **判据**：`ScriptCacheTtlTest` —— `put(saveTime=1)` → 清内存层（模拟重启）→ 读回填 →
  等 1.1 秒再读必须是 `null`。

### 1.2 响应体超限被报成"参数非法"（后端 · P1）

- **证据**：`rules/ResponseBody.kt:108` 用 `require(...)`，抛的是 `IllegalArgumentException`；
  `RuleRunner.kt` 里随后那句 `bytes.size > MAX_BODY_BYTES` 永远为假（`readLimited` 已先抛），是死分支。
- **影响**：上游给了 2 MiB 以上的响应，用户看到的是 `400 invalid_request`，于是去改自己的书源。
- **改法**：改抛 `RuleExecutionException`；删掉死分支。
- **判据**：`ScriptCacheTtlTest` 第三条（断言异常类型是规则异常，消息里说明"上游太大"）。

### 1.3 AI 工具循环进循环前只裁一次上下文（后端 · P1）

- **证据**：`ai/Agent.kt` 进循环前 `trimToBudget(convo)` 一次；循环体每轮把工具结果
  （单条最多 `MAX_TOOL_DATA` 字符）追加进 convo，之后再没人复查。
- **影响**：多轮工具调用到第 3、4 轮就可能超过预算 → 上游回 `context too long`，
  表现是"同一段对话聊到一半突然 400"。
- **改法**：非流式与流式两条路径都在**每轮开头**复查（`if (round > 0) trimmed += trimToBudget(convo)`），
  `trimmed` 改成累加值，回报给界面的"已裁历史"仍是真数。
- **判据**：`AgentPromptContextTest`「工具循环每轮都复查上下文预算」（钉两条路径的接线位置；
  预算算法本身由同一文件原有的裁剪用例守）。

### 1.4 死代码 `getBatchBooks`（后端 · P2）

- **证据**：`data/BookshelfRepository.kt` 里只有定义处（全仓 `grep` 1 处），内部逐本
  `database.shelfBook(...)` = N 次查询。
- **改法**：删除。留着它，下一个人会当"批量接口"用，直接把读池打满。

### 1.5 前端统一超时 + AI 实测说清原因（前端 · P1）

- **证据**：`lib/performance.ts` 的 `fetchWithMetrics` 是裸 `fetch`，没有超时也没有取消；
  `features/ai/AiConnectionsModal.tsx` 的探测 `catch` 一律 `'fail'`，上游半开连接会让
  「实测中…」永远转圈，用户既不知道通不通、也拿不到能照着改的原因。
- **改法**：
  - `fetchWithMetrics(url, options, timeoutMs?)`：到点 `AbortController.abort()`，
    并把中止换成一句人话（`请求超时（N 秒没有响应）`）；调用方自己传了 `signal` 时不叠加控制器。
  - `lib/api/client.ts` 的 `request(path, init, { timeoutMs })` 透传；**默认不设上限** ——
    「书源体检」这类端点本来就要跑几十分钟，套一个通用上限等于把正常长任务掐死。
  - `api.agentChat(..., { timeoutMs: 20_000 })`：探测专用上限；失败原因进 `probeReason`，
    界面上显示「实测不可达（原因）」。
- **判据**：`PerformanceMonitor.test.ts` 两条（到点真 abort；调用方取消不被改写成超时）
  + `AiTaskModels.test.ts` 一条接线（上限、原因、文案三处都在）。

## 2. 能力：把 MD3 的「详尽阅读记录」落到界面（前端）

参考 `HapeLee/legado-with-MD3` 的「阅读记录：时间轴 + 章节维度统计」。

- **现状**：`plugins/reading-log/ReadingLogPage.tsx` 只有"按天时间轴"，顶部一行总时长。
- **本轮新增**（纯前端聚合，不加端点、不新增表 —— `chapterIndex` 本来就在每天每本的记录里）：
  - 汇总卡片：最近 30 天总时长 / 读过书的天数 / **连续阅读天数** / 平均每天；
  - 按书统计：每本书「读到第 N 章 · 读过几天 · 累计时长」，按累计时长降序；
  - 一句"共读了几本、读得最久的一天"。
- **口径**：连续天数从今天往回数；今天还没读就从昨天起算（早上打开不该显示"连续 0 天"抹掉昨晚），
  昨天也没读才是真的断了；日均按"读过书的天数"摊，不按 30 天摊。
- **判据**：`ReadingLog.test.ts` 新增 5 条（汇总 / 连续天数三种断法 / 空输入 / 按书聚合 / 接线）。
- **还能再进一步**：章节维度视图（按章聚合"读过哪些章"）、30/90/365 切换
  （后端 `days` 已夹取 1..365，前端窗口写死 30）。
