# 08 新架构初步方案（目标架构提案）

> 本册是**提案**，不是施工图。它的作用是让项目负责人在进入 Phase 1 之前，能对「往哪儿走」做出知情决策。
> 所有主张都对应 02–07 分册的具体证据；凡是"看起来更干净但成本不划算"的选项，也一并列出并说明为什么不建议。
> **本册不包含任何代码改动**，也不含时间表（时间表在 `09_MIGRATION_ROADMAP.md`）。

---

## 0. 结论先行

| 问题 | 我的回答 |
|---|---|
| 新架构形态 | **模块化单体（modular monolith）**，单进程、单用户、本地 SQLite。不做微服务、不做分布式 |
| 切分维度 | **按业务域纵向切包**（domain-first），每个域内部再分 api / domain / data 三层；**共享内核（kernel）单独成包** |
| 为什么不是现在这种横向分层 | 现在的 `http/ data/ rules/ ...` 横向分层**本身就是耦合来源**：`http/` 被迫既做协议又做编排（`03` §1），`data ↔ source` 形成真环（`03` §1） |
| 规则引擎定位 | **独立组件 + 依赖倒置**：`kernel/rules` 只依赖窄接口 `Fetch`，不 import 任何域、不碰数据库 |
| 数据访问 | 单一 `Db` 门面：只暴露 `read{} / write{} / transaction{}` 三种形态，**彻底删除手动 `autoCommit`**，并用静态判据守住 |
| API 契约 | **单一路由表 + 从代码派生目录 + 从 DTO 生成 TS 类型**（现任"手写目录 + 手写类型"已产生线上 400 与 30+ 漂移） |
| 前端 | 保持 React 19 + 自研 hash 路由（不放 router 库）；引入**阅读器状态机**、**Dialog 原语**、**设计令牌替代 6,757 行 CSS**、**生成式类型** |
| 兼容性 | 黄金样本（`rule-golden/**`）升级为**一等公民的兼容测试模块**，任何重建步骤先过它 |
| 风险基调 | **外科式重建**（strangler），不做推倒重来。理由见 `01` §8 |

### 1.1 依赖规则（要写成判据，不能只写在文档里）

| # | 规则 | 现状违反 | 判据形式 |
|---|---|---|---|
| R1 | `kernel/*` 不得 import 任何域（`source/` `reading/` …） | 现 `rules/RuleRunner.kt:46-48` ↔ `content/` 互依 | grep 门禁：`kernel/` 下出现 `import io.legado.<域>` 即红 |
| R2 | 只有 `data/` 层能拼 SQL，只有 `app/` + `kernel/fetch` 能 new HTTP 客户端 | 6 处裸客户端（`04` C5）；`http/ReadingRoutes.kt:12-22` 直调 11 个 DAO 顶层函数 | grep 门禁：`data/` 外出现 `executeQuery`/`prepareStatement`；`fetch/`、`app/` 外出现 `HttpClient.newBuilder` |
| R3 | 域之间只能通过对方 `api/` 包里的接口交互，不得直接 import 对方 `data/` | `data ↔ source` 真环（`03` §1-1） | grep 门禁：跨域 import 只允许 `<域>.api.*` |
| R4 | 任何地方不得手动设置 `autoCommit` | 12 处（`04` B4） | grep 门禁：`setAutoCommit` 只允许出现在 `kernel/db` |
| R5 | DTO 只允许在 `model/` | `LogEntry` 在 `ops/LogService.kt:178`（造成 `data ↔ ops` 环） | grep 门禁：其他包出现 `data class` 且带 `@Serializable` 即告警 |
| R6 | 新样式不得进全局 CSS 单文件 | `styles.css` 6,757 行 | 文件行数上限 + 增量检查 |

> **为什么把规则写成 grep 判据而不是文档**：这是本项目已经付过学费的教训——`GuardedHttpClient.kt:19` 的注释承诺无效（6 处违反），而 `ApiCatalog.test.ts` 的正则写窄了就让门禁绿着漏 8 条端点。**写在注释里的纪律等于没有纪律。**

## 2. 六个关键设计决策（含替代方案与成本）

### 决策 D-1：模块化单体，按域纵切

| 方案 | 收益 | 成本 | 建议 |
|---|---|---|---|
| **A. 按域纵切 + 共享内核（本提案）** | 修掉 `http/` 兼编排、`data↔source` 环；换协议不用重写业务；每域可独立测试 | 中：目录大挪动（参考已成功的 `d8f683d`/`b280cf0`/`695ab5d`，本项目做过 3 次，有判据兜底） | ✅ 推荐 |
| B. 保持现状横向分层，只加服务层 | 改动最小 | 环仍在；`http/` 会继续兼任编排（加服务层只是多一层转发，本项目已因"纯转发层"删过 `HttpClients`） | 次优 |
| C. 微服务 / 多进程 | 理论隔离 | 高：单用户本地应用，SQLite 无法共享，运维成本暴增 | ❌ 反对 |
| D. 纯六边形（ports & adapters 全套） | 结构最"标准" | 高：7 个域 × 4 个端口 ≈ 28 个接口文件，对单人维护是纯负担 | ❌ 过度设计 |

### 决策 D-2：规则引擎 = 独立组件 + 依赖倒置

- **契约**：`interface Fetch { suspend fun fetch(req: FetchRequest): FetchResponse }`，由 `kernel/fetch` 实现并注入。
- **禁止**：`rules` import `data`、`source`、`http`（今天是真发生的：`rules/RuleRunner.kt:1392-1394` 自动附 Cookie、`:1174-1437` 自己发请求）。
- **收益**（针对 `04` B1/B3）：外呼预算、闸门、限读、编码从此**只有一个下钩点**；8 份抓取实现折叠为 1 份。
- **代价**：`RuleRunner` 需要在每个调用点传 `Fetch`（构造注入一次即可），以及黄金样本必须逐字节保持一致。
- **替代方案**：把 HTTP 留在 `rules` 里，只在外面加计数器 —— **不可行**：书源 JS 可以自己发请求（`JavaPackages` 里的 okhttp 模拟），计数器必须落在 `kernel/fetch` 内部才不可绕过。

### 决策 D-3：数据访问单一门面 + 事务只有一种写法

```kotlin
// kernel/db 只暴露三种形态，其他任何写法都算违规
fun <T> read(block: (Connection) -> T): T
fun <T> write(block: (Connection) -> T): T          // 单写连接，内部 begin/commit
fun <T> transaction(block: (Connection) -> T): T    // 可嵌套（savepoint），不可与 write 混用
```

- **删除**：12 处手动 `autoCommit`；`write{}` 里嵌套 `write{}` 的隐患（`data/Database.kt:128` 记录的 0.2.35 事故）。
- **保留**：手写 SQL（不引入 ORM —— 见 D-7）、21 张表的 Schema 逐列对齐（`04` B5）。
- **代价**：一次跨 4 个 DAO 的机械改造 + 全量后端测试；**风险中等，收益最高**（数据安全）。

### 决策 D-4：API 契约从代码派生（而不是手写三份）

| 今天的三个真相源 | 新架构 |
|---|---|
| `http/*Routes.kt`（代码） | **唯一真相源** |
| `agent-api.json`（手写目录，144 条，漏 8 条） | 构建期从路由表**生成** |
| `web/src/lib/api/types.ts`（手写 956 行） | 构建期从 `model/*.kt` **生成** |

- **收益**：直接消灭 `02` §0.3 那五类漂移（`progress` 字段不存在、`groupId` 可空性相反、`?url=` vs `?u=` 的线上 400、`AboutInfo.ai` 死字段…）。
- **成本**：一个 Kotlin → JSON Schema → TS 类型的生成器（约 1–2 天量级）+ CI 检查"生成物与代码一致"。
- **替代方案**：继续手写 + 加强测试 —— **已在做，且失败了**：`ApiCatalog.test.ts` 存在，仍然漏 8 条端点，因为判据本身写窄了。

### 决策 D-5：兼容性是第一等公民（独立的 compat 模块）

- 把 `product/app/src/test/resources/rule-golden/**`（6 类样本）+ 真实社区书源抽样，扩成 `compat/` 模块：
  - 输入：书源 JSON + 目标 URL（离线快照）
  - 断言：规则求值结果**逐字节一致**
- **规则**：任何重建步骤，**先让 compat 绿，再说别的**。
- 代价：需要把网络样本离线化（录制-回放），这是本提案里**最容易被低估的工作量**（见 `10` R-3）。

### 决策 D-6：前端保持"轻框架"，但补三个原语

| 项 | 今天 | 目标 | 理由 |
|---|---|---|---|
| 路由 | `hash` + `PAGES` 数据表（`lib/pageMeta.ts:31-49`） | **不变**（照抄） | 比 router 库更适合单页外壳，7 条路由加一行就够 |
| 状态 | 各页面自管 + 一个 `useSyncExternalStore` 好样板（`lib/searchStore.ts:182-205`） | 把该范式变成**默认**；阅读器引入**显式状态机** | `ReaderScreen` 34 state/27 effect 靠 effect 互耦（`04` C1） |
| 弹层 | 31 处各自实现，19 处无焦点陷阱 | 一套 `Dialog` 原语 | `04` C2 |
| 样式 | 单一 `styles.css` 6,757 行 | 设计令牌（`ui/color/scheme.ts:39` 已有 38 角色）+ 组件样式 | `04` B11 |
| 类型 | 手写 `types.ts` 956 行 | 生成（D-4） | `04` B10 |

## 3. 安全边界（按 07 分册的结论，重建时必须**设计进去**，不是加固）

| # | 边界 | 今天的状态 | 新架构的落点 |
|---|---|---|---|
| S1 | **出站唯一入口**：受控工厂 + 钉 IP 代理，禁止裸客户端 | 有实现（`ops/PinnedProxy` + `NetworkSecurity`）但**不是强制入口**（6 处裸建） | `kernel/fetch` 是唯一出口 + R2 判据 |
| S2 | **沙箱 = 白名单 + ClassShutter + 预算**（含**出站次数**与**纯 JS 堆**两档） | 白名单/ClassShutter 已强；**出站次数无预算**（07 P1-5） | 预算计数器落在 `kernel/fetch` 内（不可绕过）+ `kernel/jssandbox` |
| S3 | **默认回环 + 外部绑定必须过鉴权** | 非回环只打一条警告就放行（`Application.kt:144-153`）；Docker 默认 `0.0.0.0` | `app/` 启动闸门：非回环 ⇒ 必须提供 token 或反代声明，否则拒绝启动 |
| S4 | **不可信页面 = 服务端响应级 `CSP: sandbox`** | 前端 iframe 全 sandbox 无 `allow-same-origin`（好），但代理 HTML 无响应级 CSP（07 P2-8） | `kernel/webproxy` 出站响应统一加头 |
| S5 | **导入面 = 魔数判容器 + 真实字节封顶 + 单事务 + 不落盘**；请求体上限推广到所有原始文本端点 | 导入面已达标；`receiveStrictText` 无上限（07 P2-9） | `kernel/safety` 提供统一 body limit |

> 另有三条"边界依赖的脆弱前提"，重建时要显式写进设计说明而不是留在代码里：
> ① 同源写门**只挡带 Origin 的浏览器跨站写**，本机任意进程不受限（`http/Guard.kt:15-20`）；
> ② Cookie 按 eTLD+1 共享，是"方便"换来的跨站风险（`data/CookieDao.kt:27-33`）；
> ③ 自定义 TTS 有意放行内网（常见用法就是指向本机合成服务）。

## 5. 明确"不做什么"（防过度设计清单）

| 不做 | 为什么 |
|---|---|
| 微服务 / 多进程 / 消息队列 | 单用户本地应用，SQLite 单写连接。引入分布式只会把「一条写连接」的优势变成劣势 |
| ORM（Exposed / Room / Hibernate） | 现有手写 SQL 是资产（21 表、14 索引、3 触发器，全部显式可控）。ORM 会把"迁移风险"变成"框架行为风险" |
| GraphQL / gRPC | 单客户端、146 条端点、契约已能用 JSON 描述。换协议层收益为 0，成本为全部客户端重写 |
| DI 框架（Koin/Hilt） | 组合根只有一处（`Application.kt`），构造注入足够。DI 框架会隐藏依赖方向，而依赖方向正是要判据化的东西 |
| 前端 router 库 / 状态库（Redux/Zustand） | 7 条路由 + 数据表已够；状态问题在 `ReaderScreen` 的**结构性**，换库不解决 |
| CSS-in-JS / Tailwind 引入 | 已经有 38 角色可计算配色 + 令牌门面（`ui/color/scheme.ts:39`），缺的是收敛纪律，不是新工具 |
| 插件系统 / jar 扫描 | 2026-10-26 已整体移除（`docs/ARCHITECTURE.md:621`），不要借重建复活 |
| 多用户 / 账号体系 | 产品定位是「一个人一台机器」（`http/Guard.kt:15-20` 的产品决策）。要做多用户是产品方向变更，不是架构问题 |
| 一次性大迁移（big-bang） | 本项目已发生过「77 个编译错误的在途重构」（`d6f8ae7`）与「54 处类型错误回退」（`docs/ARCHITECTURE.md:690-698`） |

## 6. 与初步方向的差异（项目负责人给的初始设想 vs 本提案）

| 初始设想 | 本提案 | 差异原因 |
|---|---|---|
| Kotlin / Ktor / React / TypeScript / SQLite | 一致 | 现有技术栈不需要换，换栈是最贵且最不产生用户价值的选择 |
| 模块化单体 | 一致，并给出**按域纵切**的具体切法 | 「模块化」若仍按 `http/data/rules` 横切，等于没模块化 |
| 清晰的领域模型 | **部分采纳** | 领域层确实要加强（进度/正文/凭据口径唯一化），但**不做完整 DDD 战术模式**（聚合根/仓储接口/领域事件全套）——7 个域 × 全套战术模式 = 单人维护不动 |
| 独立规则执行引擎 | 一致，且给出**依赖倒置的具体接口** | 这是修 B1 的唯一正确做法 |
| 统一数据访问层 | 一致，但**只统一事务形态**，不统一 SQL 写法 | 手写 SQL 是资产 |
| 统一 API 合约 | 一致，且**从代码派生**（不是再手写一份） | 手写已失败过一次 |
| 完整兼容性测试 | 一致，升级为 `compat/` 模块 | 这是重建的验收底座 |

## 7. 风险与开放问题（详见 10 与 11）

- 本提案最大的不确定项是 **D-5 兼容性离线化的工作量**（录制-回放真实书源），以及 **C1 阅读器状态机重写的判据缺口**（7 个 reader hook 今天零覆盖）。
- 需要项目负责人决策的三件事：AI 子系统去留（`11` Q-1）、`RuleProcessor` 扩展点去留（`11` Q-3）、是否接受「保留手写 SQL 与自研路由」这个"不够现代"的选择（`11` Q-5）。
