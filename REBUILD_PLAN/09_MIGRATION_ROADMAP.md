# 09 分阶段迁移路线

> 本册把 `08` 的提案变成**可执行、可验收、可回滚**的步骤序列。
> 三条硬约束贯穿全程（来自项目负责人的长期规则 + `01` §4.4 的失败记录）：
> **① 每一步都必须可编译、可测试、可回滚；② 每一步的改动范围必须事先声明；③ 兼容判据先立，再动实现。**

---

## 0. 路线总图

| 阶段 | 名称 | 目标 | 出口判据（一句话） |
|---|---|---|---|
| **0** | 全面审计 | 建立可信资产地图 | **本目录 11 份文档**（已交付） |
| **1** | 架构设计落定 | 把 `08` 提案收敛成施工图 + 判据清单 | 负责人签字：模块边界表、依赖规则 R1–R6、compat 方案 |
| **2** | 判据先行（不做功能） | 先造尺子，后动手术 | `compat/` 能跑、6 条 grep 门禁上线且**当前基线全绿/白名单化** |
| **3** | 基础重建 | kernel 六件套（db / fetch / text / model / obs / safety） | kernel 单测独立可跑；老代码改成调用 kernel 后**行为零变化** |
| **4** | 业务重建（域纵切） | 11 个域逐个搬到新形状 | 每域：compat 绿 + 契约测试绿 + 老端点响应逐字节一致 |
| **5** | 前端重建 | 类型生成、Dialog 原语、阅读器状态机、样式收敛 | `tsc -b` 绿 + 现有 139 个前端测试绿 + 交互判据补齐 |
| **6** | 产品化 | 安装/部署/升级/数据迁移/签名 | 干净机器一次装好；老库升级后有回滚；产物签名 |

> **阶段 2 是本路线与原计划最大的差异**：原计划把"核心提取"放在架构设计之后直接动代码；本路线坚持**先造判据**。理由是本项目已经因为"没有判据就重构"付过两次学费（54 处类型错误回退、77 个编译错误在途）。

## 2. 阶段 2 · 判据先行（最重要的一步）

### 2.1 六条门禁（一次性上线，允许白名单基线）

| 门禁 | 表达式（示意） | 白名单基线（今天的已知违例） |
|---|---|---|
| G1 kernel 不许反向依赖域 | `kernel/**` 出现 `import io.legado.<domain>` | 0（今天是 0，可以硬红） |
| G2 只有 data 层拼 SQL | `data/**` 外出现 `executeQuery\|prepareStatement` | 待登记（`http/` `rules/` 里的直连） |
| G3 只有 fetch/app 建 HTTP 客户端 | `fetch/**`、`app/**` 外出现 `HttpClient.newBuilder` | **6 处**（`DesktopLauncher.kt:313,323`、`EdgeTtsService.kt:28`、`ExternalBrowserLogin.kt:99`、`WebViewProxy.kt:60`、`UpdateCheck.kt:42`） |
| G4 禁止手动 `autoCommit` | `setAutoCommit` 只允许 `kernel/db` | **12 处**（Shelf 6 / Sources 4 / Cache 1 / SourceHealth 1） |
| G5 DTO 只在 model | 其他包出现 `@Serializable data class` | 待登记（`LogEntry`@`ops/LogService.kt:178`） |
| G6 端点目录与代码一致 | 生成目录 == 代码注册 | 今天**已知 8 条差异**（146 vs 144 + `/brand` 6 条 + 方法正则漏 HEAD/OPTIONS） |

> **白名单只许单调缩小**——这条纪律本项目已在 `tools/verify/depth-check.mjs` 的 `KNOWN_DEEP` 上验证过有效，照抄。

### 2.2 compat 模块骨架

- 输入：`rule-golden/**` 6 类样本 + 增量录制的真实书源响应（离线）。
- 断言：规则求值输出逐字节一致（沿用 `GoldenRuleTest` 的既有口径）。
- 覆盖目标：搜索 / 详情 / 目录 / 正文 / 登录 v1 / 登录 v2 / RSS / 分页 —— 8 条链路各至少 1 个样本。

### 2.3 退出判据

- 6 条门禁在 CI 上跑，白名单数量**打印出来并被记录**（这样"缩小"是可量化的）。
- `compat` 模块能跑通现有 6 类黄金样本（**不改任何实现**，只是把它变成可独立运行的模块）。

**为什么这一步先做**：后面每一步都要靠它证明"行为没变"。没有它，阶段 3/4 的每一次改动都是盲改。

## 3. 阶段 3 · 基础重建（kernel 六件套）

> 顺序按「**风险从低到高、依赖从少到多**」排。每一步都是独立可交付的切片。

| 切片 | 内容 | 规模 | 判据 | 风险 |
|---|---|---|---|---|
| **3.1 `kernel/text`** | 字符集判定 6 份 → 1 份；编码/净化/LooseJson 原语 | M | 单测 + 各处调用点行为一致 | 低（纯函数） |
| **3.2 `kernel/model`** | DTO 归位（`LogEntry` 搬出 `ops/`，断开 `data↔ops` 环） | S | G5 绿；序列化字节一致 | 低 |
| **3.3 `kernel/db` 事务收口** | 删除 12 处手动 `autoCommit`；`read/write/transaction` 三形态 | **L** | G4 硬红；全量后端测试；**回滚演练**（0.2.35 事故场景重放） | **中高**（数据安全） |
| **3.4 `kernel/db` Schema 对齐** | 终态 DDL（补齐 5+3+1 列）；迁移只为老库；修 `cookie_jar=null` 与静默 `return@forEach` | M | 新库建表即终态；老库升级后逐列 diff 一致；`book_mark` 一次性迁移 | **高**（涉及真实用户库，必须先快照） |
| **3.5 `kernel/fetch`** | 唯一出站原语：SSRF 闸门 + IP 固定 + 重定向策略 + 限读 + 出站预算计数器 | **L** | G3 硬红；原 8 份抓取点全部改调用；3 份漏 gzip 限流的点被修掉 | 中（面广但机械） |
| **3.6 `kernel/obs` + `kernel/safety`** | 日志脱敏、body limit、启动闸门（非回环必须鉴权） | M | 脱敏判据（Cookie/token 不出现在日志）；body limit 单测 | 低-中 |

**阶段 3 出口判据**：kernel 六个包可以脱离域模块单独跑测试；老代码改成调用 kernel 后，compat + 全量测试**零差异**。

## 4. 阶段 4 · 业务重建（11 个域纵切）

### 4.1 迁移顺序（按"耦合度低 → 高"）

| 批次 | 域 | 理由 | 规模 |
|---|---|---|---|
| 批 1 | `localbook`、`rss`、`explore`、`media` | 耦合最低、判据已有；先跑通"域纵切"这个动作本身 | S–M |
| 批 2 | `backup` | 口径成熟（A6），依赖面清楚 | M |
| 批 3 | `shelf` | 事务问题集中（`ShelfDao` 6 处 autoCommit），配合 3.3 一起验 | M |
| 批 4 | `source` | 书源编解码是资产（A3），搬家风险可控 | M–L |
| 批 5 | `reading` | 进度/正文/缓存口径唯一化（`04` §4 表），要拆 `ReadingRoutes.kt:140-197` 的编排 | **L** |
| 批 6 | `search` + `login` | 搜索有 SSE/WS 边界；登录有 `WebViewProxy` 817 行 + `data↔source` 环 | **L** |
| 批 7 | `tts` | provider 接口化（B13）+ 出站校验统一 | M |

### 4.2 每个域的"完成定义"（必须逐条打勾）

1. 域内固定三层（`api/ domain/ data/`），跨域 import 只剩对方 `api/*`（G1/G3 判据扩展）。
2. 该域的全部端点，**响应字节与迁移前一致**（compat + 契约测试）。
3. 该域的"唯一权威"落到 `domain/`（`08` §4 负责人表跑通）。
4. 该域对应的旧文件**标记为待删**（不立即删；给一个发布周期观察）。
5. `12`（本册 §7）式的"改动范围声明"提交在 PR 描述里。

### 4.3 明确禁止的并行改动

- 迁移某域时**不许顺手改该域以外的文件**（除组合根装配）。
- **不许**在批次中途更换依赖版本（换版本与换结构分开，否则失败无法归因——本项目 `f4d878b` 换引擎时就是单独一刀）。
- **不许**在批次中途做格式化（会产生无法 review 的 diff）。

## 7. 每次提交的"改动范围声明"模板（落实铁律 2）

```markdown
## 本次切片
- 切片：3.3 事务收口 / ${域}
- 声明改动范围（只允许这些路径）：
  - kernel/db/**
  - data/ShelfDao.kt, data/SourcesDao.kt, data/CacheDao.kt, data/SourceHealthDao.kt
- 不允许出现的改动：任何 http/**、任何前端文件、任何依赖版本

## 判据（贴输出）
- G4 门禁：0 处 setAutoCommit（白名单从 12 → 0）
- compat：8/8 通过
- 后端全量测试：993/993
- 回滚场景重放：0.2.35 批量删书 case 通过

## 回滚方式
- 单提交 revert；数据无需回滚（本次不改 Schema）
```

**纪律**：评审时**只看两点**——改动是否落在声明范围内；判据是否真的跑了（不贴输出视为没跑）。

## 8. 里程碑与"最小可用重建"边界

如果要在有限投入下拿到最大收益，**做到阶段 3 + 阶段 4 批 1–3** 即可获得：

- 数据安全层面最危险的两类问题（事务双轨、Schema 缺列/孤儿）被解决；
- 契约漂移被工程化消灭（类型生成）；
- 域纵切的形状立起来了，后续批次变成"填空题"；
- 前端不受影响（只换类型来源），用户可感知变化最小。

反之，**阶段 5.4（阅读器状态机）与阶段 3.4（Schema 对齐）是仅有的两个"必须由负责人亲自把关"的切片**——前者关乎体验，后者关乎用户数据。
