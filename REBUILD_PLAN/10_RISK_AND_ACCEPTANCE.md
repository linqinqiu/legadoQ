# 10 风险与验收标准

> 本册回答两个问题：**重建过程中什么会出错**（风险登记），以及**什么叫"做完了"**（验收标准）。
> 验收标准写得比通常更苛刻，原因见 `01` §4.4：这个项目已经出现过「文件写了但没做完」「测试绿但判据写窄了」「门面类零调用方」三类假完成，每一项都骗过了当时的评审。

## 2. 验收标准

### 2.1 整体完成定义（Definition of Done）

重建整体完成，需要**同时**满足以下 10 条。任何一条不满足，就不叫完成：

| # | 条目 | 判据形式（必须可复现） |
|---|---|---|
| 1 | 兼容性未退化 | `compat` 8 条链路全绿；**并附真实源抽样批结果**（≥50 个社区源 × 搜索/详情/目录/正文） |
| 2 | 后端行为未退化 | 后端全量测试通过数 **≥ 993**（现值）+ 新增判据；不允许通过"删测试"达标 |
| 3 | 前端行为未退化 | 139 个既有测试文件全绿 + `tsc -b` 通过 + 新增交互判据 |
| 4 | 架构规则被守住 | G1–G6 六条门禁全绿，且**白名单数量单调下降有记录**（12→0、6→0、8→0） |
| 5 | 用户数据安全 | 真实用户库副本：升级演练通过 + 可回滚 + `book_mark` 那 1 行书签迁移后可见 + 孤儿行处理有记录 |
| 6 | 契约唯一真相源 | 端点目录与 TS 类型均为**生成物**，CI 校验"生成物与代码一致"；不存在手写第二份 |
| 7 | 安全五项边界成立 | `08` §3 的 S1–S5 各有**可执行判据**（不是注释） |
| 8 | 性能不退化 | `/healthz` < 1s；搜索首批返回时间不慢于基线（基线需在阶段 2 建立并记录） |
| 9 | 可安装 | 干净机器（无 JDK/无 Node）一次装好；两机器同提交构建产物哈希一致 + 签名可验 |
| 10 | 文档与实现一致 | README 功能表、`API-REFERENCE`、`ARCHITECTURE` 三处由门禁保证与代码一致 |

### 2.2 阶段级验收（Gate）

| 阶段 | 必须通过 | 不通过则 |
|---|---|---|
| 1 | 1.1–1.5 产出齐全；Q-1/Q-3/Q-5 已决策 | 不进阶段 2 |
| 2 | 6 条门禁上线且基线被记录；compat 能跑通现有 6 类样本 + **至少 1 条离线真实链路** | 不进阶段 3（不许"边做边补判据"） |
| 3 | kernel 六包可独立测试；老代码改调 kernel 后 compat + 全量测试零差异；G3/G4 白名单归零 | 该切片回滚，不进下一包 |
| 4 | 每域五条完成定义全打勾（`09` §4.2） | 该域回滚，不并行开下一域 |
| 5 | 139 测试 + 新增交互判据 + `styles.css` 行数下降 | 5.4 单独回滚（不影响其它切片） |
| 6 | 真实库升级演练 + 干净机器安装 + 签名 | 不发布 |

### 2.3 "不算完成"清单（Anti-DoD）

以下情形**历史上都被当成过完成**，本重建期间一律不算：

| 情形 | 为什么不算 | 历史实例 |
|---|---|---|
| 文件被拆小了，但没有新判据 | 拆小 ≠ 解耦；`ReaderScreen` 拆出 7 hook 后仍有 34 state / 27 effect | `04` C1 |
| 写了门面/服务层类，但零调用方 | 「写了文件」不等于「做完了」 | `http/HttpClients.kt`（被删）、`GuardedHttpClient.kt`（零强制力） |
| 文档写了新架构，代码没改 | 文档不是实现 | `ARCHITECTURE.md` §7「AI 网关」整段失效 |
| 测试绿了，但断言只查状态码 200 | 判据写窄会让门禁绿着漏 bug | `ApiCatalog.test.ts:91` 方法正则漏 HEAD/OPTIONS → 漏 8 条端点 |
| 端点目录的 `count` 从文件读 | 自己数自己，永远相等 | `RouteCatalog.kt:45` 用 `endpoints.size` 覆盖 `count` |
| 覆盖率数字上升，但新增覆盖都在 getter 上 | 覆盖率不是质量指标，判据才是 | `docs/STATUS.md:213` 承认 `tts`/`http` 覆盖薄是因为"路径不可注入" |
| `runCatching` 吞掉异常后"没有报错" | 静默失败等于没做（418 处 `runCatching`，`LogService` 零脱敏） | 07 §3-8 |

## 4. 用户数据保护红线（不可协商）

1. **任何涉及 Schema 的改动，必须在真实用户库副本上先演练**，且演练脚本可反向执行。
2. **`DbSnapshot` 必须在迁移之前生成**（现状问题：`app_user/session` 的 `drop table` 落在快照之前，`db/Schema.kt:196-199`）。
3. **不可逆的数据抹除一律禁止**：`Migration.kt:100` 的 `cookie_jar = null` 必须改为"保留原值 + 标记"，否则用户书源的登录态会被静默清空。
4. **导出必须覆盖全部用户数据域**：现状 5 域，`book_note`（笔记/书签）**零导出入口**（05 §7 P0-3）——这是"换设备即永失"，重建前必须补。
5. **孤儿数据处理要先确认归属**：`book_mark` 含 1 行真实书签、`reading_progress` 含 4 行孤儿 —— 迁移时**先迁移再清理**，不许直接删表清行。
